# Research: Local Whisper transcription for uploaded meeting files

## Goal

Determine the implementation strategy for `docs/plan-transcribe-uploaded-meeting-files-with-local-whisper.md` / `docs/prd-transcribe-uploaded-meeting-files-with-local-whisper.md`: transcription status + transcript columns on `Meeting`, a locally-executed Whisper "tiny" engine triggered automatically on upload, a `POST /meetings/:id/transcription/refresh` endpoint, and status/transcript display plus a refresh button on `/meetings/[id]` — built on the existing CQRS/Prisma backend and the existing Next.js/HeroUI/axios frontend, with no new infrastructure.

Two questions the plan leaves genuinely open are resolved here: **which** local Whisper runtime to introduce (the PRD only says "a Node binding, a bundled binary, or a subprocess" — settled below as `nodejs-whisper`, per team preference), and **how** the fire-and-forget dispatch it prescribes should be expressed in a codebase that already has exactly one async-side-effect pattern.

**Status: verified end-to-end, not just researched.** After the required toolchain (`build-essential`/`cmake`/`ffmpeg`) was installed, `nodejs-whisper` was actually run against real `.wav`/`.mp3`/`.mp4` files on this machine — model download, CMake build, and inference all completed successfully, producing a correct transcript from all three formats. Point 1 below has the full account, including a real build-time measurement (5+ minutes) and a reproduced failure mode (an interrupted first build leaves the install silently broken) that a setup script needs to guard against.

## Recommended solution

Follow the plan's five phases as sequenced. Five points below refine specific tasks; everything else in the plan already matches this repo's conventions.

### 1. Engine: `nodejs-whisper` (team-selected), with its C/C++ toolchain and system-ffmpeg prerequisites made explicit

**Team preference is `nodejs-whisper`.** An earlier pass of this research defaulted to `@huggingface/transformers` (Transformers.js) specifically to avoid a native build step, since this machine has no `gcc`/`cmake`/`make`. That trade-off is overridden here: `nodejs-whisper` is adopted, and the toolchain it needs becomes a documented project prerequisite — the same posture the repo already takes for Postgres (`docker compose up -d db`) and the Playwright browser binary (`npx playwright install chromium`), both external to `npm install` and both called out explicitly in `CLAUDE.md`/`apps/web/CLAUDE.md`.

| Candidate                     | Install requirement                                                                                                                                  | Verdict                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `smart-whisper@0.8.1`         | `"install": "node-gyp rebuild"` — compiles whisper.cpp on **every** `npm install`                                                                    | Rejected — the build cost is unconditional, not deferred |
| `nodejs-whisper@0.3.1`        | No install/postinstall script (verified — `npm install` alone succeeds, see below); builds whisper.cpp via CMake lazily, on first model download/use | **Recommended (team preference)**                        |
| `@napi-rs/whisper@0.0.4`      | Prebuilt napi binaries, but 0.0.x, last published Dec 2024, linux-x64-gnu/darwin only (no win32)                                                     | Rejected                                                 |
| `@huggingface/transformers@3` | Plain `npm install`; `onnxruntime-node` ships prebuilt `.node` binaries; no native toolchain needed                                                  | Viable, no longer recommended — see Open questions       |

**Verified by installing the real package (`nodejs-whisper@0.3.1`) in a throwaway directory, not just reading its metadata:**

- `npm install nodejs-whisper` succeeds with **no toolchain present** on this machine (`gcc`/`cc`/`make`/`cmake`/`g++` all absent) — there is no `install`/`postinstall` script; the package's `files` field is only `["dist/", "cpp/"]`. Total footprint: **36 MB**, whisper.cpp's C++ source vendored under `node_modules/nodejs-whisper/cpp/whisper.cpp/`. This is an order of magnitude lighter than Transformers.js's `onnxruntime-node` + `sharp` footprint (~380 MB, the prior recommendation's verified number) — a genuine advantage of this choice.
- The CMake build is deferred to first use, not `npm install` time. Confirmed by tracing the library's actual model-check → WAV-conversion → transcribe call chain (`nodewhisper(filePath, { modelName, autoDownloadModelName })`, `dist/index.js`) rather than assuming from the README. The build itself (`cmake` configure + `cmake --build build --config Release` against the vendored `cpp/whisper.cpp/`) runs the first time a model is actually needed — i.e., the first real upload in a freshly-provisioned environment, unless a setup step forces it earlier (see point 3, below).
- **The runtime shells out to a bare `ffmpeg` on `PATH`**, confirmed by reading `nodejs-whisper`'s `convertToWavType` (`ffmpeg -nostats -loglevel error -y -i "<in>" -ar 16000 -ac 1 -c:a pcm_s16le "<out>"`, run via `shelljs`'s `.exec()`) and by reproducing the actual failure on this machine: calling `nodewhisper()` on a real path with no `ffmpeg` installed fails with `/bin/sh: 1: ffmpeg: not found`. Unlike the Transformers.js path, `nodejs-whisper` does **not** bundle a binary — a working `ffmpeg` on `PATH` is a hard runtime prerequisite, not an implementation detail this project controls.
- **The transcription call itself is asynchronous, not a blocking `execSync`.** Traced `nodewhisper()`'s call chain down to `executeCppCommand` → `whisperShell`, which wraps `shelljs`'s callback-based `.exec()` in a `Promise` — the actual whisper.cpp binary runs as a genuine child process, off the Node event loop. This is a meaningful simplification over the Transformers.js path: **no `worker_threads` Worker is needed** for isolation (see point 4, below) — a plain `await` already keeps the HTTP event loop responsive, since the CPU-heavy work happens in a separate OS process by construction, not interleaved JS on the calling thread.
- **`npx nodejs-whisper download` (the package's own CLI) is interactive-only and cannot be scripted.** Verified by running it in a non-TTY shell: it prompts via `readline-sync` for a model name with no `process.argv`/env-var override (confirmed by reading its source), and fails hard (`The current environment doesn't support interactive reading from TTY`) when stdin isn't a real terminal — exactly the environment every `npm run setup:*`-style script, CI job, or this sandbox runs in. **Do not use this CLI as the project's setup step.** Use the library's own `autoDownloadModelName`/`modelRootPath` options instead (point 3, below), which hit the same download logic non-interactively — verified working: a direct `nodewhisper(path, { modelName: 'tiny', autoDownloadModelName: 'tiny' })` call fetched a real 74 MB `ggml-tiny.bin` over the network with no prompt.

**Full end-to-end run verified after installing the toolchain (`build-essential`/`cmake`/`ffmpeg`, Debian 13 trixie — `gcc` 14.2.0, CMake 3.31.6, `ffmpeg` 7.1.5):**

- `npm install nodejs-whisper` → a real `nodewhisper()` call against `whisper.cpp`'s own bundled sample recording (11 s, public domain — found, via `find node_modules/nodejs-whisper/cpp -iname "*.wav"`, at `cpp/whisper.cpp/bindings/go/samples/jfk.wav`, not at a top-level `samples/` path) downloaded the real `ggml-tiny.bin` (77.7 MB) and ran the CMake build end-to-end. Result matched the known transcript exactly: `"And so, my fellow Americans, ask not what your country can do for you, ask what you can do for your country."`, with `auto-detected language: en (p = 0.977)`.
- **Repeated the same call against real `.mp3` and `.mp4` files, not just `.wav`** — generated with system `ffmpeg` from the same source audio (`.mp3` via `libmp3lame`; `.mp4` by muxing it against a synthetic black video track via `libx264`/`aac`, since `nodejs-whisper` needs a real container to demux, not just a renamed file). Both produced the identical correct transcript, confirming the library's `ffmpeg`-based demux/decode step handles both formats this project actually needs. Wall-clock inference time on this 8-core machine: **~2.2 s for `.mp3`, ~2.8 s for `.wav`, ~3.4 s for `.mp4`** (the small gap for `.mp4` is the extra video-stream demux step, not slower ASR) — all for an 11 s clip on the `tiny` model, CPU-only, no GPU.
- **The one CMake-version claim in the earlier draft was wrong — corrected here.** The prior pass of this research repeated a web search snippet claiming `nodejs-whisper` "needs CMake v4+ already available." The actual build succeeded cleanly on **CMake 3.31.6** (Debian 13's stock `apt` version) with no configure error — there is no v4 floor in practice, at least not for the `tiny`-model / CPU-only build path exercised here. Treat the earlier "v4+" claim as unverified secondhand information rather than a real requirement; any Debian/Ubuntu LTS's stock `cmake` package is very likely sufficient.
- **The build is real work, not incidental — budget for it explicitly.** On this machine (8 cores, `-j4` used deliberately — see below) a _cold_ `cmake --build` took over 5 minutes; it compiles far more than the `tiny`-model path strictly needs (`whisper-server`, `parakeet-cli`, several test binaries, etc. — `nodejs-whisper`'s vendored `CMakeLists.txt` builds whisper.cpp's whole example/test suite by default, not just `whisper-cli`). This directly informs point 3's "budget an explicit build step" guidance below and the Jest-timeout risk already flagged in Risks.
- **A genuine, reproducible failure mode: an interrupted first build leaves the install permanently broken until someone notices and fixes it by hand.** Reproduced directly: killed a first `nodewhisper()` call mid-build (a `timeout` cutting it off partway through CMake compilation, simulating a CI job timeout or an OOM-killed process — this machine had only ~513 MB free RAM at the time, which is why the resumed build was deliberately capped at `-j4` rather than `-j8`). The **model download had already completed** before the kill (`ggml-tiny.bin` fully on disk), but the compiled `whisper-cli` binary had not finished linking. On the next `nodewhisper()` call, the library logged `"tiny already exist. Skipping download."` and went straight to `Error: whisper-cli executable not found` — **it does not re-attempt the build once the model file is present**, because the build is only triggered as a side effect of the download step, not as an independent "is the binary present and working" check. Manually re-running `cmake --build build --config Release` in `node_modules/nodejs-whisper/cpp/whisper.cpp/` (which resumed from the partial object files, not a cold rebuild) fixed it — but nothing in the library itself would have recovered automatically. This is not a hypothetical edge case; it is exactly what will happen to the first real deploy or the first CI run if the build step is left to happen lazily inside a request instead of an explicit, generously-timed setup step (point 3's `npm run setup:whisper` script is the fix — see the added bullet there).

Pipeline shape, driven entirely by the library's own `nodewhisper()` call:

1. `nodewhisper(storedFilePath, { modelName: 'tiny', autoDownloadModelName: 'tiny', modelRootPath, whisperOptions: { outputInText: true } })` — pass any of the seven accepted extensions directly; the library's own `ffmpeg` shell-out (above) handles both the `.mp4` demux and format normalization for every other type, so no separate audio-extraction step is needed in this project's own code.
2. The **multilingual** `tiny` model, not `tiny.en` — the PRD specifies "transcription only, in the source language" and does not restrict input to English.
3. `whisperOptions.outputInText: true` for plain transcript text (matches the PRD's "displaying the completed transcript as plain text" — no need for the SRT/VTT/JSON output variants the library also supports).

### 2. Toolchain and ffmpeg: new, explicit, non-npm project prerequisites

Adopting `nodejs-whisper` means this project gains two prerequisites that `npm install` cannot satisfy on its own — both need a `CLAUDE.md` section of their own (root, next to "Local database"), written with the same "install once, outside of `npm install`" framing already used for Postgres and the Playwright browser:

- **A C/C++ toolchain + CMake.** Linux: `build-essential` + `cmake` (the README's own instruction: `sudo apt update && sudo apt install build-essential cmake ffmpeg`). Verified working end-to-end (see point 1) with `gcc` 14.2.0 and **CMake 3.31.6 — Debian 13's plain `apt` package, no PPA or manual CMake install needed.** (An earlier pass of this research repeated a secondhand claim that "CMake v4+" is required; that was not reproduced — a stock Debian/Ubuntu LTS `cmake` built the whole thing cleanly, so don't treat v4 as a real floor without your own evidence otherwise.) macOS: Xcode Command Line Tools (`xcode-select --install`) generally already provides `make`/`clang`; a CMake install is still needed (Homebrew: `brew install cmake`). Windows: MSYS2 or MinGW-w64, per the package's own Windows instructions, plus ensuring `make`/`mingw32-make` is on `PATH` — this path remains unverified in this research (no Windows machine available), unlike the Linux path above. `NODEJS_WHISPER_CMAKE_ARGS` is available for passing custom CMake flags (e.g. disabling native CPU optimizations for a more portable build) if a specific dev machine's build fails. **Budget real time and RAM for the first build**, not just disk space: on an 8-core Linux machine with limited free RAM (~513 MB at build time here), a cold build took over 5 minutes even for `tiny`-only usage, because `nodejs-whisper`'s vendored `CMakeLists.txt` builds whisper.cpp's entire example/test suite (`whisper-server`, `parakeet-cli`, several test binaries), not just the one `whisper-cli` binary this project needs — a low-memory CI runner running the default (unlimited) parallel job count risks the compiler getting OOM-killed mid-build, which point 3's "verify the binary, not just the model" guard below is specifically meant to catch.
- **`ffmpeg` on `PATH`.** Standard OS package manager install (`apt install ffmpeg` / `brew install ffmpeg` / a Windows installer + `PATH` entry) is the straightforward option and is what's recommended here, since `nodejs-whisper` shells out to whatever `ffmpeg` command it finds — there is no way to point it at a specific binary path via its public API (confirmed from its `IOptions` types: no `ffmpegPath` field). An `ffmpeg-static` + `PATH`-prepend workaround (setting `process.env.PATH` to include `ffmpeg-static`'s directory before the module that calls `nodewhisper()` loads) is possible but adds npm weight and a GPL-3.0-or-later license question, for a dependency this approach can otherwise treat as a normal system prerequisite like Postgres. Document a plain system-`ffmpeg` install as the default; keep the `ffmpeg-static` route as a documented fallback for a dev machine where a system package isn't easily installable.

Both belong in a "Local Whisper transcription" section of root `CLAUDE.md`, cross-referenced from `apps/api/CLAUDE.md`'s "Meetings" section, the same two-file split the repo already uses for Postgres ("Local database" in root, connection details in `apps/api/CLAUDE.md`'s "Database (Prisma)").

### 3. Model download: an explicit, non-interactive setup script — not the package's own CLI, not a lazy first-request fetch

The PRD's acceptance criterion is "no audio/video or transcript text is sent to an external transcription service", and the plan's Phase 2 definition of done says this must be verifiable with the network disabled. `nodejs-whisper`'s `autoDownloadModelName` fetches the model from the network on first use if it isn't already present, which would violate that on a cold cache — and (worse, verified above) the package's own `npx nodejs-whisper download` CLI cannot be run non-interactively at all.

Mirror the repo's existing "install once, outside of `npm install`" precedent (`npx playwright install chromium`, documented in `apps/web/CLAUDE.md` as "not committed, not an npm dependency"):

- A small project-owned script (e.g. `scripts/setup-whisper.ts`, exposed as `npm run setup:whisper` from `apps/api`) that calls `nodewhisper()`'s underlying download path directly with a fixed `modelName: 'tiny'`/`autoDownloadModelName: 'tiny'` and an explicit `modelRootPath` under `apps/api/` — sidestepping the CLI's TTY prompt entirely, per the verified workaround above. This is also the natural place to force the CMake build eagerly (by running one real `nodewhisper()` call against a tiny bundled fixture) rather than deferring it to whichever request happens to be first. Give this script its own generous timeout in whatever runs it (a plain local `npm run`, a CI step, a Docker build layer) — **verified this build alone can take 5+ minutes**, well past what a request handler or a default CI step timeout would tolerate (see point 1).
- **The setup script's own success check must verify the compiled `whisper-cli` binary exists, not just that the model file downloaded** — this is not a hypothetical: reproduced directly (point 1) that `nodejs-whisper` only re-attempts the CMake build as a side effect of the download step, so if a build is interrupted (CI timeout, OOM-killed compiler — both realistic on a memory-constrained runner given the whole example/test suite gets built, see point 2) after the model already landed on disk, every subsequent `nodewhisper()` call fails immediately with `whisper-cli executable not found` and **the library never retries the build on its own**. The setup script must explicitly check for the built binary (`cpp/whisper.cpp/build/bin/whisper-cli` relative to the package's install location) after calling `nodewhisper()`, and fail loudly — with a clear "re-run `npm run setup:whisper`, or resume manually via `cmake --build build --config Release` in that directory" message — rather than reporting success just because the model download succeeded.
- Add that `modelRootPath` directory to the root `.gitignore`, alongside the existing `apps/api/uploads/` and `apps/api/prisma/generated/` entries — do not commit the ~74 MB `ggml-tiny.bin` to git.
- At runtime, always pass the same `modelRootPath` explicitly rather than relying on the library's default location, so "is the model present" is a single, predictable filesystem check.
- Guard it the way Postgres is guarded: `scripts/check-postgres.sh` runs via npm's `pre<script>` convention and "fails fast with a clear 'start it with `docker compose up -d db`' message instead of letting the failure surface later as an opaque Playwright `webServer` timeout". A sibling check (does `ggml-tiny.bin` exist at the configured `modelRootPath`? is `ffmpeg` on `PATH`? does the compiled `whisper-cli` binary exist, per the bullet above — not just "did a download run once"?) belongs in the same `pretest:e2e` hook, so a missing or half-finished prerequisite fails fast with a clear message instead of surfacing as an opaque transcription timeout deep in a Playwright/Jest run.

### 4. Trigger: publish an event on `EventBus`, don't float a `CommandBus.execute()`

The plan's Phase 2 says to "dispatch `TranscribeMeetingFileCommand` on the `CommandBus` without awaiting it". That works, but the codebase already has a documented pattern for precisely this, and it avoids a floating promise entirely.

`CreateUserHandler` (`apps/api/src/user/commands/handlers/create-user.handler.ts`) injects `EventBus` alongside `PrismaService` and calls `this.eventBus.publish(new UserCreatedEvent(...))` after its write; `UserCreatedHandler` (`@EventsHandler`) picks it up. `apps/api/CLAUDE.md` describes that handler as "the extension point for anything that should happen after a user is created (welcome email, analytics, etc.) without bloating `CreateUserHandler`" — a one-to-one description of what transcription needs.

Recommended shape:

- `MeetingTranscriptionRequestedEvent(meetingId, filePath, jobId)` in `src/meetings/events/`, published by **both** `UploadMeetingFileHandler` (after its transaction commits) and `RefreshTranscriptionHandler` (Phase 3).
- One `@EventsHandler` in `src/meetings/events/handlers/` that runs the job and owns the `PROCESSING → COMPLETED|FAILED` writes.
- Register it in `MeetingsModule`'s `providers` under an `EventHandlers` array, exactly as `UserModule` does (`const EventHandlers = [UserCreatedHandler];`).

Why this over the plan's floating command: `eventBus.publish()` returns `void`, so there is no promise to leak past the HTTP response and no `no-floating-promises` warning to suppress (that rule is downgraded to a warning in `apps/api/eslint.config.mjs`, but a warning is still noise). One trigger, two producers, no duplication between the upload path and the refresh path.

**The one thing this obliges you to get right:** `@nestjs/cqrs` does not await event handlers and does not catch their rejections. The handler must wrap its entire body in `try`/`catch` and write `FAILED` in the catch — an escaping rejection becomes an `unhandledRejection` that takes the process down under Node's default policy. This is the same discipline the plan already implies ("on any error, writes status `FAILED`"), just now load-bearing.

If the team prefers to keep `TranscribeMeetingFileCommand` as a named, independently-executable unit, keep it and have the event handler be the thing that executes it — the important part is that the _trigger_ is an event publish, not a dangling promise in a request-path handler.

### 5. Concurrency, isolation, and the stale-write guard

**No `worker_threads` Worker is needed — this is the one place `nodejs-whisper` simplifies over the earlier Transformers.js draft.** As verified in point 1: `nodewhisper()`'s actual transcription call (`executeCppCommand` → `whisperShell`) wraps `shelljs`'s callback-based `.exec()` in a `Promise` and runs the compiled whisper.cpp binary as a genuine child process. The CPU-heavy work happens off the Node process entirely, not interleaved JS on the calling thread the way Transformers.js's ONNX-Runtime-plus-JS-glue pipeline does — so a plain `await nodewhisper(...)` inside the `@EventsHandler` from point 4 already keeps the HTTP event loop responsive, with no extra isolation layer to build or to keep alive across restarts.

This still leaves a **concurrency cap of 1** worth adding explicitly (a serial promise chain / a tiny in-memory queue gating calls to `nodewhisper()`). The PRD explicitly puts "concurrency/queueing guarantees for many simultaneous transcription jobs" out of scope, but _unbounded_ is different from _unguaranteed_: without a cap, ten uploads spawn ten concurrent whisper.cpp child processes and contend for the same CPU cores (and, unlike an in-process model, each spawns its own OS process rather than sharing loaded weights). A single queue is a few lines and matches "single-server, best-effort processing is acceptable".

**Where this code lives:** a new `src/meetings/transcription/` directory mirroring the existing `src/meetings/upload/` — plain functions and constants (`getWhisperModelRootPath()` following `getUploadDir()`'s lazy-getter convention and its documented rationale), plus one small queue helper (a plain class or a closure over a promise chain) that every call to `nodewhisper()` goes through. Because there is no long-lived worker/thread to manage, this does **not** need to be a Nest `@Injectable()` provider with `OnModuleDestroy` lifecycle hooks — a module-scoped queue is sufficient, which keeps `src/meetings/transcription/` free of the "service layer" question the Transformers.js draft had to address for its worker's lifecycle.

**Guard the result write with a conditional update, not a row lock.** `UploadMeetingFileHandler` and `DeleteMeetingFileHandler` both use `SELECT ... FOR UPDATE` inside a transaction, but that pattern must _not_ be copied here: it would hold a Postgres transaction open for the entire duration of inference. Use a compare-and-set instead:

```ts
const { count } = await this.prisma.meeting.updateMany({
  where: {
    id: meetingId,
    filePath: startedFilePath,
    transcriptionJobId: jobId,
  },
  data: {
    transcriptionStatus: 'COMPLETED',
    transcriptionText: text,
    transcriptionUpdatedAt: new Date(),
  },
});
// count === 0 -> the file was replaced/deleted, or a newer run superseded this
// one, while inference was running. Drop the result silently.
```

This satisfies the plan's "re-reads the meeting row before writing its result and no-ops if `filePath` no longer matches" atomically rather than as a read-then-write race, and it costs nothing extra since the write happens anyway. Apply the same shape to the `PENDING → PROCESSING` transition.

The `transcriptionJobId String?` column in that `where` clause is one extra nullable column in the same migration, and it closes a race the `filePath` check alone cannot: a refresh issued while a job is mid-flight targets the _same_ `filePath`, so without a per-attempt token the older run's transcript can overwrite the newer run's. Phase 5 disables the refresh button during `PENDING`/`PROCESSING`, but that is a client-side guard only. Recommended; see Open questions if the team would rather skip it.

**Add a crash-recovery sweep.** `MeetingsModule` already implements `OnModuleInit` (to `mkdirSync` the upload directory). One additional statement there — `updateMany({ where: { transcriptionStatus: 'PROCESSING' }, data: { transcriptionStatus: 'FAILED' } })` — converts the plan's acknowledged "a job lost to a server restart is left in `PROCESSING` with no automatic resume" into a `FAILED` the organizer can actually recover from via the Phase 3/5 refresh button, which is the PRD's stated recovery path. Caveat to document: this is correct only for the single-server deployment the PRD assumes; with two API instances, a restart of one would mark the other's live jobs failed.

**Backend:**

- `nodejs-whisper`'s own `nodewhisper()` function — the whole engine boundary. Its `IOptions`/`WhisperOptions` types (`modelName`, `autoDownloadModelName`, `modelRootPath`, `whisperOptions.outputInText`, `logger`) are the only surface the new `@EventsHandler` needs to call; no bespoke audio-conversion code is needed since the library's own `ffmpeg` shell-out already normalizes every accepted extension to 16 kHz mono WAV.
- `apps/api/src/meetings/commands/handlers/upload-meeting-file.handler.ts` — the transaction/ownership shape to extend in Phase 1 (add the three column resets inside the same `tx.meeting.update`), and the publish point for the event afterwards. - `apps/web/src/components/meeting-file-display.tsx` — structural template for a new sibling `MeetingTranscription` component: `Card` + `Card.Header`/`Card.Content`, `Alert status="danger"` for errors, `Button isPending`/`Spinner` for the in-flight action, `ApiError`-typed catch with a 401 branch. Mount it from the page when `meetingFile !== null`, seeded from the metadata the page already fetched so there is no duplicate fetch on mount.
- **HeroUI `ChipRoot`/`ChipLabel`** for the status indicator — verified exported from `@heroui/react`'s root (`dist/components/index.d.ts` re-exports `./chip`) with `color` variants `default | accent | success | warning | danger`, which map one-to-one onto `PENDING | PROCESSING | COMPLETED | FAILED`. Note these are **flat** exports, not a `Chip.Root`/`Chip.Label` compound — the same shape `docs/research-plan-user-profile-and-edit-page.md.md` found for HeroUI's avatar module, unlike `Card`/`Alert`/`AlertDialog` which are dot-notation compounds.
- `apps/web/e2e/api-helpers.ts` + `meeting-file-management.spec.ts`'s direct multipart `POST` via `APIRequestContext` — the fastest way to seed a meeting that already has a real file for the Phase 4/5 Playwright specs, without driving the upload UI.

**No new shared constants table.** The PRD makes `.mp4`/`.mp3` the required minimum and the other five accepted types optional "if trivial". Under the ffmpeg-based decode step they _are_ trivial — `nodejs-whisper`'s own `ffmpeg` shell-out handles all seven. Transcribe whatever is stored, and add no third hand-mirrored extension table to the two (`file-upload.constants.ts` ↔ `file-types.ts`, `avatar-upload.constants.ts` ↔ `avatar-file-types.ts`) the repo already maintains by hand.

## Risks

- **Every dev and CI machine needs a C/C++ toolchain, CMake (3.31.6 confirmed sufficient — no v4 floor observed), and `ffmpeg` on `PATH` before this feature works at all.** This is the direct cost of the team's `nodejs-whisper` preference over the toolchain-free Transformers.js alternative: `npm install` alone is not enough (verified — it succeeds, but the CMake build and the `ffmpeg` shell-out both happen lazily on first real use), so a machine that skips the new prerequisites fails opaquely, deep inside the first transcription attempt, not at `npm install` time. Confirmed working end-to-end on Debian 13 once those three are installed (point 1) — this is no longer a theoretical requirement, it's a verified one. **Mitigation:** the `pretest:e2e`/setup-script checks described in point 3 (model present? `ffmpeg` on `PATH`? compiled `whisper-cli` binary present — not just "a download ran once", per the reproduced stale-build bug in point 1) turn a missing/half-finished prerequisite into an upfront, clearly-worded failure — the same job `scripts/check-postgres.sh` already does for the Postgres prerequisite.
- **Every existing e2e upload test becomes a transcription job.** `apps/api/test/meeting-file-upload.e2e-spec.ts` and `meeting-file-management.e2e-spec.ts` upload synthetic bytes — `Buffer.from('fake mp4 bytes')`, `Buffer.from('not a video')`, `Buffer.alloc(600 * 1024 * 1024)` — across a dozen-plus upload calls. Once upload triggers transcription, each of those fires a job `nodejs-whisper`'s `ffmpeg` step cannot decode (it will fail fast with a non-zero exit, landing in `FAILED` — not silently hang, since `ffmpeg` itself rejects non-media input quickly). Beyond the wasted CPU on every `git push`, the real hazard is jobs still writing to Prisma after `afterAll`'s `app.close()`, which under `--runInBand` surfaces as open-handle warnings or unhandled rejections in unrelated spec files. **Mitigation:** a `TRANSCRIPTION_ENABLED` flag read through a lazy getter (per `getUploadDir()`'s convention), defaulted off in `apps/api/.env.test` and set to `'true'` in-file by the new transcription spec before `AppModule` is imported — the lazy read is what makes per-file overriding work at all.
- **`apps/web/e2e/fixtures/test-recording.mp3` is not audio.** It is 2048 bytes that `file(1)` reports as `data`, and `apps/web/CLAUDE.md` documents this deliberately: "file _content_ doesn't need to be real audio/video since validation... only checks extension and declared MIME type, never content." That statement stops being true with this feature. Phases 4 and 5 cannot assert a `COMPLETED` status against this fixture, and a real short speech fixture is needed in both `apps/web/e2e/fixtures/` and (per Phase 2) `apps/api/test/fixtures/`. Sourcing one with a clean license is a real task, not a detail — see Open questions.
- **Jest's 5 s default per-test timeout.** Steady-state inference itself is fast and confirmed no threat to this — **~2.2–3.4 s per clip** measured on an 11 s sample across `.wav`/`.mp3`/`.mp4` on this 8-core CPU-only machine, comfortably inside a per-test timeout once the model/binary are already warm. The real threat is the _first_ transcription in a fresh environment, which additionally pays for the deferred CMake build (point 1) — **measured at 5+ minutes**, not the "tens of seconds" the earlier draft estimated by analogy to Transformers.js's model-load cost; a plain compiled-C++-build is a categorically different, much larger cost than loading pre-quantized ONNX weights. The new spec needs explicit per-test timeouts and a `beforeAll` warm-up (ideally satisfied entirely by the `npm run setup:whisper` step from point 3, so the suite's own first test isn't the one paying for it) so the first test isn't the slowest by minutes, not seconds. Every transcription test also runs serially (`--runInBand`), so its wall-clock cost is additive on the pre-push hook.
- **Cross-platform build risk is real, not hypothetical, given this repo's existing posture.** The root `package.json` already pulls in `cross-env` "for cross-platform support" and `apps/web/playwright.config.ts`/CLAUDE.md treat Windows as a supported dev platform. `nodejs-whisper`'s Windows path (MSYS2/MinGW-w64) is meaningfully more involved to set up correctly than its Linux/macOS path, and is the one platform this research could not verify directly (no Windows machine available in this session) — budget explicit onboarding time/documentation for it, and treat it as unverified until a teammate on Windows actually runs the setup script.
- **Whisper tiny on CPU is slow relative to real time.** The PRD accepts this ("transcription of longer recordings may take a nontrivial amount of wall-clock time"), but combined with the 500 MB `MAX_UPLOAD_FILE_SIZE_BYTES` default, a single upload can occupy the transcription queue for a very long time and, with the recommended concurrency cap of 1, block every other meeting's job behind it. There is no timeout or cancellation in the plan.
- **Frontend polling has no precedent in this codebase.** Nothing in `apps/web` currently polls. A `setInterval` that outlives its component, or one that keeps running in a backgrounded tab for an hour-long transcription, is the easy mistake. Use a recursive `setTimeout` inside the existing `cancelled`-flag `useEffect` idiom, stop on `COMPLETED`/`FAILED`, and add a max-attempts or `document.visibilityState` backstop.
- **Re-upload is not reachable through the UI today.** `MeetingFileUpload` renders only when `meetingFile === null`, so the PRD's "organizer replaces the meeting's file (re-upload)" scenario is currently API-only. Phase 1's invalidation is still correct and necessary, but the Phase 4/5 Playwright specs cannot exercise the replace path through the browser without a UI change that is out of this plan's scope.
- **Three CLAUDE.md files go stale on landing.** Per the root "Keeping documentation in sync" rule: the root file gains a new "Local Whisper transcription" prerequisites section (toolchain, CMake, `ffmpeg`, `npm run setup:whisper`) and a new external dependency; `apps/api/CLAUDE.md`'s Meetings section gains the transcription lifecycle and its Architecture section gains the runtime dependency; `apps/web/CLAUDE.md` gains a transcription UI section and — importantly — needs the "content doesn't need to be real audio/video" claim corrected.

## Open questions

- **`transcriptionJobId` — adopt or skip?** Recommended above (one nullable column, closes the refresh-during-`PROCESSING` overwrite race that a `filePath`-only guard misses). Skipping it leaves Phase 5's disabled button as the only protection, which a direct API call bypasses. Worth deciding before Phase 1, since it belongs in the same migration.
- **Where does the speech fixture come from, and under what license?** It needs to be committed to two directories, short enough that tiny-model inference stays fast under `--runInBand`, and clearly licensed for redistribution. `whisper.cpp`'s own `jfk.wav` (a US-government public-domain recording, vendored inside the verified `nodejs-whisper` install at `cpp/whisper.cpp/bindings/go/samples/jfk.wav`, and used directly for the end-to-end verification above — confirmed real and transcribable, not just present) is the most convenient choice but is ~11 s; trimming it to 2–3 s, or generating a clip with a local TTS, are the alternatives. Also unresolved: what "a fixture engineered to fail transcription" is in Phase 2 — the existing `Buffer.from('fake mp4 bytes')` uploads already produce exactly that (a fast `ffmpeg` decode failure, also confirmed: real `.mp3`/`.mp4` derived from `jfk.wav` via system `ffmpeg` transcoded and transcribed correctly, so the pipeline's happy path for these two formats is no longer a guess), so a forced-failure test hook may be unnecessary.
- **`ffmpeg-static` + `PATH`-prepend, or a documented system-`ffmpeg` prerequisite?** Recommended a plain system install in point 2, since `nodejs-whisper` has no API to point it at a specific binary and always shells out to whatever `ffmpeg` it finds on `PATH`. The counterargument for `ffmpeg-static` is DX consistency with the Playwright-browser-install precedent — but it adds npm weight and a GPL-3.0-or-later declaration for a dependency this project can otherwise treat as a normal system prerequisite, the same way Postgres already is.
- **Should the plan's `TranscribeMeetingFileCommand` survive?** Recommendation 4 folds the work into an `@EventsHandler` and drops the command. Keeping the command as a named unit, executed _by_ the event handler, is also defensible and stays closer to the plan as written — but it is two indirections for one job.
- **What should `transcriptionStatus` be for a meeting whose file predates the migration?** It will be `null`, which is neither the plan's four states nor "no file". Phase 4's UI needs a defined rendering (treat as "not transcribed", offer the refresh button) or Phase 1's migration needs a backfill setting existing file-bearing rows to `PENDING` — which would then transcribe every historical upload on next boot. The former is simpler and is what the recommendation assumes.
- **Is the CMake/toolchain requirement acceptable for every environment this ships to?** This is now the central trade-off of the team's `nodejs-whisper` choice (point 1) and needs an explicit yes from whoever owns deployment, not just developer machines — e.g. if the API is ever containerized, the build image needs `build-essential`/`cmake`/`ffmpeg` baked in (a straightforward `apt-get install` layer, but a real one), and if it's deployed to a minimal/serverless runtime without a writable filesystem or shell access, `nodejs-whisper`'s child-process-plus-CMake-build model may not fit at all. Nothing in the current plan or PRD specifies a deployment target, so this is worth surfacing rather than assuming.
- **Is a fallback to `@huggingface/transformers` (or a bare system `whisper-cli` subprocess) worth keeping in reserve?** If the toolchain/`ffmpeg` prerequisite proves too heavy in practice (a teammate's machine that can't easily get a working CMake, or a deployment target without a build step), a swap to either alternative behind the same call boundary (`nodewhisper()`'s call site in the `@EventsHandler`) is contained — the event handler, the compare-and-set write, and the whole frontend are engine-agnostic already. Worth keeping `src/meetings/transcription/` scoped narrowly around that one call for exactly this reason, even if the swap never happens.
