# Research: User profile page and profile editing

## Goal

Determine the implementation strategy for `docs/plan-user-profile-and-edit-page.md` / `docs/prd-user-profile-and-edit-page.md`: a `GET /users/me` profile read, username update, avatar upload/serving, and password change on the API, plus a `/profile` and `/profile/edit` page and app-wide avatar display on the web app — all built to match the existing CQRS/NestJS backend and the existing Next.js/HeroUI/axios frontend, with no new architectural patterns.

## Recommended solution

**Follow the plan's 8 phases as written — they already are the codebase's existing patterns, not a new architecture.** Concretely:

- **Backend**: give `UserModule` its own `UserController` (currently it has none — it's CQRS-only, reached via `CommandBus`/`QueryBus` from `AuthModule`, per `apps/api/CLAUDE.md`'s "User" section). Every new capability is one command or query + one handler, registered in `UserModule`'s `providers`, exactly like `AuthModule`'s and `MeetingsModule`'s existing handlers (`src/auth/commands/handlers/register.handler.ts`, `src/meetings/commands/handlers/upload-meeting-file.handler.ts`, etc.) — there is no service-layer alternative anywhere in this codebase, so introducing one for `UserModule` would be inconsistent.
- **Avatar storage**: copy `MeetingsModule`'s file-upload mechanics (`multer` + `diskStorage`, `OnModuleInit`/`mkdirSync`, `randomUUID()`-generated on-disk filenames, extension+MIME validation table, crash-safe replace ordering) into a new `src/user/upload/` directory with its own constants and its own `MAX_AVATAR_FILE_SIZE_BYTES`. Do not generalize/share code between meeting-file upload and avatar upload — the two apps/modules already tolerate near-duplicate constants (`apps/web`'s `file-types.ts` explicitly mirrors `apps/api`'s `file-upload.constants.ts` by hand, "the two apps don't share code, so keep both copies in sync"); the same hand-mirrored-duplication convention should extend to meetings-vs-avatar uploads within `apps/api` too, since unifying them would require a shared abstraction (different size limits, different accepted types, different disk subdirectory) that doesn't exist today and isn't justified by two call sites.
- **Circular `UserModule` <-> `AuthModule` import**: use `forwardRef()` on both sides exactly as the plan states — this is Nest's standard idiom for this exact situation and nothing in the codebase suggests restructuring where `JwtAuthGuard` lives (it's deliberately owned by `AuthModule` and exported for reuse, per `apps/api/CLAUDE.md`'s "Auth" section, and `MeetingsModule` already reuses it the same way by importing `AuthModule` — the only difference now is the import runs in both directions).
- **Frontend**: extend `apps/web/src/lib/api.ts` with new functions following the exact `toApiError`/`statusMessages` pattern already used for every existing call (`getProfile`, `updateUsername`, `uploadAvatar`, `changePassword`, an avatar-blob fetch helper). Build `/profile` and `/profile/edit` as new `'use client'` pages under `src/app/profile/` mirroring `page.tsx`'s and `meetings/[id]/page.tsx`'s existing loading/auth-redirect/error-`Alert` structure (`useAuth()`, `isLoading`/`!auth` redirect effect, `ApiError`-typed catch blocks, 401 → `logout()` + redirect). Build avatar upload UI mirroring `meeting-file-upload.tsx`'s validate-on-select + `ProgressBar` + per-error-case `Alert` structure.
- **Avatar rendering is a new shared component** (`Avatar`, e.g. `src/components/avatar.tsx`) since none exists today. HeroUI v3.2.2 (`@heroui/react`) does ship avatar primitives (`AvatarRoot`/`AvatarImage`/`AvatarFallback`, Radix-based) under `components/avatar`, but — unlike `Card`, `Alert`, `AlertDialog`, `ProgressBar`, which are all assembled into a single dot-notation compound export (`Card.Header`, `Alert.Indicator`, etc.) — the avatar module does **not** assemble a `Avatar.Root`/`Avatar.Image`/`Avatar.Fallback` compound; it only re-exports the three pieces as flat named exports. Build the shared `Avatar` component on top of `AvatarRoot`/`AvatarImage`/`AvatarFallback` (keeps visuals/accessibility consistent with the rest of the HeroUI-based UI) but wire its `src` to a locally-created `URL.createObjectURL` from the Bearer-authenticated blob fetch, not a raw URL — `AvatarImage`'s `src` prop accepts any string, including an object URL, so this composes cleanly. This is a genuinely new component, not a case of "an existing pattern already solves it" — but its composition still reuses only existing primitives and existing state-management patterns (the object-URL-from-blob approach is line-for-line the same technique `downloadMeetingFile` in `api.ts` already uses).

## Reusable code

**Backend:**

- `apps/api/src/auth/guards/jwt-auth.guard.ts` (`JwtAuthGuard`) — reuse directly via `@UseGuards(JwtAuthGuard)` on the new `UserController`, same as `MeetingsController`.
- `apps/api/src/auth/interfaces/authenticated-request.interface.ts` (`AuthenticatedRequest`, `{ userId, email }`) — reuse directly for reading `request.user.userId` in the new controller.
- `apps/api/src/user/interfaces/user-record.interface.ts` (`UserRecord`, `UserWithCredentials`) — extend or add a sibling interface for the richer profile shape (`{ id, email, username, avatarMimeType, avatarUploadedAt }`), following the same "narrow, purpose-specific interface" convention (`UserWithCredentials` exists solely because `LoginHandler` needs the password hash — mirror that for whatever internal-only shape password-change verification needs).
- `apps/api/src/meetings/upload/multer.config.ts`, `file-upload.constants.ts`, `validate-file-type.ts` — structural template (not shared code) for the new `src/user/upload/avatar-upload.constants.ts` + multer config + validator, per the PRD's own note that avatar validation "mirror[s] the existing meeting-file validation pattern."
- `apps/api/src/meetings/commands/handlers/upload-meeting-file.handler.ts` / `delete-meeting-file.handler.ts` — template for crash-safe write-then-update-then-delete-old-file ordering in `UploadAvatarHandler`. Note: the meeting handlers use `SELECT ... FOR UPDATE` inside a transaction specifically because a meeting can be concurrently re-uploaded to _by construction_ (any request scoped to the same `meetingId`); a user's own avatar upload is scoped to `request.user.userId` from a single authenticated session per request, so the plan's phase list doesn't call for the same row-locking — worth confirming during implementation whether concurrent tabs from the same logged-in user make that lock worth copying too, or whether the plan's simpler "update then delete" is intentionally sufficient here (see Open questions).
- `apps/api/src/user/commands/handlers/create-user.handler.ts` — `bcrypt.hash(password, 10)` convention (`SALT_ROUNDS = 10`) to reuse verbatim in the new password-change handler; `LoginHandler`'s `bcrypt.compare` for the current-password check.
- `apps/api/src/user/queries/handlers/find-user-by-email.handler.ts` — template for the new by-id credentials query the password-change flow needs (`UserWithCredentials`-shaped, internal-only, never exposed over HTTP — same rationale already documented for the email-based version).
- `apps/api/src/auth/dto/register.dto.ts` — `@MinLength(8)` password-validation convention to reuse in `ChangePasswordDto.newPassword`.
- `apps/api/prisma/schema.prisma`'s `Meeting` nullable-file-column pattern (`fileOriginalName`/`filePath`/`fileMimeType`/`fileSize`/`fileUploadedAt`, all nullable, always written/cleared together) — the exact template for `User`'s new `avatarPath`/`avatarMimeType`/`avatarUploadedAt` columns.
- `apps/api/test/auth.e2e-spec.ts` / `apps/api/test/meeting-file-upload.e2e-spec.ts` — structural template for `user-profile.e2e-spec.ts` (per-test unique emails via `Date.now()`, register-then-request-with-bearer-token helper, `getUploadDir()` for on-disk cleanup assertions).

**Frontend:**

- `apps/web/src/lib/api.ts`'s `toApiError`/`statusMessages`/`ApiError` machinery — reuse directly for every new function (`getProfile`, `updateUsername`, `uploadAvatar`, `changePassword`, an avatar-blob getter).
- `apps/web/src/lib/http.ts`'s shared `http` axios instance — already attaches the Bearer token via its request interceptor for every new call, no per-call auth wiring needed.
- `apps/web/src/lib/auth-context.tsx` (`useAuth()`) — reuse `auth`/`isLoading`/`logout` for the new pages' auth-gating, same as `page.tsx` and `meetings/[id]/page.tsx`. Per the plan's Phase 6 task, this context needs to grow to also carry the fetched profile (username/avatar) app-wide post-login, since the JWT payload alone (`{ userId, email }`, decoded by `auth-store.ts`'s `getUserId`) doesn't carry them.
- `apps/web/src/lib/file-types.ts`'s `validateFile`/`formatBytes`/extension-table structure — structural template for a new avatar-specific validation module (not the same file/constants, since accepted types and size limits differ — same "hand-mirror, don't share" convention as the backend).
- `apps/web/src/components/meeting-file-upload.tsx` — structural template for the avatar upload control (validate-on-select, `ProgressBar`, distinct `Alert`s for validation vs. server error, 401 → `onSessionExpired`).
- `apps/web/src/components/password-confirm-field.tsx` — reuse directly (or as a close template) for the password-change form's current/new-password fields; it already handles show/hide toggling and per-field validation via HeroUI's `TextField`/`FieldError`.
- `apps/web/src/app/login/page.tsx` / `apps/web/src/app/meetings/[id]/page.tsx` — structural template for `Form`/`TextField`/`toast` success-feedback conventions, and for the loading/redirect/error-`Alert` page shell.
- HeroUI's `AvatarRoot`/`AvatarImage`/`AvatarFallback` (`@heroui/react`, confirmed present in the installed `3.2.2`) — primitives to build the new shared `Avatar` component on top of, rather than hand-rolling `<img>`/initials markup from scratch.

## Risks

- **Keeping two upload-constants tables in sync, times two now.** The repo already carries the burden of hand-mirroring meeting-file constants between `apps/api` and `apps/web`; this feature adds a _second_ pair (avatar constants) with different values, doubling the surface where drift between client and server validation can silently occur. No code changes needed to mitigate — just discipline, as the existing CLAUDE.md already flags for the meeting-file case.
- **`forwardRef()` circular dependency is easy to get subtly wrong.** Missing `forwardRef()` on only one side of the `UserModule` <-> `AuthModule` import throws Nest's "cannot resolve dependency" error at bootstrap, not at compile time — the plan does call this out explicitly, but the two module files must be touched together and tested by actually booting the app (an e2e test failure here is opaque; a quick `npm run start:dev` sanity check catches it faster).
- **Avatar-as-blob adds a fetch-and-revoke lifecycle to every place an avatar renders** (profile page, edit page, main page — three independent mount points per Phase 6). Forgetting `URL.revokeObjectURL` on unmount/re-fetch leaks object URLs; the existing `downloadMeetingFile` precedent revokes immediately after a synchronous download click, but a _persistently displayed_ `<img>` needs the object URL to stay alive for as long as it's rendered and only revoke on unmount/replacement — a materially different lifecycle than the one precedent in this codebase, so it needs its own careful implementation rather than a copy-paste.
- **Multer's `limits.fileSize` static-at-import-time constraint** (already documented in `file-upload.constants.ts`'s comment) applies identically to the new `MAX_AVATAR_FILE_SIZE_BYTES` — it must be read at module-load time after `dotenv/config`, same as today; nothing new, just don't miss re-deriving this constraint for the new constants file.
- **Password change has no session invalidation** (explicitly out of scope per the PRD — "no auto-logout is required"). Existing JWTs (1-hour expiry, per `AuthModule`'s `JwtModule.registerAsync`) issued before a password change remain valid until they expire naturally. This is a PRD-accepted trade-off, not a gap to fix, but worth being aware it's a deliberate and not an accidental omission.
- **Row-locking asymmetry vs. meeting file replace** (see "Reusable code" above) — if two tabs from the same user race an avatar upload, the plan's simpler approach (no `SELECT ... FOR UPDATE`) could theoretically orphan a file the same way concurrent meeting uploads could before that lock was added. Low real-world likelihood for a single user's own concurrent uploads, but worth a deliberate call (see Open questions), not a silent gap.

## Open questions

- Should `UploadAvatarHandler` take the same `SELECT ... FOR UPDATE` transactional lock `UploadMeetingFileHandler`/`DeleteMeetingFileHandler` use, given the theoretical same-user concurrent-tab race described above — or is the plan's simpler unlocked update-then-delete acceptable here since the blast radius is a single user's own orphaned file, not cross-user data?
- Where should the new by-id user-credentials query for password verification live — a new `FindUserByIdQuery`/`FindUserByIdHandler` (id-scoped sibling to the existing email-scoped `FindUserByEmailQuery`), or should `FindUserByEmailQuery` gain an alternate id-based path? The plan (Phase 7) leaves this as "or extend the existing query/handler if it can be reused cleanly" — worth deciding before implementation rather than during it, since `UserModule`'s CLAUDE.md doc will need updating either way per the repo's "keep docs in sync" convention.
- Exact shape of the shared `Avatar` component's props/fallback-derivation (e.g. does it take the full profile object, or just `{ username, email, avatarMimeType }` plus an already-fetched blob URL?) isn't specified by the plan beyond "renders the fetched image blob if `avatarMimeType` is set... else the initials placeholder" — worth pinning down as part of implementing Phase 2 (which introduces the initials-only placeholder version) so Phase 6's swap-in doesn't require a prop-shape rewrite of every call site.
- Both app CLAUDE.md files (`apps/api/CLAUDE.md`'s "User" section, `apps/web/CLAUDE.md`) will need updates once this feature lands, per the root CLAUDE.md's "Keeping documentation in sync" rule — `UserModule` goes from "no HTTP surface" to having a controller, and `apps/web` gains a new shared `Avatar` component and a new "Profile" section analogous to the existing "Meeting file upload UI" section.
