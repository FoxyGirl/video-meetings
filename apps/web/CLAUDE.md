# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the `web` app in the `video-meetings` npm workspaces monorepo (see `../../CLAUDE.md` for the repo-wide picture). It's a Next.js App Router project scaffolded with `create-next-app` (TypeScript, Tailwind CSS v4, ESLint, `src/` directory, `@/*` import alias to `src/*`).

## Commands

Run from this directory, or from the repo root with `--workspace=web`:

```bash
npm run dev             # next dev (Turbopack), http://localhost:3000
npm run build           # next build (production build)
npm run start           # next start (serve the production build)
npm run lint            # eslint (flat config, no path args — lints the whole project)
npm run typecheck       # tsc --noEmit
```

```bash
npm run test:e2e        # playwright test — e2e/*.spec.ts against the real dev stack
```

There is no unit test script/framework configured for this app yet.

## E2E tests (Playwright)

`e2e/*.spec.ts` (config: `playwright.config.ts`, `baseURL` defaults to `http://localhost:3000`) exercise the app through a real browser against the real dev stack — no mocks. This suite is wired into the repo's **pre-push** git hook (`../../CLAUDE.md`'s "Git hooks" section) via the root `npm run test:e2e`, so it runs on every `git push`, not just on demand. `playwright.config.ts`'s `webServer` array auto-starts the `web` (`npm run dev`) and `api` (`npm run dev:api`, run from the repo root) dev servers if they aren't already up, and tears them down afterward — reusing them instead if you already have `npm run dev` running. The one thing that isn't auto-started is Postgres: the container (`docker compose up -d db`, see `../../CLAUDE.md`) must already be running, or both the api dev server's boot and the suite itself will fail/time out. Tests provision their own data over HTTP directly against the API (`API_URL`, defaults to `http://localhost:3001`) — e.g. `meeting-detail.spec.ts` registers/logs in the shared local test user (`qa-test@video-meetings.local`, see `../../CLAUDE.md`'s "Local test user" section) and creates a uniquely-titled meeting per run via `POST /meetings`, rather than depending on hand-seeded state, so the suite is safe to re-run. `npx playwright install chromium` is needed once after installing dependencies to fetch the browser binary (not committed, not an npm dependency).

- **Always fully serial (`workers: 1`), not just in CI**: `meeting-transcription.spec.ts` runs a real, CPU-bound local Whisper "tiny" inference (`nodejs-whisper`'s vendored `whisper.cpp` binary), which starves other concurrently-running specs' network/event-loop timing enough to blow unrelated tests' 30s assertion timeouts under Playwright's default parallel workers. A scoped alternative (tag that one spec, run everything else in parallel, then it alone afterward) was tried and reverted: on a memory-constrained dev machine, the "everything else, still parallel" pass turned out to be independently flaky from Chromium/memory pressure alone — unrelated to Whisper — so it didn't actually solve the reliability problem, just moved it. Blanket serial is the version that's reliably clean here; same tradeoff `apps/api`'s own e2e suite already makes (`--runInBand`) over Jest's default parallelism.
- **Cold-start flakiness**: when a `git push` finds no `npm run dev` already running, the `webServer` block above starts `next dev` fresh for that run alone. Next's dev server compiles each route on first request, not ahead of time — the first test to hit a given route (typically whichever spec touches `/meetings/[id]` earliest) can take several seconds longer than every later hit of that same route. `expect: { timeout: 10_000 }` (above the 5s default) and `retries: 1` locally (not just CI's 2) exist specifically to absorb that one-off first-hit compile — a genuinely broken test still fails identically on the retry. Reproduced by running `npm run test:e2e --workspace=web` with no dev servers already up and confirmed clean on repeat cold runs before landing this.

- `api-helpers.ts` centralizes the shared setup/teardown used across spec files: `registerUserViaApi`/`loginUserViaApi` (direct HTTP calls to the API, bypassing the UI for test data setup), plus `deleteUserByEmail` and `deleteMeetingById`, which delete rows directly from Postgres (via the `pg` devDependency, `DATABASE_URL` env var, default `postgresql://postgres:postgres@localhost:5432/video_meetings` — same default as `apps/api`'s `.env.example`). There's no delete-user API endpoint to call instead — this mirrors how `apps/api`'s own e2e suite cleans up the `User` table by talking to Postgres directly rather than through HTTP. This cleanup matters more now that the suite runs on every push, not just occasionally.
- `register.spec.ts` registers its own throwaway users (unique, timestamped emails) and deletes each one in a `test.afterEach` so repeated runs don't pile up rows in the dev `User` table.
- `meeting-detail.spec.ts` seeds the shared local test user plus a per-run meeting in `beforeAll`, deleting that meeting in `afterAll` — it can't rely on `Meeting`'s cascade-delete-with-organizer, since the shared test user itself is never deleted. It also registers a throwaway second "viewer" user (cleaned up the same way as `register.spec.ts`) to assert the organizer badge is hidden for non-organizers.
- `meeting-file-upload.spec.ts` creates a fresh meeting per test (via the shared test user, deleted in `afterEach`) rather than sharing one meeting across tests like `meeting-detail.spec.ts` does — uploading mutates the meeting's file state, so a shared meeting would let one test's upload leak into another's "no file yet" expectation regardless of worker count. Committed fixtures under `e2e/fixtures/` (`test-recording.mp3`, `invalid-file.txt`) drive the valid-upload and invalid-type cases — file _content_ doesn't need to be real audio/video since validation (both client- and server-side) only checks extension and declared MIME type, never content. (`meeting-transcription.spec.ts`'s own fixture, `short-speech.mp3`, is the one exception that does need real audio — see that file's "Meeting transcription status and transcript" section above.) Multi-file batches (multi-select, multi-file drag-and-drop, mixed valid/invalid, the 10-file cap) reuse `test-recording.mp3`'s bytes under several distinct in-memory filenames (Playwright's `FilePayload`/`buildDataTransfer`'s `name` override) rather than committing extra fixture files, and a `uploadFileViaApi` helper seeds files directly through the API when a test just needs the meeting to already be near the cap.
- `meeting-file-management.spec.ts` (metadata, download, delete) also creates a fresh meeting per test, but seeds the file(s) itself via a direct multipart `POST` through Playwright's `APIRequestContext` rather than driving the upload UI — the upload flow is already covered by `meeting-file-upload.spec.ts`, so these tests only need a meeting that already has one or more stored files. Download is asserted via Playwright's `page.waitForEvent('download')` and `suggestedFilename()`, confirming the auth-header blob round-trip actually saves the file under its original name, not just that the button click doesn't throw. Each per-file entry on the page is wrapped in a `data-testid="meeting-file-<id>"` div specifically so a test can scope a click (e.g. Delete) to one file among several by filename, without relying on DOM order.

## Architecture

- App Router lives under `src/app`. `layout.tsx` is the root layout, `page.tsx` the home route, `globals.css` the Tailwind entry point.
- `tsconfig.json` extends the repo's `../../tsconfig.base.json` and adds Next-specific compiler options (`bundler` module resolution, `jsx: react-jsx`, the `next` TS plugin, and the `.next/types` includes) — don't remove the `extends` when regenerating this file.
- `eslint.config.mjs` composes `eslint-config-next/core-web-vitals` + `eslint-config-next/typescript`, then `eslint-config-prettier` to disable any rules that conflict with the repo's shared Prettier config (`../../.prettierrc`). There is no local `.prettierrc` — formatting is controlled entirely from the repo root.
- Styling is Tailwind CSS v4 via `@tailwindcss/postcss` (see `postcss.config.mjs`); there's no `tailwind.config.*` file since v4 configures via CSS (`globals.css`) rather than a JS config.

## HTTP client (`src/lib/http.ts`, `src/lib/api.ts`)

All API calls go through `axios` (not `fetch`) via a single shared instance, `http` in `src/lib/http.ts`: `axios.create({ baseURL: API_URL })` plus a request interceptor that reads `getAuthSnapshot()` (`auth-store.ts`'s synchronous, non-React accessor) and attaches `Authorization: Bearer <token>` when a session exists. Call sites in `api.ts` (and anything built on it) never thread `accessToken` through function parameters or `useAuth()` — the interceptor attaches it uniformly.

- `api.ts` wraps every call in `try`/`catch` and funnels errors through a shared `toApiError(error, statusMessages?)` helper, since Axios rejects on any non-2xx response (unlike `fetch`, which only sets `res.ok`). `statusMessages` lets a call override the server's raw message with a friendlier one for specific statuses (e.g. 409 on register, 401 on login); when no override matches, the server's own `message` field is surfaced (e.g. the upload endpoint's specific per-case validation messages), falling back to a generic string only for truly unexpected shapes.
- `getProfile()` hits `GET /users/me` and returns the current user's profile (`id`, `email`, `username`, `avatarMimeType`, `avatarUploadedAt`) — a plain GET with no special-cased behavior beyond the standard 401 override.
- `updateUsername(username)` hits `PATCH /users/me/username` with `{ username }` and returns the refreshed `UserProfile`, mirroring the API's `UpdateUsernameDto` shape (`string | null`) — pass `null` to clear the username, same normalization the server already applies. No special-cased status messages beyond the standard 401 override; validation errors (e.g. over the 50-char limit) surface via the server's own DTO message.
- `uploadAvatar(file, onProgress?)` posts to `POST /users/me/avatar` as a `FormData` (field name `file`, matching the API's `FileInterceptor('file', ...)`) and returns the refreshed `UserProfile` — same `onUploadProgress`-driven progress callback and 413 override as `uploadMeetingFiles` below. The 413 message is deliberately _not_ size-specific (unlike the 400/401 overrides) — citing the client's mirrored max would be actively wrong in the one case this path is reachable at all: client-side validation already blocks anything over that mirrored number, so a request only reaches the server's real (env-configurable) limit when that limit is lower than the client's guess, and the client's number is then guaranteed to overstate it.
- `changePassword({ currentPassword, newPassword })` hits `PATCH /users/me/password` and returns a fresh `AuthResult` (a new JWT, since `ChangePasswordHandler` reissues one — see `apps/api/CLAUDE.md`'s "User" section). Unlike every other call here, it does **not** blanket-override 401 to "session expired": on this one endpoint a 401 can come from either `JwtAuthGuard` (missing/expired token) or `ChangePasswordHandler` itself (wrong current password, a credential check rather than an auth failure), and the server's own message already distinguishes the two, so it's left to pass through instead of being collapsed into the wrong meaning for one of the two cases.
- `getAvatarBlob()` fetches `GET /users/me/avatar` with `responseType: 'blob'` — same Bearer-authenticated-blob reasoning as `downloadMeetingFile` below, but the caller keeps the resulting object URL alive for as long as it's rendered (persistent `<img>`) rather than revoking it immediately after a one-off download click. Resolves `null` on a 404 ("no avatar yet") rather than throwing, so callers can fall back to the initials placeholder instead of treating it as an error.
- `listMeetingFiles(id)` hits `GET /meetings/:id/files` and returns every file's metadata (`MeetingFileMetadata[]`, ordered by upload time) — open to any authenticated user, same access rule the file lifecycle has always used; an empty array (not a 404) means the meeting has no files yet. The meeting detail page renders one entry per item in this list (see "Meeting file metadata..." below), and `MeetingTranscription`'s own polling effect also calls it directly to re-read its one `fileId`'s status, rather than assuming `files[0]` — see that component's section below for why that distinction matters once a meeting can hold more than one file.
- `uploadMeetingFiles(id, files, onProgress?)` posts a `FormData` with one `files` field per file (matching the API's `FilesInterceptor('files', MAX_FILES_PER_MEETING, ...)`) to `POST /meetings/:id/files`, and threads an optional `onProgress` callback through Axios's `onUploadProgress` — real byte-level progress since Axios's browser build uses `XMLHttpRequest` under the hood, not a hand-rolled estimate. Never set `Content-Type` manually on this call — the browser needs to set its own multipart boundary. The response is the full `{ accepted, rejected }` batch result (one outcome per file sent, not a single object) — returned as-is rather than unwrapped to one file or thrown on any rejection, since a batch is always a 2xx even when every file was rejected (e.g. the 10-file cap); it's `MeetingFileUpload` (below) that renders per-file outcomes.
- `downloadMeetingFile(meetingId, fileId, fileName)` fetches `GET /meetings/:meetingId/files/:fileId/download` with `responseType: 'blob'`, then triggers a client-side save via a short-lived `URL.createObjectURL` + a synthetic `<a download>` click. This is necessary (not just a stylistic choice) because the download endpoint requires the Bearer auth header, and browsers never attach custom headers to a plain `<a href>` navigation — the blob round-trip is the only way to authenticate the request while still handing the browser a normal "Save As" flow.
- `deleteMeetingFile(meetingId, fileId)` calls `DELETE /meetings/:meetingId/files/:fileId`; the caller (`MeetingFileDisplay`) is responsible for updating page state on success, this function only performs the request.

## Auth session and profile (`src/lib/auth-store.ts`, `src/lib/auth-context.tsx`, `src/lib/use-profile.ts`)

`auth-store.ts` holds the raw session (`{ accessToken, email }`, localStorage-backed) and is what `http.ts`'s request interceptor reads synchronously — see "HTTP client" above. `auth-context.tsx`'s `AuthProvider` (mounted app-wide in `app/providers.tsx`) wraps it for React consumers via `useAuth()`, exposing `auth`, `userId` (decoded from the JWT), `isLoading`, `login`/`logout`, plus the fetched `profile`/`profileError`.

- **Profile fetch**: as soon as a session exists (right after `login()`, or immediately on a fresh page load when a session is restored from localStorage), `AuthProvider` fetches `getProfile()` itself and stores the result, so `username`/`avatarMimeType`/`avatarUploadedAt` are available app-wide via `useAuth().profile` without every page re-fetching its own copy — this is what lets the main page (see below) show the real username/avatar without its own fetch. A 401 during that fetch calls `logout()`; there's no redirect here, a page's own auth-gating effect (watching `auth` go to `null`) is what actually navigates to `/login`. The fetched profile is tagged with the session token it was fetched (or `setProfile`-updated) for and only returned while that tag still matches the current session — same "only valid while the key still matches" technique `avatar.tsx`'s `useAvatarImageUrl` uses for its object URL — rather than clearing it with a synchronous `setState` on logout.
- `use-profile.ts`'s `useProfile()` is a thin wrapper for `/profile`/`/profile/edit`: it re-exposes `auth-context`'s `profile`/`setProfile`/`profileError` and adds only the redirect-to-`/login`-when-signed-out effect + a combined `isLoading`. Call sites (e.g. `AvatarUpload`'s `onUploaded`, `updateUsername`'s success handler) call the returned `setProfile(updated)` to push a mutation's result straight into `auth-context`, so it's reflected everywhere `useAuth().profile` is read, not just the page that made the change.

## Meeting file upload UI (`src/components/meeting-file-upload.tsx`, `src/lib/file-types.ts`)

On `/meetings/[id]`, once the meeting loads, the page fetches the meeting's files via `listMeetingFiles` (`lib/api.ts`, above) and renders `MeetingFileUpload` whenever the viewer is the organizer **and** `files.length < MAX_FILES_PER_MEETING` — it stays mounted alongside the file list (below) as files accumulate, only disappearing once the meeting is genuinely at the 10-file cap, not the instant a first file exists. A successful (or partially successful) upload calls the `onUploaded` prop back up to the page with the batch's `accepted` files, which the page appends to its local `files` state — the page doesn't otherwise re-fetch. Non-organizers get no upload UI at all.

- `file-types.ts` holds `ACCEPTED_FILE_TYPES` (extension → MIME), `MAX_UPLOAD_FILE_SIZE_BYTES`, and `MAX_FILES_PER_MEETING`, hand-mirrored from `apps/api/src/meetings/upload/file-upload.constants.ts` — the two apps don't share code, so keep all three identical if any changes. `validateFile(file)` checks extension, MIME (only if the browser reported one — it can be empty for some formats), and size, purely as a UX fast-fail; the server remains the authority. `formatBytes` is used only for large, MB-scale thresholds (the max-size and "too large" messages) — see `formatFileSize` below for displaying an arbitrary stored file's actual size.
- **Multi-file selection and staging**: the `<input type="file" multiple>` and the drop zone both feed into `applySelectedFiles(File[])`, which runs `validateFile` per file and stores the result as `stagedFiles: { file, error }[]` — each file gets its own inline error text immediately (before any Upload click), rather than one validation error for the whole selection. The Upload button is enabled as soon as at least one staged file passed validation; clicking it sends only the files with no client-side error (via `uploadMeetingFiles`), while the client-rejected ones are merged into the same result view described below without a wasted round trip. A `ProgressBar` (real, `onUploadProgress`-driven) shows during the request.
- **Per-file batch result**: once an upload attempt resolves (whether or not the server was actually called — an all-client-rejected selection short-circuits it), `batchResult` holds the combined `{ accepted, rejected }` and is rendered as one list item per file — `"<name> uploaded successfully"` for each accepted file, `"<name>: <reason>"` for each rejected one (client- or server-caught, same shape either way) — instead of one collapsed message for the whole batch. A single combined toast (`toast.success` if nothing was rejected, `toast.danger` otherwise) restates the same summary, because accepting even one file in a batch can push the meeting to the 10-file cap and un-render this whole card on the very next parent render (see above) — the toast, rendered outside the card, is what a user actually sees for the outcome in that case, so the inline list and the toast intentionally carry the same information.
- Any request-level failure (network, 401, 404, 413 — as opposed to a per-file rejection reported inside a 2xx batch response) surfaces its own generic `uploadError` `Alert`; a 401 calls back up to the page's `onSessionExpired` (same logout-and-redirect the page's own meeting/file fetches use) rather than rendering inline.
- **Drag-and-drop**: the control doubles as a drop zone — a `dragenter`/`dragover`/`dragleave`/`drop`-handling wrapper `div` (all four call `preventDefault()`, since without it the browser treats a drop as a navigation attempt) around the same click-to-browse `<input>`, so both interaction paths stay available side by side. `dragenter`/`dragleave` use a `useRef` counter rather than a plain boolean, since those events fire for every child element the pointer crosses (the input, the hint text) — a counter avoids the active-state highlight flickering off while dragging over a child. A dropped `DataTransfer`'s files (any count, including many at once) are read on `drop` and routed through the same `applySelectedFiles` the click-to-browse `onChange` uses — no separate validation/upload path. Only a drop with **zero** files (e.g. non-file drag data such as dragged text) surfaces a distinct `dropError` `Alert` ("No files detected in the drop...") instead.

## Meeting file metadata, download, and delete UI (`src/components/meeting-file-display.tsx`)

On `/meetings/[id]`, the page renders one `MeetingFileDisplay` (paired with its own `MeetingTranscription`, below) per entry in `files`, each wrapped in a `data-testid="meeting-file-<id>"` div — for **any** authenticated viewer (organizer or not), since the metadata (name, size, upload date) and the download action are not organizer-gated, only delete is. `MeetingFileDisplay` itself is unchanged by multi-file support (it always rendered exactly one file's card); it's the page that now maps it over a list instead of rendering it once, binding each instance's `onDeleted` to that file's own id via a closure (`onDeleted={() => handleFileDeleted(file.id)}`) so the page can remove just that one file from local state. When the list is empty **and** the viewer isn't the organizer, the page renders a plain "No recording yet." card instead of leaving the area blank; an organizer with zero files just sees the upload control from above with nothing beneath it.

- **Size formatting**: `formatFileSize` (`file-types.ts`) is a separate function from the upload flow's `formatBytes` — `formatBytes` rounds to whole MB, which is fine for large fixed thresholds but would misleadingly show "0 MB" for a small stored file (e.g. the Playwright fixture is 2 KB). `formatFileSize` adapts its unit (B/KB/MB/GB) to the actual byte count instead.
- **Download**: wired to `downloadMeetingFile` (`api.ts`, see "HTTP client" above) — the blob + object-URL pattern is required specifically because the download endpoint needs the Bearer auth header, which a plain `<a href>` navigation can't carry.
- **Delete is organizer-only** (`isOrganizer` prop, same value the page already computes for the "You are the organizer" badge) and goes through a HeroUI `AlertDialog` confirmation (`<Trash2>` trigger button → "Delete this recording?" dialog) before calling `deleteMeetingFile`. The dialog is controlled (`isOpen`/`onOpenChange` state), not the library's default `slot="close"` auto-close pattern, specifically so the confirm button can stay open and show an inline error if the delete request fails, and only close + call the page's `onDeleted` on actual success. The page's `handleFileDeleted` filters that one file out of local `files` state, un-rendering just that file's `MeetingFileDisplay`/`MeetingTranscription` pair while the rest of the list (and the upload control, if still below the cap) stays exactly as it was — no manual re-fetch.
- A 401 from either the download or delete request calls back up to the page's `onSessionExpired`, same convention as the upload component.

## Meeting transcription status and transcript (`src/components/meeting-transcription.tsx`)

On `/meetings/[id]`, one `MeetingTranscription` instance is mounted per file, paired with that file's own `MeetingFileDisplay` (a sibling, not a change to that file), seeded from that file's `transcriptionStatus`/`transcriptionText`/`id` (threaded through as the `fileId` prop) — the metadata the page already fetched via `listMeetingFiles`, so there's no duplicate fetch on mount. It renders for **any** authenticated viewer, same as `MeetingFileDisplay`, not just the organizer. A `null` status (transcription disabled server-side, or a file row that predates the transcription migration) means "no transcription run has ever started for this file" — **not** "no file exists" (the parent page never mounts this component in that case) — so a non-organizer still sees nothing (`status === null && !isOrganizer` renders `null`), but the organizer still gets a card with just the title, a "No transcription yet." line, and the Refresh button, since that button is the only UI path to trigger a first run without re-uploading the file (e.g. after `TRANSCRIPTION_ENABLED` gets turned on for a file uploaded while it was off).

- **Status chip**: a HeroUI `Chip` maps `PENDING`/`PROCESSING`/`COMPLETED`/`FAILED` to `default`/`warning`/`success`/`danger` colors, always paired with the status's text label (`Chip.Label`) rather than color alone. Passing a plain string as `Chip`'s children does **not** render — HeroUI's `Chip` only auto-wraps string children into a label in some builds; use the explicit `<Chip.Label>` compound-component form to avoid a silently empty chip.
- **`status`/`text` props seed initial state only.** Once mounted, the component owns them via its own `useState`, updated only by its polling effect below — a parent re-render passing the same seed props back in (e.g. the page re-rendering for an unrelated reason) never resets in-flight progress, since the props aren't read again after the initial `useState` call.
- **Polling**: while local `status` is `PENDING` or `PROCESSING`, a `setInterval` (3s) calls `listMeetingFiles(meetingId)` and finds **this instance's own `fileId`** in the result (rather than assuming `files[0]`, which `getMeetingFile` used to do before it was removed) — necessary now that a meeting can hold up to 10 files: assuming the first file would silently track (and display) some other file's status for any meeting with more than one. Local state updates from whatever that lookup returns, stopping itself once status settles to `COMPLETED`/`FAILED` — so a finished transcription never keeps polling in the background, and the organizer (or any viewer) sees progress with no manual page reload. Not finding this `fileId` in the list at all (deleted mid-poll by the organizer, from another tab/session) just stops polling; the page's own delete flow already handles un-rendering this component in the normal case. A 401 calls back up to the page's `onSessionExpired`, same convention as `MeetingFileDisplay`; any other polling failure is left to retry on the next tick rather than surfacing an inline error.
- **Completed**: renders `transcriptionText` as plain, whitespace-preserving text (`whitespace-pre-wrap`) below the status chip, wrapped in a HeroUI `Disclosure` behind a "Show transcript"/"Hide transcript" toggle — only the text block collapses, the status chip, in-progress spinner, Refresh button, and Failed alert stay visible regardless. Driven by a local `isExpanded` state (`useState(false)`, so collapsed by default whenever a transcript exists), scoped to this one component instance — since a meeting mounts one `MeetingTranscription` per file, expanding one file's transcript never affects another file's, with no extra wiring needed beyond the state being local rather than lifted to the page.
- **Failed**: an additional danger `Alert` supplements the red chip, so a failure isn't conveyed by color alone.
- **E2E fixture**: `e2e/fixtures/short-speech.mp3` is real (public-domain, trimmed) speech, copied from `apps/api/test/fixtures/short-speech.mp3` — unlike `test-recording.mp3` (synthetic bytes, fine for the upload/metadata specs that never look past the extension/MIME), a `COMPLETED` status needs the local Whisper "tiny" engine to actually decode and transcribe something real. `meeting-transcription.spec.ts` uploads it through the real UI and polls (no reload) until `Completed` — see the root `CLAUDE.md`'s "Local Whisper transcription" section for the toolchain this needs, and `docs/research-transcribe-uploaded-meeting-files-with-local-whisper.md` for the first-run cold-start cost (model download + CMake build) this spec's generous timeout absorbs. Its last test uploads the same fixture under two different in-memory filenames (one multi-file batch) to get two files each transcribing for real, and budgets `TRANSCRIPTION_TIMEOUT_MS * 2` since local Whisper only runs one job at a time — asserting the collapse-by-default and per-file-independent toggle behavior above needs two genuinely `COMPLETED` transcripts, not seeded/mocked ones.
- **"Refresh Transcription" button** (organizer-only, via a new `isOrganizer` prop): rendered in `Card.Header`, next to the "Transcript" title, whenever `isOrganizer` is true (including when `status` is `null`, unlike the status chip below it) — a non-organizer never sees it, same gating `MeetingFileDisplay`'s delete button uses. Uses the page's other action buttons' default size (not `size="sm"`) for touch-target/visual consistency with `MeetingFileDisplay`'s Download/Delete row; the header wraps to a column below `sm` so the button never has to squeeze onto the title's row on narrow viewports. `refreshTranscription(meetingId, fileId)` (`lib/api.ts`, `fileId` this instance's own prop) hits `POST /meetings/:meetingId/files/:fileId/transcription/refresh` and returns `{ transcriptionStatus, transcriptionText }` picked out of the response — the file's own metadata now (a file-scoped route, not a whole `Meeting` row); on success the handler sets local `status`/`text` **from that response**, not a hardcoded `PENDING`, so it can never show progress for a run that was never actually dispatched. This matters because `RefreshTranscriptionHandler`'s compare-and-set can legitimately no-op server-side (e.g. a concurrent delete already removed the file this refresh was scoped to, in which case the endpoint 404s instead) — the frontend has to actually use the response's real value rather than assume success, or it would get stuck showing "Transcribing…" forever once polling sees the file gone and stops without ever correcting the status. Reflecting it immediately (rather than waiting for the next poll tick) also re-arms the polling effect above whenever the result actually is `PENDING`/`PROCESSING` (the effect depends on `status`), and resets `consecutivePollFailures` so a fresh run doesn't inherit a stale warning from a previous, already-settled one. Disabled (`isDisabled`) while `status` is already `PENDING`/`PROCESSING`, to prevent redundant concurrent refresh clicks. A failure of the refresh request itself (network/401/etc.) surfaces its own danger `Alert` (`refreshError` state, separate from the polling-failure warning and the `FAILED`-status alert) and leaves `status`/`text` untouched, since nothing on the server actually changed; a 401 instead calls back up to the page's `onSessionExpired`, same convention as everywhere else in this component. `meeting-transcription.spec.ts`'s second test drives this end to end: upload → wait for `Completed` → click Refresh → assert `Pending` (deterministic, same reasoning as the first test's own "Pending" assertion) and the button disabled → wait for `Completed` again → a second, non-organizer viewer never sees the button at all.

## Meeting summary, action items, and decisions (`src/components/meeting-summary.tsx`)

On `/meetings/[id]`, one `MeetingSummary` instance is mounted per meeting (not per file, unlike `MeetingFileDisplay`/`MeetingTranscription`), seeded from `meeting.summaryStatus`/`summaryText`/`summaryIsPartial`/`actionItems`/`decisions` and the page's own `files` — the data the page already fetched via `getMeeting`/`listMeetingFiles`, so there's no duplicate fetch on mount. It renders for any authenticated viewer; only the Refresh Summary button is organizer-only.

- **The page gates the mount on `files.length > 0`** (`{files.length > 0 ? <MeetingSummary ... /> : null}` in `page.tsx`), not an internal early return — `MeetingSummary` only ever seeds its `files` state once (`useState(initialFiles)`, see below) and is never given a `key`, so if it mounted while the meeting still had zero files, uploading the meeting's first file would update the page's own `files` state but never reach this already-mounted instance: its seeded-empty `files` state has no re-sync path, `computeFilesReadiness` would stay `'no-files'` forever, and `shouldPoll` requires `readiness !== 'no-files'` to ever start polling — a permanent deadlock only a full page reload could break. Gating the mount in the page means the component only ever exists once there's a real file to seed it from, the same reason `MeetingFileDisplay`/`MeetingTranscription` don't hit this (they're keyed per file and remount on a genuinely new one). Covered by `e2e/meeting-summary.spec.ts`'s "the summary card appears after uploading the meeting's first file, with no reload" test — drives a real upload through the UI with no `page.reload()` anywhere in the test.

- **`summaryStatus`/`text`/etc. props seed initial state only**, same convention `MeetingTranscription`'s `status`/`text` follow — once mounted, the component owns them via its own `useState`s, updated only by its polling effect below.
- **A `null` `summaryStatus`** means generation has never been triggered for this meeting yet (see `apps/api/CLAUDE.md`'s "Meeting summary, action items, and decisions" section for the trigger condition) — the component explains why using each file's own `transcriptionStatus` (`computeFilesReadiness`): "still being transcribed" while any file is non-terminal, "every recording failed transcription" once all files are terminal with none `COMPLETED`, or a generic "not yet available" for the (normally near-instantaneous) race window where every file is terminal-with-a-completion but the trigger hasn't stamped `PENDING` yet.
- **Status chip**: same HeroUI `Chip`/`Chip.Label` convention `MeetingTranscription` uses, shown for every non-null status including `COMPLETED` — a completed summary with no visible status chip was an actual bug caught by this component's own Playwright suite (see below).
- **Polling**: while the summary/file-set combination hasn't yet reached a stable end state (`shouldPoll` — not `no-files`/`all-failed` file readiness, and summary status not `COMPLETED`/`FAILED`), a `setInterval` (3s, same cadence `MeetingTranscription` uses) calls `getMeeting(meetingId)` **and** `listMeetingFiles(meetingId)` together and updates all local state from both — the files re-fetch is what lets this component pick up the automatic `null` → `PENDING` transition once a meeting's last file finishes transcribing (each file's own `MeetingTranscription` instance polls independently and never surfaces that up to the page), without a reload. `listMeetingFiles`'s own in-flight-request coalescing (`lib/api.ts`) means this rarely costs an extra request beyond whatever `MeetingTranscription` instances are already polling for on the same tick.
- **Completed**: renders the Summary (plain `whitespace-pre-wrap` text), Action Items (a `<ul>`, each item's `assignee` appended as `" — <assignee>"` when present), and Decisions (a `<ul>`) sections; an empty action-item or decision list renders an explicit "No action items found."/"No decisions found." message rather than an empty list or nothing. `summaryIsPartial` renders a warning `Alert` above these sections.
- **Refresh Summary button**: organizer-only, disabled while `status` is already `PENDING`/`PROCESSING`, mirroring `MeetingTranscription`'s own Refresh Transcription button. `refreshMeetingSummary(meetingId)` (`lib/api.ts`) hits `POST /meetings/:id/summary/refresh` and returns a **full fresh `Meeting`** (not just two fields, unlike `refreshTranscription`) — local state is set from that response and it's also passed up to the page's own `onRefreshed` (`setMeeting`) so the page's `meeting` object stays in sync too. Trusts the response's real resulting status rather than assuming `PENDING`, same reasoning `refreshTranscription` documents: `RefreshMeetingSummaryHandler` always discards the existing summary, but a fresh run only actually starts if the meeting's files are currently all-terminal-with-at-least-one-completed.
- **E2E tests** (`e2e/meeting-summary.spec.ts`) seed a meeting's summary/action-item/decision rows and a `MeetingFile`'s `transcriptionStatus` directly via Postgres (`seedMeetingSummary`/`seedMeetingFile`, `e2e/api-helpers.ts`) rather than drive a real Whisper transcription run or a real Gemini API call — summary generation is gated purely on `GEMINI_API_KEY` (see `apps/api/CLAUDE.md`), intentionally unset in this dev environment, so a real "Refresh Summary" click here only ever discards the existing summary; it can't be relied on to complete a new one. The refresh test asserts only that discard, not a regenerated result.

## Avatar display (`src/components/avatar.tsx`)

Two components split presentation from data-fetching, specifically so nothing can accidentally render one user's fetched avatar image under another user's name:

- `UserAvatar` is a purely presentational component built on HeroUI's `Avatar`/`Avatar.Fallback` primitives (`@heroui/react`). Its props: `{ username?: string | null; email: string; imageUrl?: string | null; size?; className? }` — it never fetches anything itself, callers pass an already-resolved `imageUrl` (or omit it for the initials placeholder). Callers never compute initials themselves either, `UserAvatar` derives them internally from `username` (if set) else `email`.
- `CurrentUserAvatar` (`{ size?; className? }`) is the one component allowed to fetch an avatar image, since `getAvatarBlob()` (see "HTTP client" above) is hardcoded to the logged-in user (`GET /users/me/avatar` has no `:id` variant). It reads `auth`/`profile`/`profileError` from `useAuth()` itself rather than taking them as props, fetches the image via the same `useAvatarImageUrl` hook (below), and renders a `UserAvatar` with the resolved `imageUrl`. Every current call site (profile page, edit page, main page's logged-in-user greeting) renders the current user, so they all use `CurrentUserAvatar`, not `UserAvatar` directly — a future avatar for someone _other_ than the viewer (e.g. a meeting participant) should use `UserAvatar` directly with its own `imageUrl`, not reach for `CurrentUserAvatar`. While `profile` hasn't resolved yet (`auth` exists but neither `profile` nor `profileError` has settled — the main page's own case, since it doesn't gate rendering on the profile fetch the way `useProfile()`'s `isLoading` does for `/profile`/`/profile/edit`), it renders a bare empty `HeroAvatar` rather than `auth.email`-derived initials, to avoid a two-step paint where those initials flash and then get replaced by different (username-derived) ones once the profile arrives.
- **Image vs. initials**: when `avatarMimeType` is set on the profile, `CurrentUserAvatar` fetches the avatar via `getAvatarBlob()` and passes the result down as `imageUrl`, which `UserAvatar` renders as a `HeroAvatar.Image` in place of the initials fallback; when unset (or the fetch fails), `imageUrl` stays `null` and the initials placeholder shows. The fetch/object-URL lifecycle lives in `avatar.tsx`'s internal `useAvatarImageUrl` hook, keyed on `` `${avatarMimeType}:${avatarUploadedAt}` `` rather than `avatarMimeType` alone — re-uploading a same-type image changes the underlying bytes without changing the mime type, so `avatarUploadedAt` is what actually signals "fetch again." The hook only returns a fetched URL while its key still matches current props (rather than resetting to `null` synchronously inside the effect), and revokes the previous object URL on unmount or when a newer avatar replaces it. A 401 from this fetch calls `logout()`, same as a 401 on the profile fetch (`auth-context.tsx`) — any other failure just degrades to the initials placeholder.
- **Skipping the re-fetch after an upload**: `avatar-upload.tsx` calls `cacheAvatarPreview(profile, file)` right after a successful upload, seeding a module-level cache (keyed the same way as `useAvatarImageUrl`) with an object URL for the file already in the browser's hand. When `useAvatarImageUrl`'s key then changes to match (because the upload's `onUploaded` pushed the new `avatarUploadedAt` into `profile`), it reuses that cached URL instead of issuing a fresh `getAvatarBlob()` round trip to re-fetch bytes the browser just finished sending — this also means navigating to `/profile` or the main page right after an upload shows the same cached image with no extra fetch there either. Purely an optimistic shortcut: if the key doesn't end up matching for any reason, the normal fetch still runs as the fallback.
- **Initials rule**: a set `username` is split on whitespace — two-plus words use the first letter of the first two words (e.g. "Jane Doe" → "JD"); a single word uses its first two characters (e.g. "elena" → "EL"). No `username` falls back to the local part of `email` (before `@`), same two-character rule. Always uppercased.

## Avatar upload UI (`src/components/avatar-upload.tsx`, `src/lib/avatar-file-types.ts`)

On `/profile/edit`, `AvatarUpload` renders unconditionally (unlike `MeetingFileUpload`, it isn't gated on "no avatar yet" — re-uploading replaces the existing one). A successful upload calls `cacheAvatarPreview(profile, file)` (see "Avatar display" above) before calling the `onUploaded` prop back up to the page (`setProfile`), so the `CurrentUserAvatar` rendered elsewhere on the same page picks up the new image without an extra fetch; the component resets its own file input afterward so the same file can be re-selected for a follow-up upload.

- `avatar-file-types.ts` holds `ACCEPTED_AVATAR_TYPES` (extension → MIME) and `MAX_AVATAR_FILE_SIZE_BYTES`, hand-mirrored from `apps/api/src/user/upload/avatar-upload.constants.ts`. `validateAvatarFile(file)` delegates to `file-types.ts`'s `validateFileAgainstTypes(file, acceptedTypes, maxSizeBytes)` — the same extension/MIME/size checks `validateFile` (meeting uploads) runs, generalized to take a table and size limit so both call sites share one implementation instead of two copies.
- Validation re-runs on every file selection, disabling the Upload button until a file is selected and valid. Distinct `Alert`s separate a client-side validation error from a server-side upload failure (400s, or a generic — not size-specific, see `api.ts`'s "HTTP client" note above — message for 413) so the two never overwrite each other. A 401 calls back up to the page's `onSessionExpired`, same convention as the meeting file upload flow. No drag-and-drop here (unlike `MeetingFileUpload`) — click-to-browse only.

## Password change form (`src/app/profile/edit/page.tsx`, `src/components/password-visibility-toggle.tsx`)

On `/profile/edit`, a third card (below the avatar and username ones) holds a current-password/new-password form, independently submittable from the other two — its own `Form`, its own pending/error state, no shared submit path.

- **A wrong current password is a 403, not a 401.** `ChangePasswordHandler` deliberately doesn't collapse "wrong current password" and "session no longer valid" onto the same status (see `apps/api/CLAUDE.md`'s "User" section) — a credential-check mismatch is `403`, while `401` means only what it means on every other authenticated call in `apps/web`: `JwtAuthGuard` rejecting a missing/expired token. That lets `changePassword()` (`lib/api.ts`) use the same blanket `401 -> "session expired"` override every other call site here uses, and lets the page (`page.tsx`) branch on `error.status === WRONG_CURRENT_PASSWORD_STATUS` (403) rather than string-matching the response body — a wrong current password attaches a field error to Current password (`passwordFieldErrors`), distinct from the form's shared `passwordError` `Alert` used for unexpected failures, and kept visually separate from a "new password too short" field error (already field-scoped via `validate`) and from `SAME_AS_CURRENT_PASSWORD_MESSAGE`'s own field error on New password (hand-mirrored `ChangePasswordHandler`'s "New password must differ from current password" 400, still message-matched since that failure mode isn't ambiguous with anything else on this status code).
- **Token reissue and success feedback**: `changePassword()` resolves an `AuthResult` with a fresh JWT (`ChangePasswordHandler` reissues one so the old password's token isn't silently left stale) — a successful submit calls `login({ accessToken, email: profile.email })` to adopt it (the same `auth-context` entry point `login`/`register` use), then clears both password fields and shows a `toast.success('Password updated')` — no auto-logout, per the PRD, since the reissued token already keeps the session valid.
- **Visibility toggle reuse**: `PasswordVisibilityToggle` (`src/components/password-visibility-toggle.tsx`) was extracted out of `password-confirm-field.tsx` (used by `/login` and `/register`) into its own file so this form's two plain `TextField`s could get the same show/hide eye icon without duplicating it or forcing this form's non-paired current/new fields through `PasswordConfirmField`'s confirm-field-oriented API.
