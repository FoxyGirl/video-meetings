# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the `web` app in the `video-meetings` npm workspaces monorepo (see `../../CLAUDE.md` for the repo-wide picture). It's a Next.js App Router project (TypeScript, Tailwind CSS v4) whose `src/` tree follows Feature-Sliced Design (FSD) — see "Architecture" below for the layer layout and where the App Router itself actually lives (not `src/app`).

## Commands

Run from this directory, or from the repo root with `--workspace=web`:

```bash
npm run dev             # next dev (Turbopack), http://localhost:3000
npm run build           # next build (production build)
npm run start           # next start (serve the production build)
npm run lint            # eslint, then steiger (fsd:lint), then fsd:orphans — see "Architecture"
npm run typecheck       # tsc --noEmit
npm run fsd:lint        # steiger ./src alone, without eslint or fsd:orphans
npm run fsd:orphans     # scripts/find-orphaned-slices.mjs alone
```

```bash
npm run test:e2e        # playwright test — e2e/*.spec.ts against the real dev stack
```

There is no unit test script/framework configured for this app yet.

## E2E tests (Playwright)

`e2e/*.spec.ts` (config: `playwright.config.ts`, `baseURL` defaults to `http://localhost:3000`) exercise the app through a real browser against the real dev stack — no mocks. This suite is wired into the repo's **pre-push** git hook (`../../CLAUDE.md`'s "Git hooks" section) via the root `npm run test:e2e`, so it runs on every `git push`, not just on demand. `playwright.config.ts`'s `webServer` array auto-starts the `web` (`npm run dev`) and `api` (`npm run dev:api`, run from the repo root) dev servers if they aren't already up, and tears them down afterward — reusing them instead if you already have `npm run dev` running. The one thing that isn't auto-started is Postgres: the container (`docker compose up -d db`, see `../../CLAUDE.md`) must already be running, or both the api dev server's boot and the suite itself will fail/time out. Tests provision their own data over HTTP directly against the API (`API_URL`, defaults to `http://localhost:3001`) — e.g. `meeting-detail.spec.ts` registers/logs in the shared local test user (`qa-test@video-meetings.local`, see `../../CLAUDE.md`'s "Local test user" section) and creates a uniquely-titled meeting per run via `POST /meetings`, rather than depending on hand-seeded state, so the suite is safe to re-run. `npx playwright install chromium` is needed once after installing dependencies to fetch the browser binary (not committed, not an npm dependency).

- **Always fully serial (`workers: 1`), not just in CI**: `meeting-transcription.spec.ts` runs a real, CPU-bound local Whisper "tiny" inference (`nodejs-whisper`'s vendored `whisper.cpp` binary), which starves other concurrently-running specs' network/event-loop timing enough to blow unrelated tests' 30s assertion timeouts under Playwright's default parallel workers. A scoped alternative (tag that one spec, run everything else in parallel, then it alone afterward) was tried and reverted: on a memory-constrained dev machine, the "everything else, still parallel" pass turned out to be independently flaky from Chromium/memory pressure alone — unrelated to Whisper — so it didn't actually solve the reliability problem, just moved it. Blanket serial is the version that's reliably clean here; same tradeoff `apps/api`'s own e2e suite already makes (`--runInBand`) over Jest's default parallelism.
- **Cold-start flakiness**: when a `git push` finds no `npm run dev` already running, the `webServer` block above starts `next dev` fresh for that run alone. Next's dev server compiles each route on first request, not ahead of time — the first test to hit a given route (typically whichever spec touches `/meetings/[id]` earliest) can take several seconds longer than every later hit of that same route. `expect: { timeout: 10_000 }` (above the 5s default) and `retries: 1` locally (not just CI's 2) exist specifically to absorb that one-off first-hit compile — a genuinely broken test still fails identically on the retry. Reproduced by running `npm run test:e2e --workspace=web` with no dev servers already up and confirmed clean on repeat cold runs before landing this.

- `api-helpers.ts` centralizes the shared setup/teardown used across spec files: `registerUserViaApi`/`loginUserViaApi` (direct HTTP calls to the API, bypassing the UI for test data setup), plus `deleteUserByEmail` and `deleteMeetingById`, which delete rows directly from Postgres (via the `pg` devDependency, `DATABASE_URL` env var, default `postgresql://postgres:postgres@localhost:5432/video_meetings` — same default as `apps/api`'s `.env.example`). There's no delete-user API endpoint to call instead — this mirrors how `apps/api`'s own e2e suite cleans up the `User` table by talking to Postgres directly rather than through HTTP. This cleanup matters more now that the suite runs on every push, not just occasionally.
- `register.spec.ts` registers its own throwaway users (unique, timestamped emails) and deletes each one in a `test.afterEach` so repeated runs don't pile up rows in the dev `User` table.
- `meeting-detail.spec.ts` seeds the shared local test user plus a per-run meeting in `beforeAll`, deleting that meeting in `afterAll` — it can't rely on `Meeting`'s cascade-delete-with-organizer, since the shared test user itself is never deleted. It also registers a throwaway second "viewer" user (cleaned up the same way as `register.spec.ts`) to assert the organizer badge is hidden for non-organizers.
- `meeting-file-upload.spec.ts` creates a fresh meeting per test (via the shared test user, deleted in `afterEach`) rather than sharing one meeting across tests like `meeting-detail.spec.ts` does — uploading mutates the meeting's file state, so a shared meeting would let one test's upload leak into another's "no file yet" expectation regardless of worker count. Committed fixtures under `e2e/fixtures/` (`test-recording.mp3`, `invalid-file.txt`) drive the valid-upload and invalid-type cases — file _content_ doesn't need to be real audio/video since validation (both client- and server-side) only checks extension and declared MIME type, never content. (`meeting-transcription.spec.ts`'s own fixture, `short-speech.mp3`, is the one exception that does need real audio — see that file's "Meeting transcription status and transcript" section below.) Multi-file batches (multi-select, multi-file drag-and-drop, mixed valid/invalid, the 10-file cap) reuse `test-recording.mp3`'s bytes under several distinct in-memory filenames (Playwright's `FilePayload`/`buildDataTransfer`'s `name` override) rather than committing extra fixture files, and a `uploadFileViaApi` helper seeds files directly through the API when a test just needs the meeting to already be near the cap.
- `meeting-file-management.spec.ts` (metadata, download, delete) also creates a fresh meeting per test, but seeds the file(s) itself via a direct multipart `POST` through Playwright's `APIRequestContext` rather than driving the upload UI — the upload flow is already covered by `meeting-file-upload.spec.ts`, so these tests only need a meeting that already has one or more stored files. Download is asserted via Playwright's `page.waitForEvent('download')` and `suggestedFilename()`, confirming the auth-header blob round-trip actually saves the file under its original name, not just that the button click doesn't throw. Each per-file entry on the page is wrapped in a `data-testid="meeting-file-<id>"` div specifically so a test can scope a click (e.g. Delete) to one file among several by filename, without relying on DOM order.

## Architecture

`src/` follows Feature-Sliced Design (FSD): layers, low to high, are `shared`, `entities`, `features`, `widgets`, `_pages`, `_app`. A layer may only import from itself (same slice) or a strictly lower layer; a slice may never import a sibling slice on the same layer (e.g. one `features/*` slice importing another) — composing two same-layer slices together is lifted to the next layer up instead. `_app`/`_pages` are FSD's `app`/`pages` layers, underscore-prefixed specifically to dodge Next.js's reserved `app`/`pages` folder names; `@feature-sliced/filesystem` (which both `eslint-plugin-boundaries` and Steiger build on) recognizes the underscore-prefixed spelling as those layers natively, no extra config needed for that part.

- **Next's own App Router lives at the project root, `apps/web/app/`** — not `src/app`, which would collide with FSD's `_app` layer's own meaning. Every route file there is a one-line re-export delegating to the matching `_pages` slice's default export (e.g. `app/page.tsx` is `export { default } from '@/_pages/home';`, `app/meetings/[id]/page.tsx` is `export { default } from '@/_pages/meeting-detail';`) — all real page logic lives in the `_pages` slice, never in `app/`. `app/layout.tsx` is the one file under `app/` that isn't a thin re-export: the root layout, importing `src/_app/providers.tsx` (global context providers — see "Session and user entities" below) and `src/_app/globals.css` (the Tailwind entry point, relocated here from the old `src/app/globals.css`), plus `shared/ui`'s `ThemeToggle`.
- `@/*` still resolves to `src/*` (`tsconfig.json`'s `paths`), unaffected by the router living outside `src/`.
- `tsconfig.json` extends the repo's `../../tsconfig.base.json` and adds Next-specific compiler options (`bundler` module resolution, `jsx: react-jsx`, the `next` TS plugin, and the `.next/types` includes) — don't remove the `extends` when regenerating this file.
- **Enforcement**: `eslint.config.mjs` composes `eslint-config-next/core-web-vitals` + `eslint-config-next/typescript` + `eslint-plugin-boundaries` (layer-order and sibling-slice import rules, scoped to all of `src/**/*.{ts,tsx}`) + `eslint-config-prettier` (disables any rule that conflicts with the repo's shared Prettier config, `../../.prettierrc` — there is no local `.prettierrc`). `steiger.config.ts` runs `@feature-sliced/steiger-plugin`'s structural checks (slice/segment naming, insignificant slices, etc.) via `npx steiger ./src`; `npm run lint` runs eslint, then this (`npm run fsd:lint`), then `scripts/find-orphaned-slices.mjs` (`npm run fsd:orphans`) in sequence, so all three are part of the repo's pre-push hook (`../../CLAUDE.md`'s "Git hooks"). Both config files carry inline comments explaining every rule that's disabled or scoped away from its default, and why.
- **`fsd:orphans`** (`scripts/find-orphaned-slices.mjs`) exists specifically to cover a gap `steiger.config.ts` leaves open: `fsd/insignificant-slice` is disabled project-wide there because it also flags the app's many legitimate single-consumer features/widgets, but that same rule is what would otherwise catch a slice with _zero_ references (dead code). The script re-implements just that one case — for every slice under `_pages`/`widgets`/`features`/`entities`, it greps all of `src/**` and `app/**` (excluding the slice's own files) for an import of `@/<layer>/<slice>` and fails, listing each unreferenced slice, if any comes up with no match. It's a plain string search, not a resolved module graph — reliable here only because every cross-slice import in this codebase goes through the `@/*` alias (see "Rules enforced" — nothing does a relative reach into another slice's directory).
- Styling is Tailwind CSS v4 via `@tailwindcss/postcss` (see `postcss.config.mjs`); there's no `tailwind.config.*` file since v4 configures via CSS (`src/_app/globals.css`) rather than a JS config.

### Why `entities/meeting` and `entities/meeting-file` don't import each other

Neither entity has a field shaped like the other (`Meeting` has no `MeetingFileMetadata`-typed field and vice versa), so there's no actual type-level dependency to resolve with an FSD v2.1 `@x` cross-import — `entities/meeting/index.ts` and `entities/meeting-file/index.ts` each carry a comment recording this as a deliberate decision (Phase 4-fsd-v2), not an oversight. The two data sets genuinely _are_ used together (`widgets/meeting-summary` needs a meeting's summary fields plus its files' transcription statuses to decide what to render; `widgets/meeting-files` and `_pages/meeting-detail` need both to pair each file's card with its transcription card) — that composition is lifted to the widgets/pages layer, which is allowed to import both sibling entities since it sits strictly above them.

## Shared layer (`src/shared/`)

- **`shared/api`** (`http.ts`, `errors.ts`, re-exported via `index.ts`): `http` is the single shared axios instance (`axios.create({ baseURL: API_URL })`) every API call in the app goes through — never raw `fetch`. Its request interceptor attaches `Authorization: Bearer <token>` when a session exists, but `shared` can't import `entities/session` directly (that would be an upward import) — instead it exposes `setAuthTokenProvider(provider)`, a slot for whoever wants to supply the token getter. `entities/session/index.ts` calls `setAuthTokenProvider(() => getAuthSnapshot()?.accessToken ?? null)` as a side effect of being imported, which every consumer of the session entity does, so the slot is always filled before any component can render and issue a request. `errors.ts` holds `ApiError` and the shared `toApiError(error, statusMessages?)` helper every entity/feature API function wraps its axios call in — Axios rejects on any non-2xx response (unlike `fetch`, which only sets `res.ok`), and `statusMessages` lets a call override the server's raw message with a friendlier one for specific statuses (e.g. 409 on register, 401 on login); when no override matches, the server's own `message` field is surfaced, falling back to a generic string only for truly unexpected shapes.
- **`shared/lib`** (`file-validation.ts`, `email.ts`): `getExtension`, `formatBytes` (rounds to whole MB — fine for large fixed thresholds, but misleading for a small stored file, see `entities/meeting-file`'s own `formatFileSize` below), and `validateFileAgainstTypes(file, acceptedTypes, maxSizeBytes)` — a UX-level fast-fail (extension, declared MIME, size) shared by `entities/meeting-file`'s `validateFile` and `entities/user/lib/avatar-file-types.ts`'s `validateAvatarFile`, generalized to take a table and size limit so both call sites share one implementation instead of two copies. A client can lie about a file's extension or MIME type, so this never replaces the server-side check — it just avoids a pointless round trip for the common case of an obviously wrong file. `email.ts`'s `EMAIL_PATTERN` is shared across `/login`, `/register`, and `/meetings/new`.
- **`shared/ui`** (`password-visibility-toggle.tsx`, `password-confirm-field.tsx`, re-exported via `index.ts`): `PasswordVisibilityToggle` is the eye-icon show/hide button, used directly by `features/change-password/ui/change-password-form.tsx`'s two independent password fields and indirectly (via `PasswordConfirmField`) by `features/auth-login`/`features/auth-register`. It was extracted into `shared/ui` specifically so the change-password form's non-paired current/new fields could reuse it without going through `PasswordConfirmField`'s confirm-field-oriented API, which `/login` (`withConfirmField={false}`) and `/register` (`withConfirmField={true}`, the default) still use for their own password field(s).

## Session and user entities (`src/entities/session/`, `src/entities/user/`, `src/_app/providers.tsx`)

Session (raw auth token + decoded id) and user profile (username, avatar, fetched via HTTP) are two separate entity slices — the split matters because they sit on the same layer and FSD forbids one entity slice from importing a sibling slice directly, so their composition has to happen one layer up, in `src/_app/providers.tsx`.

- **`entities/session`** (`model.ts`, `ui/session-provider.tsx`): `model.ts` holds the raw session (`{ accessToken, email }`, localStorage-backed under the key `video-meetings:auth`) as a module-level cache with a `useSyncExternalStore`-compatible subscribe/snapshot pair (`getAuthSnapshot`/`subscribeAuth`/`setAuthState`), plus `getUserId(accessToken)` (decodes the JWT's `sub` claim client-side, tolerating a malformed token by returning `null` rather than throwing). `ui/session-provider.tsx`'s `SessionProvider`/`useSession()` wraps that store for React consumers, exposing `auth`, `userId`, `isLoading` (a mount-flag `useSyncExternalStore`, true only until the client has hydrated), and `login`/`logout`. This is the session-only half of what used to be one combined auth context — it deliberately knows nothing about the fetched profile.
- **`entities/user`** (`api.ts`, `lib/use-profile.ts`, `ui/user-provider.tsx`, `ui/avatar.tsx`): `ui/user-provider.tsx`'s `UserProvider`/`useUser()` is the profile-fetch-orchestration half — it takes session data (`hasSession`, `userId`, `email`, `isLoading`, `logout`) as **props**, not by importing `entities/session` itself (see the sibling-slice rule above), and fetches `getProfile()` (`api.ts`) as soon as a session exists, caching the result app-wide so no page needs its own copy. A 401 during that fetch calls the passed-in `logout()`; there's no redirect here, a page's own auth-gating effect (or `useProfile()`, below) is what navigates to `/login`. Both `profile` and any fetch error are tagged with the `userId` they were fetched for and only returned while that tag still matches the current `userId` prop, rather than cleared with a synchronous reset on logout — same technique `ui/avatar.tsx`'s `useAvatarImageUrl` uses for its own object URL.
- **`src/_app/providers.tsx`** is the one place that actually composes the two: its `Providers` component wraps `ThemeProvider` (next-themes) around `entities/session`'s `SessionProvider`, and a small local `UserSessionBridge` reads `entities/session`'s `useSession()` and feeds `hasSession`/`userId`/`email`/`isLoading`/`logout` into `entities/user`'s `UserProvider` as props — exactly the composition FSD calls for instead of a direct cross-entity import.
- `entities/user/lib/use-profile.ts`'s `useProfile()` is a thin wrapper for `_pages/profile` and `_pages/profile-edit`: it re-exposes `useUser()`'s `profile`/`setProfile`/`profileError` and adds the redirect-to-`/login`-when-signed-out effect plus a combined `isLoading`. Call sites that mutate the profile (`upload-avatar`'s `onUploaded`, `update-username`'s success handler, `change-password`'s reissued session) call the returned `setProfile(updated)` to push the result straight into `entities/user`'s context, so it's reflected everywhere `useUser().profile`/`useProfile().profile` is read, not just the page that made the change.
- **`entities/user/ui/avatar.tsx`** splits presentation from data-fetching, specifically so nothing can accidentally render one user's fetched avatar image under another user's name:
  - `UserAvatar` is purely presentational (HeroUI's `Avatar`/`Avatar.Fallback`), taking an already-resolved `imageUrl` (or none, for the initials placeholder) — it never fetches anything, and derives initials internally from `username` (if set) else the local part of `email`, two-plus words using each word's first letter, a single word using its first two characters, always uppercased.
  - `CurrentUserAvatar` is the one component allowed to fetch an avatar image, since `getAvatarBlob()` (`api.ts`) is hardcoded to the logged-in user (`GET /users/me/avatar` has no `:id` variant). It reads `hasSession`/`email`/`profile`/`profileError`/`logout` from `useUser()` itself rather than taking them as props, fetches the image via the internal `useAvatarImageUrl` hook, and renders `UserAvatar` with the resolved URL. Every current call site (`_pages/profile`, `_pages/profile-edit`, `_pages/home`'s greeting) renders the current user, so they all use `CurrentUserAvatar`; a future avatar for someone _other_ than the viewer (e.g. a meeting participant) should use `UserAvatar` directly instead. While the profile fetch hasn't settled yet, it renders a bare empty `HeroAvatar` rather than email-derived initials, to avoid a flash of wrong initials before the real (username-derived) ones paint.
  - `useAvatarImageUrl`, keyed on `` `${avatarMimeType}:${avatarUploadedAt}` `` (not `avatarMimeType` alone, since re-uploading a same-type image changes the bytes without changing the mime type), fetches via `getAvatarBlob()` and exposes an object URL kept alive for as long as it's rendered, revoked on unmount or when a newer avatar replaces it. A 401 calls `logout()`; any other failure just degrades to the initials placeholder.
  - `cacheAvatarPreview(profile, file)`, called by `features/upload-avatar` right after a successful upload, seeds a module-level cache (keyed the same way) with an object URL for the file already in the browser's hand, so `useAvatarImageUrl` can skip a redundant `getAvatarBlob()` round trip for bytes the browser just finished sending — a pure optimistic shortcut; the normal fetch is still the fallback if the key ever doesn't match.

## Meeting and meeting-file entities (`src/entities/meeting/`, `src/entities/meeting-file/`)

- **`entities/meeting`** (`api.ts`): the `Meeting` shape (including `summaryStatus`/`summaryText`/`summaryIsPartial`/`actionItems`/`decisions` — `null` `summaryStatus` means "not yet applicable", see `widgets/meeting-summary` below) plus `createMeeting`, `getMeetings`, `getMeeting`.
- **`entities/meeting-file`** (`api.ts`, `ui/meeting-file-card.tsx`): `MeetingFileMetadata` (`transcriptionStatus`/`transcriptionText` independently nullable from the rest — a file can exist with no transcription state yet), the file-type/size constants (`ACCEPTED_FILE_TYPES`, `MAX_UPLOAD_FILE_SIZE_BYTES`, `MAX_FILES_PER_MEETING` — all hand-mirrored from `apps/api/src/meetings/upload/file-upload.constants.ts`, keep in sync since the two apps don't share code), `validateFile` (delegates to `shared/lib`'s `validateFileAgainstTypes`), `formatFileSize` (adapts B/KB/MB/GB to the actual byte count — unlike `shared/lib`'s `formatBytes`, which would misleadingly show "0 MB" for a small stored file), and the reads: `listMeetingFiles` (coalesces concurrent same-meeting calls into one shared in-flight request/response, since a meeting with several files transcribing at once mounts one poller per file, all on the same 3s cadence), `downloadMeetingFile` (Bearer-authenticated `GET` as a blob + a short-lived `URL.createObjectURL` + synthetic `<a download>` click — required because the download endpoint needs the auth header, which a plain `<a href>` navigation can't carry), `deleteMeetingFile`. `ui/meeting-file-card.tsx`'s `MeetingFileCard` renders only a file's own metadata (name, size, upload date) plus an `actions` slot for whatever buttons the caller composes in — download/delete are their own features (below), so the entity never has to import from a higher layer to render them.

## Auth and meeting-creation features (`src/features/auth-login/`, `src/features/auth-register/`, `src/features/create-meeting/`)

- **`auth-login`** (`api.ts`, `ui/login-form.tsx`): `loginUser` posts to `/auth/login`; `LoginForm` validates email against `shared/lib`'s `EMAIL_PATTERN` and password non-emptiness via `shared/ui`'s `PasswordConfirmField` (`withConfirmField={false}`), then calls `entities/session`'s `login()` and redirects to `/`.
- **`auth-register`** (`api.ts`, `ui/register-form.tsx`): same shape, `registerUser` posts to `/auth/register` (409 override for an existing email), `RegisterForm` uses `PasswordConfirmField`'s default confirm-field mode plus a minimum-length validator.
- **`create-meeting`** (`ui/create-meeting-form.tsx`, no `api.ts` of its own — calls `entities/meeting`'s `createMeeting` directly): the date field is a plain `<input type="datetime-local">` (HeroUI's React-Aria-backed `TextField`/`Input` doesn't support that type), so it's validated by hand rather than through `Form`'s automatic per-field validation the way Title and Participants are; `datetime-local`'s local-time string is converted via `new Date(date).toISOString()` to the UTC ISO 8601 string `CreateMeetingDto` expects.

## Meeting file upload feature (`src/features/upload-meeting-files/`)

`ui/meeting-file-upload.tsx`'s `MeetingFileUpload` is rendered by `_pages/meeting-detail` whenever the viewer is the organizer **and** `files.length < MAX_FILES_PER_MEETING` — it stays mounted alongside `widgets/meeting-files`' list as files accumulate, only disappearing once the meeting is genuinely at the 10-file cap. A successful (or partially successful) upload calls the `onUploaded` prop back up to the page with the batch's `accepted` files, which the page appends to its local `files` state — the page doesn't otherwise re-fetch. Non-organizers get no upload UI at all.

- **Multi-file selection and staging**: the `<input type="file" multiple>` and the drop zone both feed into `applySelectedFiles(File[])`, which runs `entities/meeting-file`'s `validateFile` per file and stores the result as `stagedFiles: { file, error }[]` — each file gets its own inline error text immediately (before any Upload click), rather than one validation error for the whole selection. The Upload button is enabled as soon as at least one staged file passed validation; clicking it sends only the files with no client-side error (via `api.ts`'s `uploadMeetingFiles`), while the client-rejected ones are merged into the same result view described below without a wasted round trip. A `ProgressBar` (real, `onUploadProgress`-driven) shows during the request.
- **Per-file batch result**: once an upload attempt resolves (whether or not the server was actually called — an all-client-rejected selection short-circuits it), `batchResult` holds the combined `{ accepted, rejected }` and is rendered as one list item per file — `"<name> uploaded successfully"` for each accepted file, `"<name>: <reason>"` for each rejected one (client- or server-caught, same shape either way) — instead of one collapsed message for the whole batch. A single combined toast (`toast.success` if nothing was rejected, `toast.danger` otherwise) restates the same summary, because accepting even one file in a batch can push the meeting to the 10-file cap and un-render this whole card on the very next parent render — the toast, rendered outside the card, is what a user actually sees for the outcome in that case, so the inline list and the toast intentionally carry the same information.
- Any request-level failure (network, 401, 404, 413 — as opposed to a per-file rejection reported inside a 2xx batch response) surfaces its own generic `uploadError` `Alert`; a 401 calls back up to the page's `onSessionExpired` (same logout-and-redirect the page's own meeting/file fetches use) rather than rendering inline.
- **Drag-and-drop**: the control doubles as a drop zone — a `dragenter`/`dragover`/`dragleave`/`drop`-handling wrapper `div` (all four call `preventDefault()`, since without it the browser treats a drop as a navigation attempt) around the same click-to-browse `<input>`, so both interaction paths stay available side by side. `dragenter`/`dragleave` use a `useRef` counter rather than a plain boolean, since those events fire for every child element the pointer crosses (the input, the hint text) — a counter avoids the active-state highlight flickering off while dragging over a child. A dropped `DataTransfer`'s files (any count, including many at once) are read on `drop` and routed through the same `applySelectedFiles` the click-to-browse `onChange` uses — no separate validation/upload path. Only a drop with **zero** files (e.g. non-file drag data such as dragged text) surfaces a distinct `dropError` `Alert` ("No files detected in the drop...") instead.

## Meeting file list widget (`src/widgets/meeting-files/`)

`ui/meeting-file-list.tsx`'s `MeetingFileList`, rendered by `_pages/meeting-detail` for **any** authenticated viewer (organizer or not — metadata and download aren't organizer-gated, only delete is), maps `files` to one `<div data-testid="meeting-file-<id>">` per file, each pairing `entities/meeting-file`'s `MeetingFileCard` (metadata, with `features/download-meeting-file`'s `DownloadMeetingFileButton` and, organizer-only, `features/delete-meeting-file`'s `DeleteMeetingFileButton` passed in as its `actions`) with this widget's own `ui/meeting-transcription-card.tsx`. The page owns fetching/uploading the `files` list itself and only hands this widget what to render; it binds each `DeleteMeetingFileButton`'s `onDeleted` to that file's own id via a closure so the page can remove just that one file from local state. When the list is empty **and** the viewer isn't the organizer, `_pages/meeting-detail` renders a plain "No recording yet." card itself instead of leaving the area blank — an organizer with zero files just sees `features/upload-meeting-files`' control with nothing beneath it.

- `features/download-meeting-file/ui/download-meeting-file-button.tsx`'s `DownloadMeetingFileButton` wires to `entities/meeting-file`'s `downloadMeetingFile`; `features/delete-meeting-file/ui/delete-meeting-file-button.tsx`'s `DeleteMeetingFileButton` goes through a HeroUI `AlertDialog` confirmation ("Delete this recording?") before calling `deleteMeetingFile` — the dialog is controlled (`isOpen`/`onOpenChange` state), not the library's default `slot="close"` auto-close pattern, specifically so the confirm button can stay open and show an inline error if the delete request fails, and only close + call the widget's `onDeleted` on actual success.
- A 401 from either button's request calls back up to the page's `onSessionExpired`, same convention as the upload feature.

## Meeting transcription status and transcript (`src/widgets/meeting-files/ui/meeting-transcription-card.tsx`, `src/features/refresh-transcription/`)

One `MeetingTranscriptionCard` instance is mounted per file inside `widgets/meeting-files/ui/meeting-file-list.tsx`, paired with that file's own `MeetingFileCard` (a sibling, not a change to that file), seeded from that file's `transcriptionStatus`/`transcriptionText`/`id` (the metadata `_pages/meeting-detail` already fetched via `listMeetingFiles`, so there's no duplicate fetch on mount). It renders for **any** authenticated viewer, same as `MeetingFileCard`, not just the organizer. A `null` status (transcription disabled server-side, or a file row that predates the transcription migration) means "no transcription run has ever started for this file" — **not** "no file exists" (the parent list never mounts this component in that case) — so a non-organizer still sees nothing (`status === null && !isOrganizer` renders `null`), but the organizer still gets a card with just the title, a "No transcription yet." line, and the Refresh button, since that button is the only UI path to trigger a first run without re-uploading the file (e.g. after `TRANSCRIPTION_ENABLED` gets turned on for a file uploaded while it was off).

- **Status chip**: a HeroUI `Chip` maps `PENDING`/`PROCESSING`/`COMPLETED`/`FAILED` to `default`/`warning`/`success`/`danger` colors, always paired with the status's text label (`Chip.Label`) rather than color alone. Passing a plain string as `Chip`'s children does **not** render — HeroUI's `Chip` only auto-wraps string children into a label in some builds; use the explicit `<Chip.Label>` compound-component form to avoid a silently empty chip.
- **`status`/`text` props seed initial state only.** Once mounted, the component owns them via its own `useState`, updated only by its polling effect below — a parent re-render passing the same seed props back in (e.g. the list re-rendering for an unrelated reason) never resets in-flight progress, since the props aren't read again after the initial `useState` call.
- **Polling**: while local `status` is `PENDING` or `PROCESSING`, a `setInterval` (3s) calls `entities/meeting-file`'s `listMeetingFiles(meetingId)` and finds **this instance's own `fileId`** in the result (rather than assuming `files[0]`) — necessary since a meeting can hold up to 10 files: assuming the first file would silently track (and display) some other file's status for any meeting with more than one. Local state updates from whatever that lookup returns, stopping itself once status settles to `COMPLETED`/`FAILED` — so a finished transcription never keeps polling in the background, and the organizer (or any viewer) sees progress with no manual page reload. Not finding this `fileId` in the list at all (deleted mid-poll by the organizer, from another tab/session) just stops polling; the page's own delete flow already handles un-rendering this component in the normal case. A 401 calls back up to `onSessionExpired`, same convention as `MeetingFileCard`'s action buttons; any other polling failure is left to retry on the next tick rather than surfacing an inline error.
- **Completed**: renders `text` as plain, whitespace-preserving text (`whitespace-pre-wrap`) below the status chip, wrapped in a HeroUI `Disclosure` behind a "Show transcript"/"Hide transcript" toggle — only the text block collapses, the status chip, in-progress spinner, Refresh button, and Failed alert stay visible regardless. Driven by a local `isExpanded` state (`useState(false)`, so collapsed by default whenever a transcript exists), scoped to this one component instance — since the widget mounts one `MeetingTranscriptionCard` per file, expanding one file's transcript never affects another file's, with no extra wiring needed beyond the state being local rather than lifted to the page.
- **Failed**: an additional danger `Alert` supplements the red chip, so a failure isn't conveyed by color alone.
- **E2E fixture**: `e2e/fixtures/short-speech.mp3` is real (public-domain, trimmed) speech, copied from `apps/api/test/fixtures/short-speech.mp3` — unlike `test-recording.mp3` (synthetic bytes, fine for the upload/metadata specs that never look past the extension/MIME), a `COMPLETED` status needs the local Whisper "tiny" engine to actually decode and transcribe something real. `meeting-transcription.spec.ts` uploads it through the real UI and polls (no reload) until `Completed` — see the root `CLAUDE.md`'s "Local Whisper transcription" section for the toolchain this needs, and `docs/research-transcribe-uploaded-meeting-files-with-local-whisper.md` for the first-run cold-start cost (model download + CMake build) this spec's generous timeout absorbs. Its last test uploads the same fixture under two different in-memory filenames (one multi-file batch) to get two files each transcribing for real, and budgets `TRANSCRIPTION_TIMEOUT_MS * 2` since local Whisper only runs one job at a time — asserting the collapse-by-default and per-file-independent toggle behavior above needs two genuinely `COMPLETED` transcripts, not seeded/mocked ones.
- **`features/refresh-transcription`** (`api.ts`, `ui/refresh-transcription-button.tsx`): the "Refresh Transcription" `RefreshTranscriptionButton` is rendered in `MeetingTranscriptionCard`'s `Card.Header`, next to the "Transcript" title, whenever `isOrganizer` is true (including when `status` is `null`, unlike the status chip below it) — a non-organizer never sees it, same gating `DeleteMeetingFileButton` uses. `refreshTranscription(meetingId, fileId)` hits `POST /meetings/:meetingId/files/:fileId/transcription/refresh` and returns `{ transcriptionStatus, transcriptionText }` picked out of the response — the file's own metadata now (a file-scoped route, not a whole `Meeting` row); `MeetingTranscriptionCard`'s `onRefreshed` handler sets local `status`/`text` **from that response**, not a hardcoded `PENDING`, so it can never show progress for a run that was never actually dispatched. This matters because `RefreshTranscriptionHandler`'s compare-and-set can legitimately no-op server-side (e.g. a concurrent delete already removed the file this refresh was scoped to, in which case the endpoint 404s instead) — the frontend has to actually use the response's real value rather than assume success, or it would get stuck showing "Transcribing…" forever once polling sees the file gone and stops without ever correcting the status. Reflecting it immediately (rather than waiting for the next poll tick) also re-arms the polling effect above whenever the result actually is `PENDING`/`PROCESSING` (the effect depends on `status`), and resets `consecutivePollFailures` so a fresh run doesn't inherit a stale warning from a previous, already-settled one. Disabled (`isDisabled`) while `status` is already `PENDING`/`PROCESSING`, to prevent redundant concurrent refresh clicks. A failure of the refresh request itself (network/401/etc.) surfaces its own danger `Alert` (`refreshError` state, separate from the polling-failure warning and the `FAILED`-status alert) and leaves `status`/`text` untouched, since nothing on the server actually changed; a 401 instead calls back up to `onSessionExpired`, same convention as everywhere else in this widget. `meeting-transcription.spec.ts`'s second test drives this end to end: upload → wait for `Completed` → click Refresh → assert `Pending` (deterministic, same reasoning as the first test's own "Pending" assertion) and the button disabled → wait for `Completed` again → a second, non-organizer viewer never sees the button at all.

## Meeting summary widget (`src/widgets/meeting-summary/`, `src/features/refresh-meeting-summary/`)

One `MeetingSummaryCard` instance (`widgets/meeting-summary/ui/meeting-summary-card.tsx`) is mounted per meeting (not per file, unlike `MeetingTranscriptionCard`), seeded from `entities/meeting`'s `Meeting.summaryStatus`/`summaryText`/`summaryIsPartial`/`actionItems`/`decisions` and `_pages/meeting-detail`'s own `files` — the data the page already fetched via `getMeeting`/`listMeetingFiles`, so there's no duplicate fetch on mount. It renders for any authenticated viewer; only the Refresh Summary button is organizer-only.

- **The page gates the mount on `files.length > 0`** (`{files.length > 0 ? <MeetingSummaryCard ... /> : null}` in `_pages/meeting-detail/ui/meeting-detail-page.tsx`), not an internal early return — `MeetingSummaryCard` only ever seeds its `files` state once (`useState(initialFiles)`) and is never given a `key`, so if it mounted while the meeting still had zero files, uploading the meeting's first file would update the page's own `files` state but never reach this already-mounted instance: its seeded-empty `files` state has no re-sync path, `computeFilesReadiness` (`widgets/meeting-summary/lib/compute-files-readiness.ts`) would stay `'no-files'` forever, and `shouldPoll` requires `readiness !== 'no-files'` to ever start polling — a permanent deadlock only a full page reload could break. Gating the mount in the page means the component only ever exists once there's a real file to seed it from, the same reason `MeetingFileCard`/`MeetingTranscriptionCard` don't hit this (they're keyed per file and remount on a genuinely new one). Covered by `e2e/meeting-summary.spec.ts`'s "the summary card appears after uploading the meeting's first file, with no reload" test — drives a real upload through the UI with no `page.reload()` anywhere in the test.
- **`summaryStatus`/`text`/etc. props seed initial state only**, same convention `MeetingTranscriptionCard`'s `status`/`text` follow — once mounted, the component owns them via its own `useState`s, updated only by its polling effect below.
- **A `null` `summaryStatus`** means generation has never been triggered for this meeting yet (see `apps/api/CLAUDE.md`'s "Meeting summary, action items, and decisions" section for the trigger condition) — the component explains why using each file's own `transcriptionStatus` (`computeFilesReadiness`, `widgets/meeting-summary/lib/compute-files-readiness.ts`): "still being transcribed" while any file is non-terminal, "every recording failed transcription" once all files are terminal with none `COMPLETED`, or a generic "not yet available" for the (normally near-instantaneous) race window where every file is terminal-with-a-completion but the trigger hasn't stamped `PENDING` yet.
- **Status chip**: same HeroUI `Chip`/`Chip.Label` convention `MeetingTranscriptionCard` uses, shown for every non-null status including `COMPLETED` — a completed summary with no visible status chip was an actual bug caught by this widget's own Playwright suite (see below).
- **Polling**: while the summary/file-set combination hasn't yet reached a stable end state (`shouldPoll` — not `no-files`/`all-failed` file readiness, and summary status not `COMPLETED`/`FAILED`), a `setInterval` (3s, same cadence `MeetingTranscriptionCard` uses) calls `entities/meeting`'s `getMeeting(meetingId)` **and** `entities/meeting-file`'s `listMeetingFiles(meetingId)` together and updates all local state from both — the files re-fetch is what lets this component pick up the automatic `null` → `PENDING` transition once a meeting's last file finishes transcribing (each file's own `MeetingTranscriptionCard` instance polls independently and never surfaces that up to the page), without a reload. `listMeetingFiles`'s own in-flight-request coalescing (`entities/meeting-file/api.ts`) means this rarely costs an extra request beyond whatever `MeetingTranscriptionCard` instances are already polling for on the same tick.
- **Completed**: renders the Summary (plain `whitespace-pre-wrap` text), Action Items (a `<ul>`, each item's `assignee` appended as `" — <assignee>"` when present), and Decisions (a `<ul>`) sections; an empty action-item or decision list renders an explicit "No action items found."/"No decisions found." message rather than an empty list or nothing. `summaryIsPartial` renders a warning `Alert` above these sections.
- **`features/refresh-meeting-summary`** (`api.ts`, `ui/refresh-meeting-summary-button.tsx`): organizer-only, disabled while `status` is already `PENDING`/`PROCESSING`, mirroring `refresh-transcription`'s own button. `refreshMeetingSummary(meetingId)` hits `POST /meetings/:id/summary/refresh` and returns a **full fresh `Meeting`** (not just two fields, unlike `refreshTranscription`) — `MeetingSummaryCard`'s `handleRefreshed` sets local state from that response and also passes it up to the page's own `onRefreshed` (`setMeeting`) so the page's `meeting` object stays in sync too. Trusts the response's real resulting status rather than assuming `PENDING`, same reasoning `refreshTranscription` documents: `RefreshMeetingSummaryHandler` always discards the existing summary, but a fresh run only actually starts if the meeting's files are currently all-terminal-with-at-least-one-completed.
- **E2E tests** (`e2e/meeting-summary.spec.ts`) seed a meeting's summary/action-item/decision rows and a `MeetingFile`'s `transcriptionStatus` directly via Postgres (`seedMeetingSummary`/`seedMeetingFile`, `e2e/api-helpers.ts`) rather than drive a real Whisper transcription run or a real Gemini API call — summary generation is gated purely on `GEMINI_API_KEY` (see `apps/api/CLAUDE.md`), intentionally unset in this dev environment, so a real "Refresh Summary" click here only ever discards the existing summary; it can't be relied on to complete a new one. The refresh test asserts only that discard, not a regenerated result.

## Avatar upload feature (`src/features/upload-avatar/`, `src/entities/user/lib/avatar-file-types.ts`)

On `_pages/profile-edit`, `ui/avatar-upload.tsx`'s `AvatarUpload` renders unconditionally (unlike `upload-meeting-files`, it isn't gated on "no avatar yet" — re-uploading replaces the existing one). - `entities/user/lib/avatar-file-types.ts` holds `ACCEPTED_AVATAR_TYPES` (extension → MIME) and `MAX_AVATAR_FILE_SIZE_BYTES`, hand-mirrored from `apps/api/src/user/upload/avatar-upload.constants.ts`. `validateAvatarFile(file)` delegates to `shared/lib`'s `validateFileAgainstTypes(file, acceptedTypes, maxSizeBytes)` — the same extension/MIME/size checks `entities/meeting-file`'s `validateFile` runs, generalized to take a table and size limit so both call sites share one implementation instead of two copies.
- Validation re-runs on every file selection, disabling the Upload button until a file is selected and valid. Distinct `Alert`s separate a client-side validation error from a server-side upload failure (400s, or a generic — not size-specific — message for 413) so the two never overwrite each other. A 401 calls back up to the page's `onSessionExpired`, same convention as the meeting file upload feature. No drag-and-drop here (unlike `upload-meeting-files`) — click-to-browse only.

## Username and password features (`src/features/update-username/`, `src/features/change-password/`)

On `_pages/profile-edit/ui/profile-edit-page.tsx`, three independently submittable cards — avatar (above), username, password — sit stacked, each with its own `Form`, its own pending/error state, no shared submit path.

- **`update-username`** (`api.ts`, `ui/update-username-form.tsx`): `updateUsername(username)` `PATCH`es `/users/me/username` with `{ username }` (`string | null` — `null` clears it) and returns the refreshed `UserProfile`; validation (the 50-char limit, hand-mirrored from the API's DTO) surfaces via the server's own message.
- **`change-password`** (`api.ts`, `ui/change-password-form.tsx`): **a wrong current password is a 403, not a 401.** `ChangePasswordHandler` deliberately doesn't collapse "wrong current password" and "session no longer valid" onto the same status (see `apps/api/CLAUDE.md`'s "User" section) — a credential-check mismatch is `403`, while `401` means only what it means on every other authenticated call here: `JwtAuthGuard` rejecting a missing/expired token. That lets `changePassword()` use the same blanket `401 -> "session expired"` override every other call site uses, and lets `ChangePasswordForm` branch on `error.status === WRONG_CURRENT_PASSWORD_STATUS` (403) rather than string-matching the response body — a wrong current password attaches a field error to Current password (`passwordFieldErrors`), distinct from the form's shared `passwordError` `Alert` used for unexpected failures, and kept visually separate from a "new password too short" field error (already field-scoped via `validate`) and from `SAME_AS_CURRENT_PASSWORD_MESSAGE`'s own field error on New password (hand-mirrored from `ChangePasswordHandler`'s "New password must differ from current password" 400).
  - **Token reissue and success feedback**: `changePassword()` resolves an `AuthResult` with a fresh JWT (`ChangePasswordHandler` reissues one so the old password's token isn't silently left stale) — a successful submit calls `entities/session`'s `login({ accessToken, email: profile.email })` to adopt it, then clears both password fields and shows a `toast.success('Password updated')` — no auto-logout, per the PRD, since the reissued token already keeps the session valid.
  - **Visibility toggle reuse**: `shared/ui`'s `PasswordVisibilityToggle` (see "Shared layer" above) is what gives this form's two plain `TextField`s the same show/hide eye icon `PasswordConfirmField` uses on `/login`/`/register`, without forcing this form's non-paired current/new fields through `PasswordConfirmField`'s confirm-field-oriented API.

## UI changes must be visually tested

Any change that affects the UI (component markup, styling, layout, theming, interactive behavior) must be visually verified before the task is considered complete:
