# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the `api` app in the `video-meetings` npm workspaces monorepo (see `../../CLAUDE.md` for the repo-wide picture). It's a NestJS project scaffolded with `@nestjs/cli` (TypeScript, Express platform, Jest).

## Commands

Run from this directory, or from the repo root with `--workspace=api`:

```bash
npm run start:dev              # nest start --watch, http://localhost:3001
npm run start                  # nest start (no watch)
npm run start:debug            # nest start --debug --watch
npm run build                  # nest build -> dist/
npm run start:prod             # node dist/main (run after build)

npm run lint                   # eslint over {src,apps,libs,test} with --fix
npm run typecheck              # tsc --noEmit

npm run test                   # jest (unit tests, *.spec.ts, rootDir: src) - none currently exist; passWithNoTests keeps this green
npm run test:watch
npm run test:cov               # coverage output to ../coverage (i.e. apps/api/coverage)
npm run test:e2e               # jest -c test/jest-e2e.json (test/*.e2e-spec.ts)
npm run test:debug             # jest --runInBand under the node inspector

# run a single e2e file
npx jest -c test/jest-e2e.json auth.e2e-spec.ts
# run a single test by name
npx jest -c test/jest-e2e.json -t "creates a user and returns a JWT"
```

The API listens on `process.env.PORT ?? 3001` (`src/main.ts`) — deliberately not Nest's default 3000, since that port is used by the `web` app when both run together via the root `npm run dev`.

## Database (Prisma)

Data access goes through Prisma ORM 7, talking to the Postgres container from the root `docker-compose.yml` (see `../../CLAUDE.md`).

- `prisma/schema.prisma` defines the models: `User` (`id`, `email` (unique), `password`, `createdAt`, `updatedAt`); `Meeting` (`id`, `title`, `date`, `participants` (string array), `organizerId` FK to `User` with `onDelete: Cascade` and an `@@index` (Postgres doesn't index FK columns automatically), `createdAt`, `updatedAt`); and `MeetingFile` (`id`, `meetingId` FK to `Meeting` with `onDelete: Cascade` and an `@@index`, `originalName`, `filePath`, `mimeType`, `size`, `uploadedAt`, nullable transcription columns `transcriptionStatus` (`TranscriptionStatus?` — the schema's first enum: `PENDING`/`PROCESSING`/`COMPLETED`/`FAILED`), `transcriptionText`, `transcriptionUpdatedAt`, `createdAt`, `updatedAt` — see "Meetings" below). File and transcription state used to live directly on `Meeting` as nullable columns; Phase 1-multi-file-upload-drag-drop-fix moved it onto this separate one-to-many `MeetingFile` model instead, with no route or response-shape change (see "Meetings" below for how that's preserved). `updatedAt` on all three models is `@default(now()) @updatedAt` (Prisma sets it automatically on every write; the `@default` is kept so the schema matches the DB-level default the migration needed to backfill existing rows — dropping it would make `prisma migrate diff` non-empty). `prisma.config.ts` (repo convention as of Prisma 7 — connection URL no longer lives in the schema file) points Migrate at `DATABASE_URL`.
- The generator (`provider = "prisma-client"`, `moduleFormat = "cjs"`) writes generated client source to `prisma/generated/prisma/` — **gitignored, not committed**. Run `npx prisma generate` (or reinstall — it's wired as a `postinstall` script) after cloning or whenever `schema.prisma` changes.
- `PrismaClient` requires an explicit driver adapter in v7; construct it with `@prisma/adapter-pg`'s `PrismaPg` adapter over `DATABASE_URL`, not a bare `new PrismaClient()`.
- Env: copy `.env.example` to `.env` for the dev database (`video_meetings`). `.env.test` (committed — dummy local credentials only) points at a separate `video_meetings_test` database on the same container, used by e2e tests.
- Migrations: `npm run db:migrate:dev` against the dev DB (creates + applies a migration); apply the same migration to the test DB with `DATABASE_URL=<test-url> npm run db:migrate:deploy`. The test database itself needs to exist first — `docker/postgres-initdb/01-create-test-db.sql` (repo root) creates it automatically on a fresh container volume; for an already-initialized volume, create it once by hand (`docker exec <db-container> psql -U postgres -c "CREATE DATABASE video_meetings_test;"`).
- `PrismaModule` (`src/prisma/`) wraps `PrismaService` (extends `PrismaClient`, connects/disconnects with the Nest lifecycle) and is `@Global()`, so any module can inject `PrismaService` without importing `PrismaModule` itself.

## Auth

`AuthModule` (`src/auth/`) implements registration and login, both driven by the e2e tests in `test/auth.e2e-spec.ts` (written first, per this feature's TDD approach). It follows the CQRS pattern via `@nestjs/cqrs` rather than a conventional service layer — there is no `AuthService`. It owns authorization concerns only (token generation, token verification, credential verification); it does not touch the `User` table directly — that's [User](#user)'s job, reached via `CommandBus`/`QueryBus` rather than direct injection.

- `AuthController` only depends on `CommandBus`/`QueryBus`; it never calls Prisma or business logic directly. `POST /auth/register` dispatches a `RegisterCommand` (`src/auth/commands/`); `POST /auth/login` dispatches a `LoginQuery` (`src/auth/queries/`). Both take `{ email, password }` and both resolve to `{ accessToken: "<jwt>" }` on success.
- `RegisterHandler` (`@CommandHandler`) delegates the actual user creation to `UserModule` by dispatching a `CreateUserCommand` on the injected `CommandBus` (propagates `409 ConflictException` if the email is taken), then signs the JWT from the returned `{ id, email }`.
- `LoginHandler` (`@QueryHandler`) delegates the user lookup to `UserModule` by dispatching a `FindUserByEmailQuery` on the injected `QueryBus`, then verifies the password with `bcrypt.compare` and signs the JWT. `401 UnauthorizedException` for either an unknown email (query returns `null`) or a wrong password — deliberately not distinguished, to avoid leaking which emails are registered.
- Both handlers (plus `CqrsModule` and `UserModule`) are registered as `providers`/`imports` in `AuthModule`; there's no separate "module per handler" — keep new command/query handlers there too as the module grows. `AuthModule` imports `UserModule` purely to put its handlers in the Nest module graph (so `@nestjs/cqrs`'s app-wide handler discovery picks them up) — it never injects anything from `UserModule` directly.
- Request bodies are validated by DTOs (`src/auth/dto/`, `class-validator` decorators, definite-assignment `!` on properties since they're populated by `class-transformer`, not a constructor) enforced through a global `ValidationPipe` registered via the `APP_PIPE` token in `AppModule` — use `APP_PIPE`, not `app.useGlobalPipes()` in `main.ts` alone, since the e2e tests build the Nest app straight from `AppModule` and never run `main.ts`'s bootstrap.
- JWTs are signed by `@nestjs/jwt`'s `JwtModule`, configured with `registerAsync`/`useFactory` (not `register`) specifically so `process.env.JWT_SECRET` is read lazily at Nest's provider-instantiation time rather than at module-import time — a plain `register({ secret: process.env.JWT_SECRET })` would read `undefined` because `AuthModule`'s imports are evaluated before `main.ts`'s `import 'dotenv/config'` has a chance to run when Node resolves the module graph.
- `.env` / `.env.example` / `.env.test` all need a `JWT_SECRET` alongside `DATABASE_URL`.
- `JwtAuthGuard` (`src/auth/guards/jwt-auth.guard.ts`) is a plain `CanActivate`, not `@nestjs/passport` — there's no `passport`/`passport-jwt` dependency in this project, so it extracts the `Bearer` token from the `Authorization` header itself, verifies it via the injected `JwtService`, and sets `request.user` (typed by `AuthenticatedRequest`, `src/auth/interfaces/`) to `{ userId, email }` from the token payload; throws `401` if the header is missing or the token fails verification. `AuthModule` exports both `JwtModule` and `JwtAuthGuard` (alongside importing `AuthModule` itself) so other feature modules can protect their own routes with `@UseGuards(JwtAuthGuard)` and read `request.user` without redefining JWT verification.

## User

`UserModule` (`src/user/`) owns the `User` entity: creating a user, searching for one by email, and the authenticated user's own profile (including their avatar). Like `AuthModule`, it follows the CQRS pattern via `@nestjs/cqrs` — no `UserService`. Unlike `AuthModule`, it does have its own HTTP surface: `UserController` (behind `@UseGuards(JwtAuthGuard)` on the controller), reached via the shared `CommandBus`/`QueryBus`. `GET /users/me` dispatches a `GetUserProfileQuery` (`src/user/queries/`); `PATCH /users/me/username` dispatches an `UpdateUsernameCommand` (`src/user/commands/`), the request body validated by `UpdateUsernameDto` (`src/user/dto/`, `username` optional and nullable, `@MaxLength(50)`); `PATCH /users/me/password` dispatches a `ChangePasswordCommand`, the request body validated by `ChangePasswordDto` (`currentPassword` `@MinLength(1)`, `newPassword` `@MinLength(8)`); `POST /users/me/avatar` and `GET /users/me/avatar` (below) upload/replace and stream back the authenticated user's avatar. `CreateUserCommand`/`FindUserByEmailQuery` have no HTTP route of their own — they're reached only from `AuthModule`'s handlers.

- `CreateUserHandler` (`@CommandHandler` for `CreateUserCommand`, `src/user/commands/`) checks for an existing email (`409 ConflictException` if taken), hashes the password with `bcrypt` (10 salt rounds — never store or compare plaintext), creates the `User` row, publishes a `UserCreatedEvent` via `EventBus`, and returns `{ id, email }` (`UserRecord`, `src/user/interfaces/`) — deliberately not the password hash.
- `UpdateUsernameHandler` (`@CommandHandler` for `UpdateUsernameCommand`, `src/user/commands/`) persists a new `username` for one user id (always the authenticated user's — the command carries no other scope) and returns the refreshed `UserProfile`. It normalizes the incoming value first: `undefined` (field omitted from the request body) is passed straight through to Prisma, which skips `undefined` fields, so an omitted username leaves the stored value untouched; an empty/whitespace-only string or an explicit `null` clears it to `null`; anything else is stored trimmed. `404 NotFoundException` if the user id no longer exists (a still-valid JWT for a deleted user).
- `ChangePasswordHandler` (`@CommandHandler` for `ChangePasswordCommand`, `src/user/commands/`) looks up the authenticated user's stored hash via `FindUserByIdQuery` on the injected `QueryBus`. Unlike `LoginHandler`, the two failure modes here are deliberately _not_ collapsed onto the same status: a missing user (`404`-shaped race — a still-valid JWT for a since-deleted user, same as `UpdateUsernameHandler`'s P2025 case on `update`) is `401 UnauthorizedException`, meaning "this session is no longer valid"; a `bcrypt.compare` mismatch against `currentPassword` is `403 ForbiddenException`, meaning "you're authenticated, but this specific operation is refused" — a credential check, not an auth failure. `apps/web`'s client relies on this split to tell a wrong current password (show a field error) apart from a genuinely expired session (log out), rather than string-matching the response body. Rejects with `400 BadRequestException` if `newPassword` equals `currentPassword` (nothing meaningful to change), then `bcrypt.hash`es `newPassword` (10 salt rounds) and persists it. Returns a freshly signed `AuthResult` (same shape `LoginHandler` returns), since the caller's old token was minted before the change — outstanding tokens issued for _other_ sessions/devices are unaffected and remain valid until they naturally expire; this only rotates the calling session's own token, it doesn't invalidate the others.
- `FindUserByEmailHandler` (`@QueryHandler` for `FindUserByEmailQuery`, `src/user/queries/`) and `FindUserByIdHandler` (`@QueryHandler` for `FindUserByIdQuery`) both look a user up (by email, by id) and return `{ id, email, password }` (`UserWithCredentials`, `src/user/interfaces/`) or `null` if none exists. These are the only places the password hash leaves `UserModule` — safe because both queries are internal-only (never exposed over HTTP): `FindUserByEmailQuery` is consumed by `AuthModule`'s `LoginHandler` to verify credentials at login, `FindUserByIdQuery` mirrors its shape for handlers that already have the authenticated user's id (e.g. password change) and need the current hash instead of a fresh email lookup.
- `UserCreatedHandler` (`@EventsHandler`, `src/user/events/`) reacts to `UserCreatedEvent` — currently just an audit log line. This is the extension point for anything that should happen after a user is created (welcome email, analytics, etc.) without bloating `CreateUserHandler`.
- All of these handlers (plus `CqrsModule` itself) are registered as `providers` in `UserModule`; keep new command/query/event handlers there too as the module grows. `UserModule` also implements `OnModuleInit` to `mkdirSync` the avatar upload directory at startup, same as `MeetingsModule` does for its own upload directory.

### Avatar upload (`POST /users/me/avatar`)

- `UploadAvatarHandler` (`@CommandHandler` for `UploadAvatarCommand`, `src/user/commands/`) is scoped to `request.user.userId` from the JWT — there's no separate ownership check to make (unlike meeting file upload, which is reachable by any request naming a `meetingId`). It does still take the same `SELECT ... FOR UPDATE` row lock `UploadMeetingFileHandler` takes, inside a Prisma transaction: a single user can still issue two concurrent requests (two open tabs, two devices), and without the lock both would read the same "old" `avatarPath` and race on which newly-written file gets orphaned. Deliberately hand-mirrors (not shares code with) `UploadMeetingFileHandler`'s validation, locking, crash-safe replace ordering, and on-any-error disk cleanup — see `docs/research-plan-user-profile-and-edit-page.md.md` for why the two upload paths are kept independently duplicated rather than unified behind a shared abstraction.
- Files are stored via `multer`'s `diskStorage` (`src/user/upload/multer.config.ts`), wired onto the route with `@UseInterceptors(FileInterceptor('file', avatarUploadOptions))` — same server-generated `randomUUID()` on-disk filename convention as meeting uploads. The upload directory defaults to `apps/api/uploads/avatars` (override with the `AVATAR_UPLOAD_DIR` env var); `apps/api/.env.test` points it at `uploads/avatars-e2e-test`, isolated from meetings' own `.env.test`-scoped upload directory the same way.
- `src/user/upload/avatar-upload.constants.ts` holds the accepted extension → MIME type table (`.jpg`/`.jpeg`/`.png`/`.webp`) and `MAX_AVATAR_FILE_SIZE_BYTES` (env var, default 5 MB); `validate-file-type.ts` checks both, rejecting an unsupported extension, an unsupported MIME type, and an extension/MIME mismatch. Unlike meetings' upload path (below), this only runs once, in multer's `fileFilter` — `file.originalname`/`file.mimetype` are populated by multer from the multipart headers and are immutable for the rest of the request, so nothing between `fileFilter` and `UploadAvatarHandler` could flip a previously-valid pair to invalid; a handler-level re-check would just repeat the same check against the same inputs. An oversized file gets Nest's own `413 PayloadTooLargeException` for free via `FileInterceptor`.
- Re-uploading replaces any existing avatar in the same crash-safe order as meeting file replace: the new file is written to disk first (by multer), then the `User` row's three avatar columns (`avatarPath`, `avatarMimeType`, `avatarUploadedAt`) are updated to point at it, and only then is the old file unlinked — a crash between these leaves at worst an orphaned old file, never a row pointing at a deleted one. `avatarPath` itself is never exposed in `UserProfile` (an internal storage detail, like `password` is excluded from `UserRecord`); the response is the same `UserProfile` shape `GET /users/me` returns.

### Avatar serving (`GET /users/me/avatar`)

- `GetUserAvatarHandler` (`@QueryHandler` for `GetUserAvatarQuery`, `src/user/queries/`) is scoped to `request.user.userId` from the JWT, same as the upload handler — there's no separate ownership check, since an avatar is only ever reachable via the requesting user's own session. `404 NotFoundException` if the user row has no avatar (`avatarPath` null); all three of `avatarPath`, `avatarMimeType`, and `avatarUploadedAt` are always written together by `UploadAvatarHandler`, so a non-null `avatarPath` guarantees the other two are non-null too.
- The controller streams the file with `StreamableFile` (`@Res({ passthrough: true })`, not bare `@Res()`, same as meeting file download), setting `Content-Type` from the stored MIME type. Unlike meeting file download, there's no `Content-Disposition` — an avatar is displayed inline (e.g. an `<img>` tag), never downloaded as a named attachment.
- The avatar is displayed on several pages at once (profile, edit, main), so the response sets `Cache-Control: private, max-age=60, must-revalidate` and `Last-Modified` (from `avatarUploadedAt`, refreshed on every re-upload) to let the browser skip re-fetching the same bytes across navigations within that window. `private` only keeps the response out of shared/proxy caches — it doesn't make the browser's own cache key on the `Authorization` header, so without an explicit `Vary: Authorization` a shared/kiosk browser could replay one user's cached avatar bytes to the next user who logs in with a different token inside that 60s window; the response sets `Vary: Authorization` specifically to rule that out.

## Meetings

`MeetingsModule` (`src/meetings/`) implements meeting CRUD (create/list/get-by-id/delete) plus multi-file recording upload/list/download/delete, behind `JwtAuthGuard`, driven by `test/meetings.e2e-spec.ts`, `test/delete-meeting.e2e-spec.ts`, `test/meeting-file-multi-upload.e2e-spec.ts`, `test/meeting-file-transcription.e2e-spec.ts`, and `test/meeting-transcription-refresh.e2e-spec.ts` (all written first, same TDD approach as auth). Like `AuthModule`, it follows the CQRS pattern via `@nestjs/cqrs` — no `MeetingsService`.

- `MeetingsController` only depends on `CommandBus`/`QueryBus` plus the current request's `user` (attached by `JwtAuthGuard`, via `@UseGuards(JwtAuthGuard)` on the controller). `POST /meetings` dispatches a `CreateMeetingCommand` (`src/meetings/commands/`); `GET /meetings` dispatches a `GetMeetingsQuery`, scoped to the authenticated user's own meetings (`organizerId`); `GET /meetings/:id` dispatches a `GetMeetingQuery` (`src/meetings/queries/`) with just the `id` — any authenticated user can read any meeting by id, not only its organizer; `DELETE /meetings/:id` dispatches a `DeleteMeetingCommand` (below), organizer-scoped, returning `204 No Content`; `POST /meetings/:id/files` (below) batch-uploads one or more of a meeting's recordings; `GET /meetings/:id/files`, `GET /meetings/:id/files/:fileId/download`, `DELETE /meetings/:id/files/:fileId`, and `POST /meetings/:id/files/:fileId/transcription/refresh` (below) round out the per-file lifecycle; `POST /meetings/:id/summary/refresh` (below) lets an organizer force a fresh meeting-level summary, and `POST /meetings/:id/summary/stop` (below) lets an organizer abandon one that's still in flight. These file-scoped routes replaced an earlier meeting-scoped generation (`POST/GET/DELETE /meetings/:id/file`, `POST /meetings/:id/transcription/refresh`) as a breaking route change — there is no v1/v2 coexistence, the old routes are gone.
- `CreateMeetingHandler` (`@CommandHandler`) just persists the `Meeting` row via Prisma (`title`, `date`, `participants`, `organizerId`) and returns it — no side effects yet, unlike `RegisterHandler`'s event publish.
- `GetMeetingsHandler` (`@QueryHandler`) lists meetings filtered by `organizerId` only — there's no cross-user visibility for the list endpoint.
- `GetMeetingHandler` (`@QueryHandler`) looks a meeting up by `id` alone (`findUnique`) and throws `404 NotFoundException` if none matches — reads are intentionally unscoped by organizer; only `GetMeetingsQuery` (the list) is organizer-scoped.
- `DeleteMeetingHandler` (`@CommandHandler` for `DeleteMeetingCommand`, `src/meetings/commands/`) takes the same `SELECT "id" FROM "Meeting" ... FOR UPDATE`-locked ownership check as the file-lifecycle handlers below (`404`, not `403`, for a non-organizer or nonexistent meeting), reads the meeting's `MeetingFile` rows inside that same transaction (their `filePath`s are gone once the delete below cascades), then deletes the `Meeting` row — Prisma's `onDelete: Cascade` on `MeetingFile`/`ActionItem`/`Decision`'s `meetingId` FK removes all three dependent row sets automatically. Every file's on-disk bytes are unlinked (`getUploadDir()` + `filePath`, same as `DeleteMeetingFileHandler`) only after the transaction commits, same crash-safe ordering as file delete.
- All handlers plus `CqrsModule` are registered as `providers` in `MeetingsModule`, which also imports `AuthModule` (to get `JwtAuthGuard` and its `JwtService` dependency into scope) — same one-module structure as `AuthModule`, keep new meeting command/query/event handlers there as it grows. `MeetingsModule` also implements `OnModuleInit` to `mkdirSync` the upload directory (see below) at startup, since multer's `diskStorage` does not create missing directories itself.
- Request bodies are validated by `CreateMeetingDto` (`src/meetings/dto/`): `title` required non-empty string, `date` an ISO-8601 string (stored as Prisma `DateTime`), `participants` an array of valid emails (an empty array is allowed — inviting no one is valid).
- `Meeting` (`prisma/schema.prisma`) has an `organizerId` FK to `User` with `onDelete: Cascade`, so deleting a user cleans up their meetings automatically, plus a one-to-many `files MeetingFile[]` relation (below) — a meeting starts with no files and can hold up to `MAX_FILES_PER_MEETING` (10, see below), each uploaded independently and never replaced by a later upload. `GetMeetingHandler`/`GetMeetingsHandler` are untouched by the multi-file work and still `include: { files: true }` and re-flatten only the _first_ (oldest) file back onto the response object via `flattenMeetingFile` (`src/meetings/meeting-file-flatten.util.ts`), under the old singular field names (`fileOriginalName`, `filePath`, `fileMimeType`, `fileSize`, `fileUploadedAt`, `transcriptionStatus`, `transcriptionText`, `transcriptionUpdatedAt`) — a legacy, deliberately-partial view kept for backward compatibility, not the source of truth for a meeting's files. `GET /meetings/:id/files` (below) is the real per-file listing; a meeting with more than one file has files `GET /meetings`/`GET /meetings/:id` never surface.
- `MeetingFile` (`prisma/schema.prisma`) owns one uploaded recording and its own transcription state: `meetingId` FK to `Meeting` with `onDelete: Cascade` and an `@@index`, `originalName`, `filePath`, `mimeType`, `size`, `uploadedAt` (all required — a row only ever exists once a file has actually been uploaded), plus nullable transcription columns `transcriptionStatus`, `transcriptionText`, `transcriptionUpdatedAt`, null meaning "not yet transcribed". `UploadMeetingFileHandler` (below) only ever adds new rows — it never deletes or updates an existing one as a side effect of a new upload. `DeleteMeetingFileHandler` deletes exactly the one targeted row and no other. `RefreshTranscriptionHandler` is the one handler that updates an existing `MeetingFile` row in place (resetting its own three transcription columns), since a refresh reuses the same underlying file.
- `meeting-file.types.ts`'s `MeetingFileMetadata`/`toMeetingFileMetadata` is the one shared response shape for every route that returns a single file's metadata (list, upload's per-file batch results, delete, refresh) — `{ id, originalName, mimeType, size, uploadedAt, transcriptionStatus, transcriptionText }`, deliberately never including `filePath` (an internal on-disk storage detail no client needs).

### File upload (`POST /meetings/:id/files`)

- `UploadMeetingFileHandler` (`@CommandHandler` for `UploadMeetingFileCommand`, `src/meetings/commands/`) accepts a batch (`Express.Multer.File[]`, possibly just one file — the web client always sends exactly one today) and returns `{ accepted: MeetingFileMetadata[], rejected: { originalName, reason }[] }`, one entry per file in the request, rather than failing the whole batch on one bad file. Type (`validateFileType`) and size (`file.size > MAX_UPLOAD_FILE_SIZE_BYTES`) are validated per file up front, tolerating individual failures; the remaining type/size-valid files are then organizer-scoped and cap-checked inside one `SELECT * FROM "Meeting" ... FOR UPDATE`-locked transaction (`404`, not `403`, for a non-organizer or nonexistent meeting) — the lock serializes a concurrent batch upload to the same meeting so two requests can't both read the same "existing count" and together overshoot the cap. Whichever type/size-valid files still fit under `MAX_FILES_PER_MEETING` (10) each become their own new `MeetingFile` row inside that transaction; any that don't fit are rejected with a cap-exceeded reason, same as a type/size failure. Uploads are purely additive — no existing row is ever read, updated, or deleted by this handler.
- Disk cleanup on failure is intentionally asymmetric around the transaction: if the transaction itself throws (nonexistent/non-organizer meeting), every file in the batch is still just unattached bytes on disk, so all of them are unlinked. Once the transaction commits, the created rows are real — a later failure (e.g. the follow-up `PENDING` write below) must never unlink an already-committed file's bytes, or it would orphan a live DB row pointing at nothing; that write is caught and logged per file instead of aborting the batch. Every _rejected_ file (bad type, oversized, or over-cap) is still individually unlinked once the accept/reject split is known, since multer wrote it to disk before this handler ever ran (`filePath`, not the client's original name, is what's compared, so this can't accidentally sweep up an accepted file sharing a rejected one's original name).
- Files are stored on local disk via `multer`'s `diskStorage` (`src/meetings/upload/multer.config.ts`), wired onto the route with `@UseInterceptors(FilesInterceptor('files', MAX_FILES_PER_MEETING, meetingFilesUploadOptions))`. The on-disk filename is always server-generated (`randomUUID()` + original extension), never the client's — a path-traversal defense; the original filename is kept only as metadata.
- The upload directory defaults to `apps/api/uploads/` (override with the `UPLOAD_DIR` env var), gitignored since it holds real uploaded files. `apps/api/.env.test` points `UPLOAD_DIR` at a nested `uploads/e2e-test` subdirectory specifically so the meeting-file e2e specs' cleanup (`rm -rf` on their own `UPLOAD_DIR`) can never delete real files sitting in the same top-level directory during a locally running `npm run dev` — mirrors how `.env.test` already isolates `DATABASE_URL` into a separate database.
- `src/meetings/upload/file-upload.constants.ts` holds the accepted extension → MIME type table, `MAX_UPLOAD_FILE_SIZE_BYTES` (env var, default 500 MB — not a value specified anywhere in the PRD, just a starting assumption; `apps/api/.env.test` lowers it to 1 MB so the oversized-file e2e test doesn't need to allocate hundreds of MB), and `MAX_FILES_PER_MEETING` (fixed at 10, not configurable per environment — see the PRD's "Non-goals"). `validate-file-type.ts` checks extension/MIME against `Express.Multer.File`, rejecting an unsupported extension, an unsupported MIME type, and an extension/MIME mismatch, each with its own message. This table must stay identical to whatever `apps/web` uses for its own client-side validation — the two apps don't share code, so keep both copies in sync by hand.
- `meetingFilesUploadOptions` (`multer.config.ts`) deliberately has **no `fileFilter`**, unlike the old single-file upload options: a batch must tolerate individual invalid files without aborting the other, valid ones in the same request, and Multer's `fileFilter` contract can't do that (calling back with an error there fails the whole request) — so every file is written to disk unconditionally and validated authoritatively, per file, in the handler (above). Its `limits.fileSize` is likewise not the real per-file cap: Multer's own size limit can't be made batch-tolerant either (once it trips mid-stream, Multer aborts the entire multipart request, no per-file equivalent of `fileFilter`'s "skip just this one" exists), so it's set to a much looser `MULTER_FILE_SIZE_HARD_LIMIT_BYTES` (4× `MAX_UPLOAD_FILE_SIZE_BYTES`) purely as a DoS backstop for a truly extreme single file — the real cap is enforced, batch-tolerantly, in the handler instead. A file that does trip this outer ceiling still gets Nest's own `413 PayloadTooLargeException` for the whole request.

### Listing, download, and delete (`GET /meetings/:id/files`, `GET /meetings/:id/files/:fileId/download`, `DELETE /meetings/:id/files/:fileId`)

- `ListMeetingFilesHandler` (`@QueryHandler` for `ListMeetingFilesQuery`, `src/meetings/queries/`) confirms the meeting exists (`404` if not) then returns every `MeetingFile` row for it, ordered `uploadedAt: 'asc'`, mapped through `toMeetingFileMetadata`. Unscoped by organizer, same access rule the file lifecycle has always used — any authenticated user can list a meeting's files.
- `GetMeetingFileQuery`/`GetMeetingFileHandler` (`src/meetings/queries/`) is the read behind the download route: confirms the meeting exists (`404` if not), then `findUnique`s the `MeetingFile` by its own `id`. Scoped by both `fileId` and `meetingId` — a `fileId` that exists but belongs to a different meeting is treated the same as one that doesn't exist at all (`404`), rather than leaking cross-meeting existence.
- `GET /meetings/:id/files/:fileId/download` streams the file with `StreamableFile` (`@Res({ passthrough: true })`, not bare `@Res()`, so Nest's response pipeline still applies). `Content-Type` is set from the stored MIME type; `Content-Disposition` is built by `src/meetings/upload/content-disposition.ts` using the RFC 5987 `filename*=UTF-8''...` form (plus an ASCII-fallback `filename="..."` for older clients) rather than naive interpolation of the original name — a stored name with `"` or non-ASCII characters would otherwise produce a malformed header. Also accessible to any authenticated user.
- `DELETE /meetings/:id/files/:fileId` (`DeleteMeetingFileCommand`/`DeleteMeetingFileHandler`, `src/meetings/commands/`) takes the same `SELECT * FROM "Meeting" ... FOR UPDATE` lock upload takes, so a concurrent upload/delete on the same meeting serializes instead of racing on a stale file read. `404`, not `403`, for a non-organizer or nonexistent meeting; `404` again for a `fileId` that doesn't exist or belongs to a different meeting (same cross-meeting-leakage guard as download). Deletes exactly the one row matching `fileId` — every other file on the meeting, and its own transcript, is untouched. Crash-safe ordering: the `MeetingFile` row is deleted (inside the transaction) before the file is unlinked from disk (after it commits) — a crash between the two leaves at worst an orphaned file, never a row pointing at a deleted one.

### Transcription

- Uploading a file automatically starts transcription in the background, no separate user action — `UploadMeetingFileHandler` (above), once its transaction has committed and disk cleanup for rejected files is done, writes `transcriptionStatus: 'PENDING'` as a follow-up update for each accepted file (so the response already reflects it) and dispatches one `TranscribeMeetingFileCommand` per accepted file on the injected `CommandBus` **without awaiting any of them** — fire-and-forget, per the plan's "Open technical decision" (in-process async, not a durable queue; see `docs/plan-transcribe-uploaded-meeting-files-with-local-whisper.md`). A batch of N accepted files fires N independent jobs, each carrying its own `fileId`/`filePath`, so one file's job can never read or write another's row. Each dispatch (and each PENDING write) is wrapped in its own `.catch()` (logged, not thrown) so a failure on one file can't surface as an unhandled rejection or block the rest of the batch's response. Guarded by `isTranscriptionEnabled()` (`src/meetings/transcription/whisper.constants.ts`) — see root `CLAUDE.md`'s "Local Whisper transcription" section for why this can be off.
- `TranscribeMeetingFileCommand`/`TranscribeMeetingFileHandler` (`src/meetings/commands/`) is the actual job: carries `meetingId` (for logging only), `fileId`, and `filePath`; it re-reads the `MeetingFile` row by `fileId` and no-ops if the row is gone or its `filePath` no longer matches what the job was dispatched for (deleted, or — pre-multi-file — replaced, before the job even started), writes `PROCESSING`, calls `transcribeFile()` (`src/meetings/transcription/transcribe-file.ts`, the sole call into `nodejs-whisper`'s `nodewhisper()`), then writes `COMPLETED` + the transcript text + `transcriptionUpdatedAt` on success or `FAILED` on any error (transcript left untouched). All three writes past the initial guard — `PROCESSING`, `COMPLETED`, `FAILED` — use `updateMany({ where: { id: fileId, filePath } })` on `MeetingFile`, not `update`, as an atomic compare-and-set, not just a plain write: `transcribeFile()` can take anywhere from seconds to minutes, long enough for a delete (or, on another file entirely, an unrelated upload) to have already superseded this row. If the row no longer matches by the time any of these writes run, it's stale and is dropped silently (`count === 0`, and for `PROCESSING` specifically, the handler returns without ever calling `transcribeFile()`) rather than overwriting whatever the delete already left. Deliberately **not** the `SELECT ... FOR UPDATE` row lock the upload/delete handlers use — that would hold a Postgres transaction open for the entire duration of inference.
- `transcribeFile()` passes `modelName: 'tiny'` (multilingual, not `tiny.en` — the PRD is transcription-only in the source language, not English-only), `autoDownloadModelName: 'tiny'`, and an explicit `modelRootPath` (`getWhisperModelRootPath()`, same lazy-getter convention as `getUploadDir()`) into `nodewhisper()`. It never passes the live uploaded file directly — `nodejs-whisper`'s own conversion step doesn't just read whatever isn't already a valid 16kHz-mono-PCM WAV, it re-encodes and **renames the temp file over the input path** for anything already `.wav`-extensioned (i.e. most real `.wav` recordings, which aren't 16kHz mono), silently destroying the original. `transcribeFile()` copies the upload to a disposable temp path first and runs `nodewhisper()` against that copy, so nothing it does can ever touch the original file. `nodewhisper()`'s own resolved value is whisper-cli's raw stdout, which prefixes every segment with a `[HH:MM:SS.mmm --> HH:MM:SS.mmm]` timestamp — there's no flag in `nodejs-whisper`'s typed options to suppress this — so `transcribeFile()` instead reads the separate, timestamp-free `<wavPath>.txt` sidecar file that the `-otxt` flag (`whisperOptions.outputInText`) makes whisper-cli write alongside its stdout, and deletes the copy plus both byproduct files afterwards.
- `getUploadDir()` (`src/meetings/upload/file-upload.constants.ts`) is always resolved to an absolute path (`path.resolve`), even though `UPLOAD_DIR` itself can be relative (as `apps/api/.env.test`'s is) — `nodejs-whisper`'s own whisper-cli invocation does a `shelljs.cd()` into its own package directory for the duration of the call, which changes this whole Node process's `cwd`; a relative path resolved elsewhere at the wrong moment would resolve against that directory instead. The no-`UPLOAD_DIR` fallback specifically is resolved once at module load and reused, rather than re-resolving against `process.cwd()` on every call — otherwise that fallback path would reopen the exact same race for the (documented-default) case where `UPLOAD_DIR` is unset.
- The command is registered in `MeetingsModule`'s `CommandHandlers` array like every other meetings handler — no separate module.
- `POST /meetings/:id/files/:fileId/transcription/refresh` (`RefreshTranscriptionCommand`/`RefreshTranscriptionHandler`, `src/meetings/commands/`) lets the organizer re-run transcription for one specific file — retrying a `FAILED` result, or re-transcribing on top of a `COMPLETED` one. Organizer-scoped using the same `SELECT ... FOR UPDATE`-locked raw query on `Meeting` as upload/delete (`404`, not `403`, for a non-organizer or nonexistent meeting); `404` again for a `fileId` that doesn't exist or belongs to a different meeting. Inside that locked transaction it's the one handler that updates an existing `MeetingFile` row in place, resetting its `transcriptionStatus`/`transcriptionText`/`transcriptionUpdatedAt` to `null` (discarding whatever transcript belongs to the run being refreshed), then — after the transaction commits — writes `PENDING` as its own compare-and-set follow-up update (keyed on the file's `id` + `filePath`, same guard `TranscribeMeetingFileHandler` uses) and dispatches `TranscribeMeetingFileCommand` fire-and-forget, the same two-step upload uses (guarded by `isTranscriptionEnabled()` the same way). Its response always comes from a fresh re-read of the file by id (not a locally-constructed object, and no longer the whole `Meeting` row) — the compare-and-set above may have no-opped because a concurrent delete removed the `MeetingFile` row entirely, in which case a `404` is what the caller should see, not a fabricated `PENDING`. Returns `200`, not `201` — this triggers an action on an existing resource, it doesn't create one.

### Meeting summary, action items, and decisions

Once every one of a meeting's files reaches a terminal transcription state (`COMPLETED`/`FAILED`) with at least one `COMPLETED`, a meeting-level summary, action-item list, and decision list are generated automatically via the Gemini API, mirroring transcription's own trigger/status/compare-and-set shape one level up (meeting instead of file) — see `docs/prd-meeting-summary-action-items-and-decisions.md` and `docs/research-meeting-summary-action-items-and-decisions.md` for the full design rationale. An organizer can also force a fresh run via `POST /meetings/:id/summary/refresh`, abandon an in-progress one via `POST /meetings/:id/summary/stop` (see "Stop" below), and any upload, delete, or transcription refresh on a meeting with an existing summary invalidates it automatically (see "Refresh and invalidation" below).

- Schema: `SummaryStatus` (`prisma/schema.prisma`, same four values as `TranscriptionStatus`) plus `summaryStatus`, `summaryText`, `summaryIsPartial`, `summaryUpdatedAt`, `summaryGenerationToken` directly on `Meeting` (a meeting has exactly one summary, unlike the one-to-many `MeetingFile` relation, so this is a 1:1 fit for flat columns). `ActionItem` (`id`, `meetingId` FK with `onDelete: Cascade` and an `@@index`, `description`, `assignee` nullable, `order`, `createdAt`, `updatedAt`) and `Decision` (same shape minus `assignee`) are their own one-to-many models off `Meeting`. `order` (`Int @default(0)`) exists because Postgres evaluates `now()` once per transaction, not per statement — every row from one `createMany` call would otherwise get an identical `createdAt` with no reliable tiebreaker; `order` is stamped from each result array's index at creation time so `GET /meetings/:id` can return them in the LLM's original order.
- Trigger detection: `MeetingSummaryTriggerService.maybeTrigger()` (`src/meetings/summary/meeting-summary-trigger.service.ts`, an injectable provider — constructor-DI'd `PrismaService`/`CommandBus`, same convention every handler in this codebase uses) is called from `TranscribeMeetingFileHandler` after each terminal write (`COMPLETED` or `FAILED`) actually lands (guarded on that write's own `updateMany` count, so a stale/superseded write can't trigger a check), and again from `DeleteMeetingFileHandler`/`RefreshMeetingSummaryHandler` after their own file-set change (see "Refresh and invalidation" below) — `UploadMeetingFileHandler` and `RefreshTranscriptionHandler` deliberately do _not_ call it themselves, since the file they just touched is always non-terminal at that point (see below), so `TranscribeMeetingFileHandler`'s own call, once that file's (re)transcription lands, is what actually re-triggers generation for those two. It re-reads every sibling `MeetingFile` row and, if all are terminal and at least one is `COMPLETED`, stamps a fresh `summaryGenerationToken` (`randomUUID()`) and writes `summaryStatus: 'PENDING'` synchronously (same null-safe `OR` guard `GenerateMeetingSummaryHandler`'s own claim uses below, so it never disturbs an already-`PROCESSING` run — and so a client polling right after this fires can observe an intermediate "Pending" state) and dispatches `GenerateMeetingSummaryCommand` with that token, fire-and-forget — same `.catch()`-logged, non-awaited dispatch style the transcription handlers use. Safe to call redundantly: two files finishing near-simultaneously can each independently dispatch the command, and whichever token the row ends up holding is the one whose eventual claim succeeds (see below). Unlike a typical fire-and-forget dispatch, `maybeTrigger()` itself never rejects — its whole body is wrapped in try/catch-and-log — since, unlike its original `TranscribeMeetingFileHandler` caller (which is itself dispatched fire-and-forget), `DeleteMeetingFileHandler`/`RefreshMeetingSummaryHandler` await it directly in the request path, and a transient DB error re-checking the trigger must never fail an otherwise-successful delete/refresh whose primary write already committed.
- `GenerateMeetingSummaryCommand`/`GenerateMeetingSummaryHandler` (`src/meetings/commands/`) is the actual job, carrying the `summaryGenerationToken` the trigger stamped it with. Every write this handler makes is keyed on `id` + that token — analogous to `TranscribeMeetingFileHandler`'s `updateMany` keyed on `id` + `filePath` — so a run superseded by a refresh/invalidation (which nulls the token via `clearMeetingSummary`, see below) can no longer overwrite newer results once its token no longer matches the row's current one. The initial claim also keeps the pre-token `summaryStatus` OR-guard: `updateMany({ where: { id: meetingId, summaryGenerationToken: token, OR: [{ summaryStatus: null }, { summaryStatus: { not: 'PROCESSING' } }] }, data: { summaryStatus: 'PROCESSING' } })` — the explicit `summaryStatus: null` branch is load-bearing, since Prisma's `not` filter on a nullable column compiles to a raw SQL `<>`, which never matches `NULL` under three-valued logic, so without it a meeting generating its summary for the very first time could never be claimed. `claimed === 0` means either another concurrent run already owns it or this run was already superseded, and it no-ops either way. Once claimed, it re-reads the meeting's files; if none are `COMPLETED` any more (e.g. a delete raced the fire-and-forget dispatch and removed the file that triggered it), it resets `summaryStatus` back to `null` (still token-guarded) rather than `FAILED` — there was nothing to summarize, which isn't the same as a failed attempt. Otherwise it builds one combined transcript from the `COMPLETED` files' `transcriptionText`, ordered by `uploadedAt` and joined with `\n\n`, calls `generateMeetingSummary()`, and on success the `COMPLETED` + `summaryText` + `summaryIsPartial` (`true` if any sibling file is `FAILED`) + `summaryUpdatedAt` write is itself the token compare-and-set — only if it actually matches (row count > 0) does the same transaction go on to replace `ActionItem`/`Decision` rows (each stamped with its `order`, see above), so a superseded run's stale action items/decisions can never clobber a newer run's. On any _actual_ error (an LLM API error or a malformed response) it writes `FAILED` (again token-guarded), leaving any prior summary/action items/decisions untouched — same failure behavior `TranscribeMeetingFileHandler` gives an existing transcript. Gated first by `isSummaryGenerationEnabled()` (below) — if unset, the whole thing no-ops, leaving `summaryStatus` exactly as it was.
- LLM client (`src/meetings/summary/`): `generateMeetingSummary()` (`generate-meeting-summary.ts`) wraps the Gemini API (`@google/genai`, the current official Google Gen AI Node/TypeScript SDK) via `responseSchema` + `responseMimeType: 'application/json'` for structured output — not the already-installed `@anthropic-ai/claude-agent-sdk`, since Gemini's free tier avoids per-call billing (see the research doc's "LLM call" section for the full tradeoff). `parseMeetingSummaryResponse()` (`parse-meeting-summary-response.ts`, unit-tested on its own since `responseSchema` doesn't guarantee a parseable/valid response every time) validates the raw JSON text into `{ summary, actionItems: { description, assignee? }[], decisions: string[] }`, throwing on anything malformed — an empty `assignee` string is normalized away (field omitted) rather than stored. `isSummaryGenerationEnabled()` (`summary.constants.ts`) gates the feature purely on `GEMINI_API_KEY`'s presence (no separate on/off flag, unlike `TRANSCRIPTION_ENABLED`) — same lazy-getter-at-point-of-use convention as `isTranscriptionEnabled()`. `.env.test` explicitly blanks `GEMINI_API_KEY` (not merely omits it) so the bulk of the e2e suite never attempts generation — dotenv's `config()` never overrides a key already present in `process.env`, and `jest-e2e.setup.ts` loads `.env.test` before falling back to a developer's own `.env` (real secrets, e.g. `ANTHROPIC_API_KEY`, never need to live in a committed file); merely never setting it in `.env.test` let a real `GEMINI_API_KEY` in `.env` leak through that fallback into every e2e spec's process, not just the summary-specific ones — since `MeetingSummaryTriggerService.maybeTrigger()` fires after _any_ real transcription completes, this made unrelated real-Whisper specs trigger real, unmocked Gemini calls as a side effect once a real key was ever configured locally (confirmed 2026-08-26, flaky failures with nothing to do with what those tests actually exercise); `meeting-summary-generation.e2e-spec.ts` and `meeting-summary-refresh.e2e-spec.ts` set a dummy value for themselves (to pass the gate) and `jest.mock()` `generate-meeting-summary.ts` (to avoid a real, billed network call) rather than gating on a real key the way `agent-sdk.e2e-spec.ts` does for its Anthropic call. `test/gemini-api.e2e-spec.ts` is the one spec that _does_ call the real Gemini API (a trivial "reply with exactly: pong" prompt against the actual configured `GEMINI_MODEL`) — added after `gemini-2.5-flash` was retired for new users and every real call silently ended in `FAILED` with nothing in the suite ever noticing, since every other summary test mocks the LLM call itself. Unlike `agent-sdk.e2e-spec.ts` (`it.skip`'d even when a key is present — Anthropic's API isn't free), this one runs whenever a real key is configured, since Gemini's free tier is genuinely $0. It deliberately reads `GEMINI_API_KEY` straight out of `.env` on disk (`dotenv.parse`) rather than trusting `process.env.GEMINI_API_KEY` — `test:e2e` runs `--runInBand` (one shared process for every e2e file), and both dummy-key specs above unconditionally overwrite that same `process.env` key at module load time; since Jest's default sequencer doesn't guarantee a fixed file order, trusting `process.env` here would make this test's gate (and even its actual API key) depend on which of those files happened to run first.
- `GetMeetingHandler` additionally includes `actionItems`/`decisions` (via `include`, ordered by `order` — not `createdAt`, see above — mapped through `toActionItemMetadata`/`toDecisionMetadata` in `src/meetings/summary/action-item-decision.types.ts` — same small-response-shaping-function precedent as `toMeetingFileMetadata`) in `GET /meetings/:id`'s response; `summaryStatus`/`summaryText`/`summaryIsPartial`/`summaryUpdatedAt` pass through automatically since they're plain `Meeting` columns already included by `flattenMeetingFile`'s `...meeting` spread, but `summaryGenerationToken` is explicitly destructured back out before returning — an internal compare-and-set correlation detail, not something a client needs, same as `MeetingFile`'s own `filePath` is excluded from `MeetingFileMetadata`. `GetMeetingsHandler` (the list endpoint) is untouched — this data is only surfaced on the detail route.
- `GenerateMeetingSummaryHandler`/`RefreshMeetingSummaryHandler` are registered in `MeetingsModule`'s `CommandHandlers` array like every other meetings handler; `MeetingSummaryTriggerService` is registered directly in `providers` (it's neither a command nor a query handler) — no separate module.

**Refresh and invalidation:** `POST /meetings/:id/summary/refresh` (`RefreshMeetingSummaryCommand`/`RefreshMeetingSummaryHandler`, `src/meetings/commands/`) lets an organizer force a fresh run — organizer-scoped using the same `SELECT ... FOR UPDATE`-locked raw query on `Meeting` as upload/delete/refresh-transcription (`404`, not `403`, for a non-organizer or nonexistent meeting). It always discards the current summary via `clearMeetingSummary()` (`src/meetings/summary/clear-meeting-summary.ts`, a small shared helper every invalidation path below also uses — deletes `ActionItem`/`Decision` rows and nulls `summaryStatus`/`summaryText`/`summaryIsPartial`/`summaryUpdatedAt`/`summaryGenerationToken` on `Meeting`, taking a `Prisma.TransactionClient` so every caller runs it inside whatever lock it already holds), unconditionally — unlike the file-change hooks below, an explicit Refresh click always attempts a new run regardless of whether one exists yet. It then calls `MeetingSummaryTriggerService.maybeTrigger()` and returns a fresh `GetMeetingQuery` read (not a locally-constructed response), since the trigger may or may not have actually fired a new run depending on the meeting's current file states. `UploadMeetingFileHandler`, `DeleteMeetingFileHandler`, and `RefreshTranscriptionHandler` each call `clearMeetingSummary()` the same way, but conditionally — only when the file-set change actually happens (a fully rejected upload batch changes nothing) _and_ the meeting already has a non-empty summary (`summaryText !== null`, read from the same locked `Meeting` row each handler's `SELECT ... FOR UPDATE` already fetches). Only `DeleteMeetingFileHandler` additionally calls `maybeTrigger()` afterward (unconditionally, regardless of whether anything was actually cleared) — deleting a file can itself be what makes the remaining file set newly eligible, since no other row changes state. `UploadMeetingFileHandler` and `RefreshTranscriptionHandler` don't: the file they just created/reset is itself always non-terminal (`null`) at that point, so `maybeTrigger()`'s "all files terminal" check could never fire there regardless of any sibling file's state — `TranscribeMeetingFileHandler`'s own pre-existing call, once that file's (re)transcription actually lands, is what re-triggers generation for those two instead.

**Stop:** `POST /meetings/:id/summary/stop` (`StopMeetingSummaryCommand`/`StopMeetingSummaryHandler`, `src/meetings/commands/`) lets an organizer abandon a summary run that's still `PENDING`/`PROCESSING` — same organizer-scoped `SELECT ... FOR UPDATE` lock as refresh (`404`, not `403`, for a non-organizer or nonexistent meeting), reading `summaryStatus` off the locked row. Only actually calls `clearMeetingSummary()` when that status is `PENDING`/`PROCESSING`; a `COMPLETED`/`FAILED`/`null` summary is left untouched (there's nothing in-flight to stop, and clearing it would just discard a finished result for no reason — a real hazard given Stop and the run's own completion write can race). `clearMeetingSummary()` nulls `summaryGenerationToken` along with the rest, so it doubles as the actual cancellation mechanism: `GenerateMeetingSummaryHandler`'s writes are all keyed on that token, so the abandoned run's own `generateMeetingSummary()` call — still genuinely in flight against the Gemini API, since nothing here can cancel an outbound HTTP call — finds its token no longer current whenever it eventually resolves, and its result-write compare-and-set no-ops instead of resurrecting what Stop just discarded (the identical protection a superseding refresh already relies on). Unlike refresh, this handler deliberately never calls `MeetingSummaryTriggerService.maybeTrigger()` afterward — the meeting's files are still all-terminal-with-a-completion, so an immediate re-trigger would just restart the very run the organizer asked to stop; generation only resumes on an explicit `POST /meetings/:id/summary/refresh` or a subsequent file-set change. Registered in `MeetingsModule`'s `CommandHandlers` array like every other meetings handler.

Adding the feature required a new dependency (`@google/genai`) and a new env var (`GEMINI_API_KEY`, in `.env`/`.env.example`; intentionally unset in `.env.test`, see above) — get a free-tier key from Google AI Studio to exercise this locally.

## Architecture

- `app.module.ts` is the root module, importing `PrismaModule`, `AuthModule`, and `MeetingsModule` (no root-level controller/service — the default scaffolded `AppController`/`AppService` `GET /` "Hello World!" endpoint was unused by the `web` app and has been removed). `main.ts` bootstraps via `NestFactory.create(AppModule)`, after `import 'dotenv/config'` (must be the first import, so env vars are set before anything else in the module graph loads). Add further features as their own Nest modules under `src/` and import them into `AppModule`.
- `tsconfig.json` extends the repo's `../../tsconfig.base.json`. Note this app intentionally does **not** use TypeScript's master `strict: true` — it sets individual flags (`strictNullChecks`, `noImplicitAny`, `strictBindCallApply`, plus `forceConsistentCasingInFileNames` from the base) because Nest's decorator-heavy DI patterns don't pair well with the full strict set (e.g. `strictPropertyInitialization`). Don't casually turn on full `strict` mode without checking DI-injected class properties still compile.
- `tsconfig.build.json` extends `tsconfig.json` and excludes `test/**` and `*spec.ts` — this is what `nest build` actually uses (see `nest-cli.json`'s implicit build config), so `npm run build` won't pull in test files even though `tsconfig.json` itself has no `include`/`exclude`.
- `eslint.config.mjs` is a flat config built on `typescript-eslint`'s `recommendedTypeChecked` (type-aware linting via `parserOptions.projectService`) plus `eslint-plugin-prettier/recommended`. `@typescript-eslint/no-explicit-any` is turned off and `no-floating-promises`/`no-unsafe-argument` are downgraded to warnings — expect `any` to be allowed and floating promises to warn rather than error. There is no local `.prettierrc`; Prettier formatting comes from the repo root config.
- Tests: unit specs sit next to the code they test (`*.spec.ts`, Jest config inlined in `package.json` with `rootDir: "src"`); e2e specs live in `test/*.e2e-spec.ts` under their own Jest config (`test/jest-e2e.json`). e2e tests boot the real `AppModule` (via `@nestjs/testing` + `supertest`) against the real Postgres test database (`.env.test`), not mocks — `auth.e2e-spec.ts` cleans the `User` table in `beforeEach` via a Prisma client of its own, while `meetings.e2e-spec.ts` isolates itself with a uniquely-emailed registered user per test instead (there's no `Meeting` table cleanup — a fresh user per test has no meetings to collide with). Because multiple spec files mutate the same shared test database, `test:e2e` runs Jest with `--runInBand` — without it, Jest's default per-file worker parallelism caused real, reproducible cross-file flakiness (one spec's `User` cleanup racing another spec's assertions). The `test:e2e` script also runs Jest with `NODE_OPTIONS=--experimental-vm-modules` (via `cross-env` for cross-platform support) because Prisma 7's generated client uses a WASM query compiler loaded through a dynamic `import()`, which Jest's CJS runtime otherwise rejects. `jest-e2e.json` also maps `.js`-suffixed relative imports back to their `.ts` source (`moduleNameMapper`) since the generated client's own imports use `.js` extensions per Node's ESM-style resolution even in `cjs` output mode. The unit config carries the identical `moduleNameMapper` — a unit spec for any handler that injects `PrismaService` pulls the generated client into the module graph (even when every Prisma call is mocked), and without the mapper the suite fails to load with `Cannot find module './internal/class.js'`.
