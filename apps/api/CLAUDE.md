# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the `api` app in the `video-meetings` npm workspaces monorepo (see `../../CLAUDE.md` for the repo-wide picture). It's a NestJS project scaffolded with `@nestjs/cli` (TypeScript, Express platform, Jest).

## Commands

Run from this directory, or from the repo root with `--workspace=api`:

```bash
npm run start:dev              # nest start --watch, http://localhost:3001
npm run start                  # nest start (no watch)
npm run start:debug            # nest start --debug --watch
npm run build                  # nest build -> dist/
npm run start:prod             # node dist/main (run after build)

npm run lint                   # eslint over {src,apps,libs,test} with --fix
npm run typecheck              # tsc --noEmit

npm run test                   # jest (unit tests, *.spec.ts, rootDir: src) - none currently exist; passWithNoTests keeps this green
npm run test:watch
npm run test:cov               # coverage output to ../coverage (i.e. apps/api/coverage)
npm run test:e2e               # jest -c test/jest-e2e.json (test/*.e2e-spec.ts)
npm run test:debug             # jest --runInBand under the node inspector

# run a single e2e file
npx jest -c test/jest-e2e.json auth.e2e-spec.ts
# run a single test by name
npx jest -c test/jest-e2e.json -t "creates a user and returns a JWT"
```

The API listens on `process.env.PORT ?? 3001` (`src/main.ts`) — deliberately not Nest's default 3000, since that port is used by the `web` app when both run together via the root `npm run dev`.

## Database (Prisma)

Data access goes through Prisma ORM 7, talking to the Postgres container from the root `docker-compose.yml` (see `../../CLAUDE.md`).

- `prisma/schema.prisma` defines the models: `User` (`id`, `email` (unique), `password`, `createdAt`, `updatedAt`) and `Meeting` (`id`, `title`, `date`, `participants` (string array), `organizerId` FK to `User` with `onDelete: Cascade` and an `@@index` (Postgres doesn't index FK columns automatically), `createdAt`, `updatedAt`, plus nullable file metadata columns `fileOriginalName`, `filePath`, `fileMimeType`, `fileSize`, `fileUploadedAt` — see "Meetings" below). `updatedAt` on both models is `@default(now()) @updatedAt` (Prisma sets it automatically on every write; the `@default` is kept so the schema matches the DB-level default the migration needed to backfill existing rows — dropping it would make `prisma migrate diff` non-empty). `prisma.config.ts` (repo convention as of Prisma 7 — connection URL no longer lives in the schema file) points Migrate at `DATABASE_URL`.
- The generator (`provider = "prisma-client"`, `moduleFormat = "cjs"`) writes generated client source to `prisma/generated/prisma/` — **gitignored, not committed**. Run `npx prisma generate` (or reinstall — it's wired as a `postinstall` script) after cloning or whenever `schema.prisma` changes.
- `PrismaClient` requires an explicit driver adapter in v7; construct it with `@prisma/adapter-pg`'s `PrismaPg` adapter over `DATABASE_URL`, not a bare `new PrismaClient()`.
- Env: copy `.env.example` to `.env` for the dev database (`video_meetings`). `.env.test` (committed — dummy local credentials only) points at a separate `video_meetings_test` database on the same container, used by e2e tests.
- Migrations: `npm run db:migrate:dev` against the dev DB (creates + applies a migration); apply the same migration to the test DB with `DATABASE_URL=<test-url> npm run db:migrate:deploy`. The test database itself needs to exist first — `docker/postgres-initdb/01-create-test-db.sql` (repo root) creates it automatically on a fresh container volume; for an already-initialized volume, create it once by hand (`docker exec <db-container> psql -U postgres -c "CREATE DATABASE video_meetings_test;"`).
- `PrismaModule` (`src/prisma/`) wraps `PrismaService` (extends `PrismaClient`, connects/disconnects with the Nest lifecycle) and is `@Global()`, so any module can inject `PrismaService` without importing `PrismaModule` itself.

## Auth

`AuthModule` (`src/auth/`) implements registration and login, both driven by the e2e tests in `test/auth.e2e-spec.ts` (written first, per this feature's TDD approach). It follows the CQRS pattern via `@nestjs/cqrs` rather than a conventional service layer — there is no `AuthService`. It owns authorization concerns only (token generation, token verification, credential verification); it does not touch the `User` table directly — that's [User](#user)'s job, reached via `CommandBus`/`QueryBus` rather than direct injection.

- `AuthController` only depends on `CommandBus`/`QueryBus`; it never calls Prisma or business logic directly. `POST /auth/register` dispatches a `RegisterCommand` (`src/auth/commands/`); `POST /auth/login` dispatches a `LoginQuery` (`src/auth/queries/`). Both take `{ email, password }` and both resolve to `{ accessToken: "<jwt>" }` on success.
- `RegisterHandler` (`@CommandHandler`) delegates the actual user creation to `UserModule` by dispatching a `CreateUserCommand` on the injected `CommandBus` (propagates `409 ConflictException` if the email is taken), then signs the JWT from the returned `{ id, email }`.
- `LoginHandler` (`@QueryHandler`) delegates the user lookup to `UserModule` by dispatching a `FindUserByEmailQuery` on the injected `QueryBus`, then verifies the password with `bcrypt.compare` and signs the JWT. `401 UnauthorizedException` for either an unknown email (query returns `null`) or a wrong password — deliberately not distinguished, to avoid leaking which emails are registered.
- Both handlers (plus `CqrsModule` and `UserModule`) are registered as `providers`/`imports` in `AuthModule`; there's no separate "module per handler" — keep new command/query handlers there too as the module grows. `AuthModule` imports `UserModule` purely to put its handlers in the Nest module graph (so `@nestjs/cqrs`'s app-wide handler discovery picks them up) — it never injects anything from `UserModule` directly.
- Request bodies are validated by DTOs (`src/auth/dto/`, `class-validator` decorators, definite-assignment `!` on properties since they're populated by `class-transformer`, not a constructor) enforced through a global `ValidationPipe` registered via the `APP_PIPE` token in `AppModule` — use `APP_PIPE`, not `app.useGlobalPipes()` in `main.ts` alone, since the e2e tests build the Nest app straight from `AppModule` and never run `main.ts`'s bootstrap.
- JWTs are signed by `@nestjs/jwt`'s `JwtModule`, configured with `registerAsync`/`useFactory` (not `register`) specifically so `process.env.JWT_SECRET` is read lazily at Nest's provider-instantiation time rather than at module-import time — a plain `register({ secret: process.env.JWT_SECRET })` would read `undefined` because `AuthModule`'s imports are evaluated before `main.ts`'s `import 'dotenv/config'` has a chance to run when Node resolves the module graph.
- `.env` / `.env.example` / `.env.test` all need a `JWT_SECRET` alongside `DATABASE_URL`.
- `JwtAuthGuard` (`src/auth/guards/jwt-auth.guard.ts`) is a plain `CanActivate`, not `@nestjs/passport` — there's no `passport`/`passport-jwt` dependency in this project, so it extracts the `Bearer` token from the `Authorization` header itself, verifies it via the injected `JwtService`, and sets `request.user` (typed by `AuthenticatedRequest`, `src/auth/interfaces/`) to `{ userId, email }` from the token payload; throws `401` if the header is missing or the token fails verification. `AuthModule` exports both `JwtModule` and `JwtAuthGuard` (alongside importing `AuthModule` itself) so other feature modules can protect their own routes with `@UseGuards(JwtAuthGuard)` and read `request.user` without redefining JWT verification.

## User

`UserModule` (`src/user/`) owns the `User` entity: creating a user, searching for one by email, and the authenticated user's own profile (including their avatar). Like `AuthModule`, it follows the CQRS pattern via `@nestjs/cqrs` — no `UserService`. Unlike `AuthModule`, it does have its own HTTP surface: `UserController` (behind `@UseGuards(JwtAuthGuard)` on the controller), reached via the shared `CommandBus`/`QueryBus`. `GET /users/me` dispatches a `GetUserProfileQuery` (`src/user/queries/`); `PATCH /users/me/username` dispatches an `UpdateUsernameCommand` (`src/user/commands/`), the request body validated by `UpdateUsernameDto` (`src/user/dto/`, `username` optional and nullable, `@MaxLength(50)`); `PATCH /users/me/password` dispatches a `ChangePasswordCommand`, the request body validated by `ChangePasswordDto` (`currentPassword` `@MinLength(1)`, `newPassword` `@MinLength(8)`); `POST /users/me/avatar` and `GET /users/me/avatar` (below) upload/replace and stream back the authenticated user's avatar. `CreateUserCommand`/`FindUserByEmailQuery` have no HTTP route of their own — they're reached only from `AuthModule`'s handlers.

- `CreateUserHandler` (`@CommandHandler` for `CreateUserCommand`, `src/user/commands/`) checks for an existing email (`409 ConflictException` if taken), hashes the password with `bcrypt` (10 salt rounds — never store or compare plaintext), creates the `User` row, publishes a `UserCreatedEvent` via `EventBus`, and returns `{ id, email }` (`UserRecord`, `src/user/interfaces/`) — deliberately not the password hash.
- `UpdateUsernameHandler` (`@CommandHandler` for `UpdateUsernameCommand`, `src/user/commands/`) persists a new `username` for one user id (always the authenticated user's — the command carries no other scope) and returns the refreshed `UserProfile`. It normalizes the incoming value first: `undefined` (field omitted from the request body) is passed straight through to Prisma, which skips `undefined` fields, so an omitted username leaves the stored value untouched; an empty/whitespace-only string or an explicit `null` clears it to `null`; anything else is stored trimmed. `404 NotFoundException` if the user id no longer exists (a still-valid JWT for a deleted user).
- `ChangePasswordHandler` (`@CommandHandler` for `ChangePasswordCommand`, `src/user/commands/`) looks up the authenticated user's stored hash via `FindUserByIdQuery` on the injected `QueryBus`, `bcrypt.compare`s it against `currentPassword` (`401 UnauthorizedException` on a missing user or a mismatch — deliberately not distinguished, same reasoning as `LoginHandler`), then `bcrypt.hash`es `newPassword` (10 salt rounds) and persists it. Same `404`-shaped race as `UpdateUsernameHandler` (a still-valid JWT for a since-deleted user hitting `update`'s P2025), but surfaced as `401` here instead, for consistency with the rest of this handler's "invalid credentials" framing. Returns a freshly signed `AuthResult` (same shape `LoginHandler` returns), since the caller's old token was minted before the change — outstanding tokens issued for _other_ sessions/devices are unaffected and remain valid until they naturally expire; this only rotates the calling session's own token, it doesn't invalidate the others.
- `FindUserByEmailHandler` (`@QueryHandler` for `FindUserByEmailQuery`, `src/user/queries/`) and `FindUserByIdHandler` (`@QueryHandler` for `FindUserByIdQuery`) both look a user up (by email, by id) and return `{ id, email, password }` (`UserWithCredentials`, `src/user/interfaces/`) or `null` if none exists. These are the only places the password hash leaves `UserModule` — safe because both queries are internal-only (never exposed over HTTP): `FindUserByEmailQuery` is consumed by `AuthModule`'s `LoginHandler` to verify credentials at login, `FindUserByIdQuery` mirrors its shape for handlers that already have the authenticated user's id (e.g. password change) and need the current hash instead of a fresh email lookup.
- `UserCreatedHandler` (`@EventsHandler`, `src/user/events/`) reacts to `UserCreatedEvent` — currently just an audit log line. This is the extension point for anything that should happen after a user is created (welcome email, analytics, etc.) without bloating `CreateUserHandler`.
- All of these handlers (plus `CqrsModule` itself) are registered as `providers` in `UserModule`; keep new command/query/event handlers there too as the module grows. `UserModule` also implements `OnModuleInit` to `mkdirSync` the avatar upload directory at startup, same as `MeetingsModule` does for its own upload directory.

### Avatar upload (`POST /users/me/avatar`)

- `UploadAvatarHandler` (`@CommandHandler` for `UploadAvatarCommand`, `src/user/commands/`) is scoped to `request.user.userId` from the JWT — there's no separate ownership check to make (unlike meeting file upload, which is reachable by any request naming a `meetingId`). It does still take the same `SELECT ... FOR UPDATE` row lock `UploadMeetingFileHandler` takes, inside a Prisma transaction: a single user can still issue two concurrent requests (two open tabs, two devices), and without the lock both would read the same "old" `avatarPath` and race on which newly-written file gets orphaned. Deliberately hand-mirrors (not shares code with) `UploadMeetingFileHandler`'s validation, locking, crash-safe replace ordering, and on-any-error disk cleanup — see `docs/research-plan-user-profile-and-edit-page.md.md` for why the two upload paths are kept independently duplicated rather than unified behind a shared abstraction.
- Files are stored via `multer`'s `diskStorage` (`src/user/upload/multer.config.ts`), wired onto the route with `@UseInterceptors(FileInterceptor('file', avatarUploadOptions))` — same server-generated `randomUUID()` on-disk filename convention as meeting uploads. The upload directory defaults to `apps/api/uploads/avatars` (override with the `AVATAR_UPLOAD_DIR` env var); `apps/api/.env.test` points it at `uploads/avatars-e2e-test`, isolated from meetings' own `.env.test`-scoped upload directory the same way.
- `src/user/upload/avatar-upload.constants.ts` holds the accepted extension → MIME type table (`.jpg`/`.jpeg`/`.png`/`.webp`) and `MAX_AVATAR_FILE_SIZE_BYTES` (env var, default 5 MB); `validate-file-type.ts` checks both, rejecting an unsupported extension, an unsupported MIME type, and an extension/MIME mismatch. Unlike meetings' upload path (below), this only runs once, in multer's `fileFilter` — `file.originalname`/`file.mimetype` are populated by multer from the multipart headers and are immutable for the rest of the request, so nothing between `fileFilter` and `UploadAvatarHandler` could flip a previously-valid pair to invalid; a handler-level re-check would just repeat the same check against the same inputs. An oversized file gets Nest's own `413 PayloadTooLargeException` for free via `FileInterceptor`.
- Re-uploading replaces any existing avatar in the same crash-safe order as meeting file replace: the new file is written to disk first (by multer), then the `User` row's three avatar columns (`avatarPath`, `avatarMimeType`, `avatarUploadedAt`) are updated to point at it, and only then is the old file unlinked — a crash between these leaves at worst an orphaned old file, never a row pointing at a deleted one. `avatarPath` itself is never exposed in `UserProfile` (an internal storage detail, like `password` is excluded from `UserRecord`); the response is the same `UserProfile` shape `GET /users/me` returns.

### Avatar serving (`GET /users/me/avatar`)

- `GetUserAvatarHandler` (`@QueryHandler` for `GetUserAvatarQuery`, `src/user/queries/`) is scoped to `request.user.userId` from the JWT, same as the upload handler — there's no separate ownership check, since an avatar is only ever reachable via the requesting user's own session. `404 NotFoundException` if the user row has no avatar (`avatarPath` null); all three of `avatarPath`, `avatarMimeType`, and `avatarUploadedAt` are always written together by `UploadAvatarHandler`, so a non-null `avatarPath` guarantees the other two are non-null too.
- The controller streams the file with `StreamableFile` (`@Res({ passthrough: true })`, not bare `@Res()`, same as meeting file download), setting `Content-Type` from the stored MIME type. Unlike meeting file download, there's no `Content-Disposition` — an avatar is displayed inline (e.g. an `<img>` tag), never downloaded as a named attachment.
- The avatar is displayed on several pages at once (profile, edit, main), so the response sets `Cache-Control: private, max-age=60, must-revalidate` and `Last-Modified` (from `avatarUploadedAt`, refreshed on every re-upload) to let the browser skip re-fetching the same bytes across navigations within that window. `private` only keeps the response out of shared/proxy caches — it doesn't make the browser's own cache key on the `Authorization` header, so without an explicit `Vary: Authorization` a shared/kiosk browser could replay one user's cached avatar bytes to the next user who logs in with a different token inside that 60s window; the response sets `Vary: Authorization` specifically to rule that out.

## Meetings

`MeetingsModule` (`src/meetings/`) implements meeting CRUD (create/list/get-by-id) plus recording file upload/metadata/download/delete, behind `JwtAuthGuard`, driven by `test/meetings.e2e-spec.ts`, `test/meeting-file-upload.e2e-spec.ts`, and `test/meeting-file-management.e2e-spec.ts` (all written first, same TDD approach as auth). Like `AuthModule`, it follows the CQRS pattern via `@nestjs/cqrs` — no `MeetingsService`.

- `MeetingsController` only depends on `CommandBus`/`QueryBus` plus the current request's `user` (attached by `JwtAuthGuard`, via `@UseGuards(JwtAuthGuard)` on the controller). `POST /meetings` dispatches a `CreateMeetingCommand` (`src/meetings/commands/`); `GET /meetings` dispatches a `GetMeetingsQuery`, scoped to the authenticated user's own meetings (`organizerId`); `GET /meetings/:id` dispatches a `GetMeetingQuery` (`src/meetings/queries/`) with just the `id` — any authenticated user can read any meeting by id, not only its organizer; `POST /meetings/:id/file` (below) uploads or replaces a meeting's recording; `GET /meetings/:id/file`, `GET /meetings/:id/file/download`, and `DELETE /meetings/:id/file` (below) round out the file lifecycle.
- `CreateMeetingHandler` (`@CommandHandler`) just persists the `Meeting` row via Prisma (`title`, `date`, `participants`, `organizerId`) and returns it — no side effects yet, unlike `RegisterHandler`'s event publish.
- `GetMeetingsHandler` (`@QueryHandler`) lists meetings filtered by `organizerId` only — there's no cross-user visibility for the list endpoint.
- `GetMeetingHandler` (`@QueryHandler`) looks a meeting up by `id` alone (`findUnique`) and throws `404 NotFoundException` if none matches — reads are intentionally unscoped by organizer; only `GetMeetingsQuery` (the list) is organizer-scoped.
- All handlers plus `CqrsModule` are registered as `providers` in `MeetingsModule`, which also imports `AuthModule` (to get `JwtAuthGuard` and its `JwtService` dependency into scope) — same one-module structure as `AuthModule`, keep new meeting command/query/event handlers there as it grows. `MeetingsModule` also implements `OnModuleInit` to `mkdirSync` the upload directory (see below) at startup, since multer's `diskStorage` does not create missing directories itself.
- Request bodies are validated by `CreateMeetingDto` (`src/meetings/dto/`): `title` required non-empty string, `date` an ISO-8601 string (stored as Prisma `DateTime`), `participants` an array of valid emails (an empty array is allowed — inviting no one is valid).
- `Meeting` (`prisma/schema.prisma`) has an `organizerId` FK to `User` with `onDelete: Cascade`, so deleting a user cleans up their meetings automatically. It also carries nullable file metadata columns (`fileOriginalName`, `filePath`, `fileMimeType`, `fileSize`, `fileUploadedAt`) — nullable because a meeting starts with no file, and the feature keeps at most one file per meeting, always replaced, no version history.

### File upload (`POST /meetings/:id/file`)

- `UploadMeetingFileHandler` (`@CommandHandler` for `UploadMeetingFileCommand`, `src/meetings/commands/`) is organizer-scoped using the same `findFirst`-by-`id`-and-`organizerId` shape `GetMeetingHandler` used before its Phase 1 change (a non-organizer gets `404`, not `403`, consistent with not leaking which meetings exist). The ownership check, metadata update, and old-file-path capture run inside a single Prisma transaction using `SELECT ... FOR UPDATE` to lock the meeting row — this makes two concurrent re-uploads to the same meeting serialize instead of racing on which file gets orphaned.
- Files are stored on local disk via `multer`'s `diskStorage` (`src/meetings/upload/multer.config.ts`), wired onto the route with `@UseInterceptors(FileInterceptor('file', meetingFileUploadOptions))`. The on-disk filename is always server-generated (`randomUUID()` + original extension), never the client's — a path-traversal defense; the original filename is kept only as metadata.
- The upload directory defaults to `apps/api/uploads/` (override with the `UPLOAD_DIR` env var), gitignored since it holds real uploaded files. `apps/api/.env.test` points `UPLOAD_DIR` at a nested `uploads/e2e-test` subdirectory specifically so `meeting-file-upload.e2e-spec.ts`'s cleanup (`rm -rf` on its own `UPLOAD_DIR`) can never delete real files sitting in the same top-level directory during a locally running `npm run dev` — mirrors how `.env.test` already isolates `DATABASE_URL` into a separate database.
- `src/meetings/upload/file-upload.constants.ts` holds the accepted extension → MIME type table and the max upload size (`MAX_UPLOAD_FILE_SIZE_BYTES` env var, default 500 MB — not a value specified anywhere in the PRD, just a starting assumption). `validate-file-type.ts` checks both against `Express.Multer.File`, rejecting an unsupported extension, an unsupported MIME type, and an extension/MIME mismatch, each with its own message. Validation runs twice: cheaply in multer's `fileFilter` (before any bytes hit disk) and again authoritatively in the handler. This table must stay identical to whatever `apps/web` uses for its own client-side validation (Phase 5) — the two apps don't share code, so keep both copies in sync by hand.
- An oversized file is rejected with Nest's own `413 PayloadTooLargeException` — `FileInterceptor` already maps multer's `LIMIT_FILE_SIZE` error to it automatically; no custom exception filter is needed (or present).
- Re-uploading to a meeting that already has a file replaces it, in crash-safe order: the new file is written to disk (by multer, before the handler runs) and the row is updated to point at it, before the old file is deleted from disk. A crash mid-sequence leaves at worst an orphaned old file, never a row pointing at a deleted one.

### Metadata, download, and delete (`GET /meetings/:id/file`, `GET /meetings/:id/file/download`, `DELETE /meetings/:id/file`)

- `GetMeetingFileQuery`/`GetMeetingFileHandler` (`src/meetings/queries/`) is the shared read behind both the metadata and download routes: an unscoped-by-organizer `findUnique` by `id` (same lookup `GetMeetingHandler` uses), `404` if the meeting doesn't exist, `404` again if it exists but has no file (`filePath` null). It narrows Prisma's nullable file columns down to a non-null `MeetingFileRecord` — safe because `UploadMeetingFileHandler`/`DeleteMeetingFileHandler` always write or clear all five file columns together, never a subset.
- `GET /meetings/:id/file` maps that record to `{ fileOriginalName, fileMimeType, fileSize, fileUploadedAt }` — no `filePath`, since that's an on-disk storage detail, not something a client needs. Accessible to any authenticated user, not just the organizer.
- `GET /meetings/:id/file/download` reuses the same query, then streams the file with `StreamableFile` (`@Res({ passthrough: true })`, not bare `@Res()`, so Nest's response pipeline still applies). `Content-Type` is set from the stored MIME type; `Content-Disposition` is built by `src/meetings/upload/content-disposition.ts` using the RFC 5987 `filename*=UTF-8''...` form (plus an ASCII-fallback `filename="..."` for older clients) rather than naive interpolation of `fileOriginalName` — a stored name with `"` or non-ASCII characters would otherwise produce a malformed header. Also accessible to any authenticated user.
- `DELETE /meetings/:id/file` (`DeleteMeetingFileCommand`/`DeleteMeetingFileHandler`, `src/meetings/commands/`) is organizer-scoped using the same `findFirst`-by-`id`-and-`organizerId` shape as upload conceptually, but implemented as a `SELECT ... FOR UPDATE` inside a Prisma transaction — same lock `UploadMeetingFileHandler` takes — so a concurrent upload/reupload to the same meeting serializes against the delete instead of racing on a stale `filePath` read (without the lock, a delete reading the row just before a reupload commits could clear the _new_ file's metadata while unlinking the already-replaced old path, orphaning the new file on disk). `404`, not `403`, for a non-organizer or nonexistent meeting; `404` again if the meeting has no file. Crash-safe ordering matches the upload replace path: the row's five file columns are cleared (inside the transaction) before the file is unlinked from disk (after it commits) — a crash between the two leaves at worst an orphaned file, never a row pointing at a deleted one.

## Architecture

- `app.module.ts` is the root module, importing `PrismaModule`, `AuthModule`, and `MeetingsModule` (no root-level controller/service — the default scaffolded `AppController`/`AppService` `GET /` "Hello World!" endpoint was unused by the `web` app and has been removed). `main.ts` bootstraps via `NestFactory.create(AppModule)`, after `import 'dotenv/config'` (must be the first import, so env vars are set before anything else in the module graph loads). Add further features as their own Nest modules under `src/` and import them into `AppModule`.
- `tsconfig.json` extends the repo's `../../tsconfig.base.json`. Note this app intentionally does **not** use TypeScript's master `strict: true` — it sets individual flags (`strictNullChecks`, `noImplicitAny`, `strictBindCallApply`, plus `forceConsistentCasingInFileNames` from the base) because Nest's decorator-heavy DI patterns don't pair well with the full strict set (e.g. `strictPropertyInitialization`). Don't casually turn on full `strict` mode without checking DI-injected class properties still compile.
- `tsconfig.build.json` extends `tsconfig.json` and excludes `test/**` and `*spec.ts` — this is what `nest build` actually uses (see `nest-cli.json`'s implicit build config), so `npm run build` won't pull in test files even though `tsconfig.json` itself has no `include`/`exclude`.
- `eslint.config.mjs` is a flat config built on `typescript-eslint`'s `recommendedTypeChecked` (type-aware linting via `parserOptions.projectService`) plus `eslint-plugin-prettier/recommended`. `@typescript-eslint/no-explicit-any` is turned off and `no-floating-promises`/`no-unsafe-argument` are downgraded to warnings — expect `any` to be allowed and floating promises to warn rather than error. There is no local `.prettierrc`; Prettier formatting comes from the repo root config.
- Tests: unit specs sit next to the code they test (`*.spec.ts`, Jest config inlined in `package.json` with `rootDir: "src"`); e2e specs live in `test/*.e2e-spec.ts` under their own Jest config (`test/jest-e2e.json`). e2e tests boot the real `AppModule` (via `@nestjs/testing` + `supertest`) against the real Postgres test database (`.env.test`), not mocks — `auth.e2e-spec.ts` cleans the `User` table in `beforeEach` via a Prisma client of its own, while `meetings.e2e-spec.ts` isolates itself with a uniquely-emailed registered user per test instead (there's no `Meeting` table cleanup — a fresh user per test has no meetings to collide with). Because multiple spec files mutate the same shared test database, `test:e2e` runs Jest with `--runInBand` — without it, Jest's default per-file worker parallelism caused real, reproducible cross-file flakiness (one spec's `User` cleanup racing another spec's assertions). The `test:e2e` script also runs Jest with `NODE_OPTIONS=--experimental-vm-modules` (via `cross-env` for cross-platform support) because Prisma 7's generated client uses a WASM query compiler loaded through a dynamic `import()`, which Jest's CJS runtime otherwise rejects. `jest-e2e.json` also maps `.js`-suffixed relative imports back to their `.ts` source (`moduleNameMapper`) since the generated client's own imports use `.js` extensions per Node's ESM-style resolution even in `cjs` output mode. The unit config carries the identical `moduleNameMapper` — a unit spec for any handler that injects `PrismaService` pulls the generated client into the module graph (even when every Prisma call is mocked), and without the mapper the suite fails to load with `Cannot find module './internal/class.js'`.
